# 云端账本发现（跨设备新建账本同步）需求文档

> 版本：v1.0  日期：2026-08-14
> 关联设计：`/prd/remote_ledger_discovery/design.md`
> 前置功能：`/prd/startup_sync_check/`（启动时云端数据拉取检查）

---

## 1. 背景与目标

### 1.1 背景

路径 A（S3 / WebDAV / Supabase / iCloud）的同步是"按本地账本逐个对照云端文件"的模式：
云端文件名为 `ledger_<本地id>.json`，启动检查器（`StartupSyncChecker`）只遍历**本地已存在**的账本并逐一检查其对应云端文件。

由此产生功能缺口：设备 A 新建账本（如 id=5）并上传 `ledger_5.json` 后，设备 B 本地没有 id=5 的账本行，永远不会去检查这个文件 → **设备 A 新建的账本在设备 B 上完全不可见**，用户必须手动导入。

### 1.2 目标

- **云端发现**：启动检查时列出云端所有 `ledger_*.json` 文件，识别出本机没有的账本
- **用户确认**：发现新账本时弹窗展示账本名与交易数，由用户决定是否下载
- **完整导入**：确认后下载文件、创建本地账本行（保留远端 id 以维持后续同步）、导入全部交易/账户/分类/标签
- **零回归**：不影响现有启动检查流程；list 失败时静默降级（跳过发现，不阻塞原流程）

### 1.3 非目标

- 不覆盖路径 B（PiggyCount Cloud）——其账本发现由 SyncEngine 的 `readLedgers` 已实现
- 不处理"远端文件名 id 与本地不同账本撞号"的存量设计缺陷（路径 A 文件名即本地 id，撞号是既有语义）
- 不做后台周期性发现——仅随启动检查执行一次
- 不实现选择性导入部分账本——弹窗为整体确认/跳过（保持简单，账本数量通常很少）

## 2. 用户故事

### US-1：启动时发现云端新账本

**作为**多设备用户，
**我希望**设备 B 启动时能发现设备 A 上传到云端的、本机没有的账本，
**以便**新账本无需手动导出/导入即可出现在所有设备上。

验收标准：
- 启动检查流程中，在逐账本状态检查之前执行云端文件列表
- 列出根目录下所有匹配 `ledger_<数字>.json` 的文件
- 与本地账本 id 对比，得出"本机没有"的账本列表
- 本地零账本的新设备同样能发现（现有 `ledgers.isEmpty` 提前返回需移到发现之后）

### US-2：确认后下载新账本

**作为**用户，
**我希望**看到新账本的名称和交易条数后再决定是否下载，
**以便**避免误拉陌生/废弃的云端数据。

验收标准：
- 弹窗列出每个新账本的名称（来自文件 payload 的 `ledgerName`）与条数（`count`）
- 用户选择"下载"→ 逐个导入，overlay 显示应用进度；完成后显示"已下载 N 个新账本"
- 用户选择"跳过"→ 不导入，继续原启动检查流程
- 导入的账本参与后续逐账本检查，且应为 inSync（本地=云端指纹）

### US-3：异常降级

**作为**用户，
**我希望**云端列表失败（网络/权限/后端不支持）时启动检查照常进行，
**以便**发现功能永不阻塞原有同步体验。

验收标准：
- `list` 抛异常 → 记日志，跳过发现，继续原流程
- 单个文件下载/解析失败 → 记日志，跳过该账本，不影响其他
- 加密密文无法解密（无密钥）→ 跳过该账本（不触发崩溃），存量加密恢复流程不变

## 3. 边界条件与风险

| 场景 | 处理 |
|---|---|
| 云端存在 `ledger_5.json` 但本地已有 id=5（不同账本） | 视为"本机已有"，不发现（路径 A 既有语义，本次不解决撞号） |
| 导入时本地已有人抢先建了同 id 账本（极端竞态） | 导入前再查一次，已存在则跳过并记日志 |
| 云端文件为空账本（count=0） | 正常创建空账本（不适用"拒绝空覆盖"——本地无对应账本，无覆盖风险） |
| payload 缺 `ledgerName`/`currency`/`monthStartDay` | fallback：名称 `云端账本 N`、币种 CNY、起始日 1 |
| 远端 id 保留插入后，本地自增序列 | SQLite 显式插入 id 会推进 sqlite_sequence，后续本地新建账本从 max+1 继续，无冲突 |
| 加密开启时 | 下载内容经 `_decryptIfNeeded` 解密后解析；解密失败按 US-3 降级 |
