## 一、背景

两件事在报告里被并作一条，因为它们的产品后果是同一个：**用户看到界面坏了，但得不到任何解释**。

### 1.1 同步失败被归成「网络问题」

`SyncMetricsService.classifyError` 是同步失败归因的唯一入口，但当时有两处漏判/错判：

1. **「未配置云端」被吞成别的类**：用户根本没填凭据时，报错落进 `unknown` 或 `networkTimeout`，
   于是 UI 提示用户「检查网络」——而真正该说的是「你还没配置云端备份」。这与网络无关。
2. **`CloudNotAuthenticatedException` 漏判**：它是 `CloudAuthException` 的**兄弟类**而非子类，
   于是「未认证」这类最高频的同步失败掉进了 `unknown`，用户拿到的是「未知错误」。

### 1.2 展示层把归因结果丢了

- `sync_health_card.dart` 的错误分类标签是**硬编码英文字符串**，中文界面下显示英文——
  而这条信息恰恰是给用户看的。
- `cloud_sync_page.dart` 的备份/下载失败提示**自己判一遍**（只分 auth / 非 auth），
  没复用 `classifyError`，于是「未配置」和「数据损坏」都被兜成网络问题——
  即 1.1 修好的归因，在展示层又被抹掉了。

### 1.3 本地库损坏 = 静默的数据全空

`PiggyDatabase` 的打开路径对损坏库没有任何检测，而 `main()` 的启动链各自吞掉自身异常。
后果不是崩溃，而是**每条查询都失败**：用户看到一个数据全空、且没有任何解释的界面。
这是最坏的失败形态——静默，且用户无法自我解释，只会得出「我的账没了」的结论。

## 二、需求范围

### R1 同步异常归因补齐

- `SyncErrorClass` 必须能区分「未配置」与「网络失败」与「未认证」，且**判定的先后顺序正确**：
  「未配置」要先于 auth 判定（未配置时也可能抛出与认证相似的异常）。
- `CloudNotAuthenticatedException` 与 `CloudAuthException` 一并归入 `auth`。
- `SyncErrorClass.label` 是**稳定串**（用于日志/埋点的可聚合口径），不随 UI 语言变化。

### R2 展示层复用归因，且本地化

- `sync_health_card` 的错误分类标签走 l10n，未知枚举落 `syncErrOther`，**不得**硬编码英文。
- `cloud_sync_page` 的备份/下载失败提示统一复用 `SyncMetricsService.classifyError`，
  不再自判 auth/非 auth。

### R3 本地库损坏检测

- 提供只读探测：能区分 `ok` / `corrupted` / `unreadable` 三态。
- 探测**必须不修改数据库文件**（不跑迁移、不写入）。
- `corrupted` 的判定必须有**正面证据**（`PRAGMA quick_check` 返回非 `ok`），不允许「打不开就报损坏」。

### R4 损坏恢复引导

- 损坏时给出全屏引导，动作含：**导出留存** → **重置本地库**（二次确认）→ **稍后处理**。
- 引导不得依赖 `Navigator`/`AppDialog`（它渲染在 Navigator 之上）。
- 用户未被引导时，健康库的界面**逐帧不变**（零回归）。

## 三、验收标准

### AC-R1

| # | 场景 | 预期 |
|---|------|------|
| 1 | 未配置云端凭据 | `classifyError` → `notConfigured`（**不是** `networkTimeout`/`unknown`） |
| 2 | 抛 `CloudNotAuthenticatedException` | → `auth`（**不是** `unknown`） |
| 3 | 抛 `CloudAuthException` | → `auth` |
| 4 | 网络超时 / 网关错误 / 数据损坏异常 | 分别 → `networkTimeout` / `gateway` / `dataCorruption` |
| 5 | `notConfigured` 与 auth 同时成立 | `notConfigured` 优先 |
| 6 | `label` 稳定性 | 各枚举 `label` 为固定串，不随 locale 变化 |

### AC-R2

| # | 场景 | 预期 |
|---|------|------|
| 1 | 中文界面 + 网络超时 | 显示「网络超时」（**不是** `Network timeout`） |
| 2 | 未配置 | 显示「未配置」 |
| 3 | 未知枚举 | 显示 `syncErrOther`（不抛、不显示枚举名字面量） |
| 4 | 云同步页备份失败（未配置） | 提示指向「未配置」而非网络问题 |

### AC-R3

| # | 场景 | 预期 |
|---|------|------|
| 1 | 健康库 | `ok` |
| 2 | 库文件不存在（首次安装） | `ok`（不是 `unreadable`） |
| 3 | 非 SQLite 内容的文件 | `unreadable` |
| 4 | 0 字节文件 | `ok`（SQLite 视其合法空库，`quick_check` 返回 `ok`） |
| 5 | **WAL 库 + 主连接仍打开（旁路 `-wal`/`-shm` 存在）** | `ok`——**这是最危险的误报场景** |
| 6 | WAL 残留（主连接已关） | `ok` |
| 7 | 合法头 + 垃圾内容 | **不得**判 `ok` |
| 8 | 探测前后 | 文件字节与 mtime 不变（只读） |

### AC-R4

| # | 场景 | 预期 |
|---|------|------|
| 1 | 库健康 | 覆盖层不占据屏幕（零视觉影响） |
| 2 | `corrupted` | 标题 + 三个动作（导出 / 重置 / 稍后处理） |
| 3 | `unreadable` | 另一套正文（与 corrupted 的成因不同，措辞不同） |
| 4 | 诊断 `detail` | 不泄漏用户内容，不出现在 UI 文案里 |
| 5 | 点「稍后处理」 | 覆盖层隐藏 |
| 6 | 重置 | 需二次确认；确认态可取消 |
| 7 | 会话内已忽略 | 不再渲染 |

> 明确**不做**的事：原设计里有「从云端备份恢复」按钮，已移除——库损坏时写不进任何数据，
> 该按钮**必然失败**，属误导性入口。

### AC-通用

- `flutter analyze --fatal-infos` 零 issue。
- 全量 `flutter test` 通过（收获时：1209 passed / 1 skipped）。
- 无空 `catch` 吞错：新增路径的失败都要有 `logger` 痕迹。

## 四、非目标

- **不做写入侧预防（写后即验）**：每次写入后校验代价高、且收益不明，属需单独评估的取舍。
- **不自动修复损坏库**（`REINDEX`/`VACUUM` 之类）：损坏形态不可枚举，自动修复可能扩大损坏面。
- **不自动删除或搬移用户数据**：隔离只在用户显式确认后执行，且语义是「移到保留目录」而非删除
  ——损坏库往往仍可被专业工具部分恢复。
- 不改 `SyncMetricsService` 的对外上报口径（仅补枚举与判定），不新建埋点通道。
