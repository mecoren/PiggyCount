# 交易建模补全（F1）— 需求文档

## 一、背景

对标：钱迹把"退款 + 报销"作显性卖点；Firefly III 直到 #12651 才补齐退款机制（历史抱怨
#4826/#3457/#7697，其中 #7697 指出**退款应回补预算**）。本仓现状（评估时核实）：
`deletedAt` / `deleted_at` / `recycleBin` 全库零命中 —— 删除即物理删行，用户误删无法找回；
退款只有文案（`categoryIncomeRefund` 分类名、`tagDefaultRefundable` 标签），无实体建模。

本轮（`docs/optimization-plan-2026-09-19.md` §四 F1）拆成两半：

- **F1-a 软删除 / 回收站**：本轮已落地。
- **F1-b 退款关联 + 报销状态**：**移交下一轮**，理由见本目录 `design.md` 第三节。

## 二、需求范围（F1-a，本轮）

### R1 删除可恢复

- 4 个用户删除入口（首页滑动、分类详情、标签详情、搜索批量）一律改为软删。
- 软删的交易对**所有既有读路径不可见**：余额、统计、预算、首页列表、附件 GC 判存活
  都不必各自新增谓词就得正确。
- 恢复必须**无损**：交易本体逐字段回到删除前，标签关联与附件（含磁盘文件）原地保留。
- 非用户删除的路径**保持硬删**：同步 diff 的清理、AI 识别撤销。

### R2 回收站管理

- 一个页面列出本机已软删交易（含所属账本、金额、删除时间），支持单条恢复与就地彻底删除。
- 彻底删除连带辅助行与物理文件一起走；删账本 / 清空账本连带清回收站，且不越界动别的账本。
- 恢复冲突要如实告知，不得静默换 id 落回（那等于把标签/附件丢在原地）。

### R3 文案与实现一致

- 凡是"此操作无法撤销 / 删除后无法找回"这类已经变成假话的文案，必须改写。

## 三、验收标准

1. v44 迁移测试：`onCreate` 与 `onUpgrade` 两条路都建表 + 建索引，且建表**幂等**。
2. 行为回归（`test/data/recycle_bin_round_trip_test.dart`）钉住：软删后
   `getTransactionsByLedger` / `transactionsWithCategoryAll` / `totalsInRange` 全部看不到这笔钱；
   标签行 + 附件行 + 磁盘文件原地保留；恢复后整行逐字段相等；id 被占用时拒绝且不误删占用者；
   purge 连物理文件一起走；删账本/清空账本连带清回收站；孤儿扫描不报假孤儿。
3. F2 的报表测试附带一条交叉验证：软删的交易不进任何统计（含新的区间报表）。
4. `flutter analyze` 0 issue + 全量 `flutter test` 绿。

## 四、未纳入本轮

- 退款/冲正关联（`refund_of_id`）、报销状态（`reimburse_status`）：见 `design.md` §三。
- 预算结转 rollover + 超支主动推送：属 F3。
- 一键清空回收站 / 30 天 TTL 自动清理：**明确不做**（回收站只占被删交易的元数据行，
  无容量压力；自动删除用户数据是比不删更糟的默认）。
