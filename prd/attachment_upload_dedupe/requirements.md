# 附件对象上传并发去重需求（attachment_upload_dedupe）

## 需求理解

快照链路（WebDAV/S3/Supabase/iCloud）把附件二进制按内容寻址存为 `attachments/<sha256>.bin`。当**同一 sha256 被多个账本引用**、且这些账本的附件上传在时间上发生重叠时，同一时刻会有多路并发 PUT 同一目标对象，触发服务端覆盖竞态（WebDAV 上表现为 MOVE 抛 Windows `WinError 5`），失败路径随后自清理自己的临时对象，并向用户报「上传失败」。本需求在**客户端**收敛「同一 sha256 的并发上传」，保证同一 sha256 在任一时刻只有一路在传。

## 背景（2026-10-14 双端同步回归测试实测）

审计源 `scripts/webdav_test/wd_wdphase_20261014.err`：

```
20:50:55  PUT    …36b7793d….bin.tmp.1791982255943_0   → MOVE ✅
20:50:55  PUT    …36b7793d….bin.tmp.1791982255945_6   → MOVE ❌ PermissionError [WinError 5] 拒绝访问
20:50:55  PUT    …36b7793d….bin.tmp.1791982255950_7   → MOVE ✅
20:50:57  DELETE …36b7793d….bin.tmp.1791982255945_6   ← 上传失败路径自清理自身临时对象
```

- 三个临时名指向**同一 sha256**（`_tempSeq` 为进程级计数器，说明是同进程的三条并发路径）。
- **无损**：正式对象由成功路落位（`attachments/36b7793d….bin` = 24979B 在位），磁盘 `.tmp` 残留 0，云端 `piggycount-bak/` 3 个备份 zip 完整保留；代价是一次冗余流量、一次误计失败、一次服务端 DELETE 记录。
- 详见 `docs/synctest/WebDAV同步功能测试报告_20261014.md` §7 与 `scripts/live_db/run_20261014_wd/WD_delete_analysis.md`。

## 需求范围

### R1 同一 sha256 的并发上传收敛
- 当任一路径正在上传 `sha256 = X` 的对象时，其它路径对同一 `X` **不得再发起第二个上传 PUT**。
- 收敛维度 = **进程内、按 sha256**（与后端类型、账本无关）。

### R2 串行与重试语义不变
- 串行的多次同步语义保持：本轮失败的 sha 不进入「已上传」集合，下一次同步仍会重新尝试。
- 单账本内、**不同 sha 之间**的并发度（semaphore 4）保持不变。

### R3 可观测
- 被收敛（合并/等待）的上传在日志中可分辨（例如 `附件对象上传合并(同 sha 并发): <sha8>`），不与「真失败」混淆。

## 非目标

- **不改服务端 / 存储协议**：不做服务端 MOVE 竞态容错、不引入锁服务。
- **不改内容寻址、快照契约与 E2EE**：`attachments/<sha256>.bin` 命名、清单 `sha256` 字段、加密语义、快照格式版本（15）均不动。
- **不做对象 GC**：孤儿对象清理仍归「全量对账 GC」后续项（见 `attachment_binary_sync` 非目标）。
- **不改 Cloud 链路**（PiggyCount Cloud）的附件上传。

## 验收标准

1. **单测（并发合并）**：桩 storage 记录每个 sha 的 PUT 次数；两路并发引用同一 sha（模拟两个账本同时上传）→ 断言该 sha 的 **PUT 次数 = 1**，两路调用均不计 `failed`。
2. **单测（失败传播）**：首路失败时，等待路拿到失败且不重复 PUT；**下一轮**调用仍会重新 PUT（重试语义未被吞掉）。
3. **单测（并发度保持）**：多个不同 sha 仍并发（PUT 并发数 > 1，semaphore 4 生效）。
4. **端到端（WebDAV）**：复跑一轮全量上传，`附件对象上传失败` 计数归零；`scripts/live_db/run_20261014_wd/wd_audit.py` 中 **DELETE = 0**（回到 `VERDICT OK`）。
5. `flutter analyze` 无新增告警；既有附件相关测试全绿。
