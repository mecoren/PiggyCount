二、两个关键发现

发现 1：账户 ledger_id=0 不是数据损坏，是应用设计。
  • lib/services/data/account_dedup_service.dart 在每次启动引导阶段运行，把所有账户收敛为 全局实体（ledger_id=0，与账本解耦）。
  • 应用运行后，注入时写在账户上的账本归属（原本 2–6）被主动全局化，因此账本列表显示"账户 0"属正常终态，并非挂空。
  • 交易不受影响：transactions.ledger_id 仍为 2–6，每账本精确 500 笔，归账正确。
发现 2：两个实例出现云同步「串台」，账户互相污染。
  • 账户数从注入时的 50 膨胀到 97；且 16384 出现了 16416 专属账户名（如「校园一卡通」「学生支付宝」「饭卡」），16416 对称。
  • 几乎可以确定两个 dev 实例共用了同一个云同步账号/桶，运行时会互相同步，把对方账户拉进本地并全局化。
  • 后果：两边数据不再是「干净的差异化测试数据」，账本边界被云同步打破。

三、结论与建议

结构层面：两边完全一致（6 账本 / 97 账户 / 2500 交易 / 60 分类 / 交易归账正确 / schema 一致）。

内容层面：并不「一致」——账本名是刻意差异化的，且被云同步串台互相混入对方账户，已不是隔离的测试数据。

建议（如需恢复为干净、隔离的差异化数据）：

  • 让两个 dev 实例使用不同的云同步账号/桶，或在调试期间临时禁用云同步；
  • 断开同步后，重新执行 scripts/inject_into_live.py 注入流程（拉取→注入→推回→重启）；
  • 注意：在 PiggyCount 当前模型中「账户是全局的」，ledger_id=0 会被自动保持，无法通过该字段体现「每个账本专属 N 个账户」，但交易已正确挂在各账本下，统计/筛选不受影响。
