## 6. 问题分析

### 6.1 【风险·中】「从备份恢复」后方向断言仍误判 `localNewer`（与 S3 轮同源，两后端稳定复现）

**现象**（`WDZC_16384_upload_applogs.txt`）：

```
1791362672006 [CloudSync] 同步状态: 1 -> SyncDiff.localNewer
1791362686055 [CloudSync] 缓存命中: ledgerId=1, diff=SyncDiff.localNewer
（其余 7 个账本均为 SyncDiff.inSync）
```

此刻**本地 40011 / 云端 40012**（云端多一笔 ④ 自动同步的 `77.77`），按内容事实应为 `cloudNewer`。

**归因**（`WDZ_restored.sqlite`，与 S3 轮 `S3Z_restored2.sqlite` 逐项一致）：

1. 恢复落 9 条 `snapshot_restore/success` 地板行（8 逐账本 + 1 整轮）。
2. 地板对 `ledgers.updated_at` **已生效**（各账本 `updated_at ≤ 其地板 ts`）。
3. **`local_changes` 残留 1 行未推送**：`id=40 type=category entity_id=29 ledger_id=0 created_at=1791164563 pushed_at=NULL`（注入时刻的历史残留，未被 `_purgeStaleLocalChanges` 清除）。
4. 条件 b（未推送 `local_changes`）按设计不设地板 → 恒真 → 判 `localNewer`。

**后果**：`startup_sync_checker.dart` 只对 `cloudNewer` 弹窗 ⇒ 该误判**不弹窗**；用户按同步页指引「上传」会把云端较新副本回退（本轮收敛轮实测把云端 40012 覆写为 40011，只存在于云端的那一笔丢失）。**属静默失败家族**，与 13:47 版报告 §6.6 相同，但本轮证明 `90a015b0` 的「恢复地板」修复**未闭环**（未覆盖上述残留）。

**建议**：`_purgeStaleLocalChanges` 需清掉「快照时点之前产生的未推送行」，或在 `_localChangeEvidence` 条件 b 上同样套用恢复地板。

### 6.2 【文案/口径·轻】备份日志「整包」≠ 云端对象大小

| 来源 | 数值 |
|---|---|
| App 日志 `[Backup] 备份完成: PiggyCount-2026-10-07.zip 账本=8 附件=7 (跳过=0, 附件总量=128KB, 整包=2.1MB)` | 整包 = **2.1MB**（本地 zip 长度，`cloud_backup_service.dart:367`） |
| 服务端实测对象 | **3,891,711 B = 3.71 MB**，头部魔数 `BEECRYPT1:`（E2EE 信封） |
| 「从备份恢复」列表条目 | **3.7 MB**（= 对象大小，正确） |

建议把「整包」改称「zip」或补「信封后约 …」，避免与云端对象大小混淆。

### 6.3 契约外字段差异 5150+ 行为何属预期

同 S3 轮：集中在 `created_at` / `updated_at` / `created_by_user_id` / `last_edited_by_user_id` / `is_shared` / `member_count` / `owner_user_id` / `cloud_file_id` / `cloud_sha256` / `tag_sync_ids_override`，均为设备本地写入时刻 / 本机身份 / 云端定位信息 / 覆盖语义索引列，**不进同步契约**。

### 6.4 回收站（`deleted_transactions`）两端不同，属设计行为

ZC 轮 `A=2 / B=0`。回收站是刻意的**设备本地态**：归档行进本地表，不入快照 / 不入备份 / 不上云。
