## 1. 测试环境与「后端不可达」排查（阻断 → 解除）

| 阶段 | 现象与证据 |
|---|---|
| **阻断** | 清库造数后切到 WebDAV，A 端冷启动弹窗：`8 个账本同步状态检查失败（网络或超时），请检查网络后重试`；`我的 → 云同步`页「同步健康」卡：`近 30 天成功率 0.0% · 成功 0 · 失败 1 · 主要失败类别：网络超时 × 1`；同步页长时间处于状态查询忙碌态，「全量上传 / 全量下载」行**不可点击**（a11y 合并为单个不可点容器），UI 无法继续驱动 |
| **定位** | 测试入口 `netcheck` 直连探测（`HttpClient`，自签证书放行）：<br>• WebDAV `https://10.0.2.2:8443` → `SocketException: Connection refused (errno = 111)`，2106 ms<br>• 对照 S3 `https://oss-cn-shenzhen.aliyuncs.com/` → **HTTP 403**（未鉴权根路径的正常响应），170 ms<br>→ 设备出网正常，**仅 WebDAV 端点无监听**（服务未启动） |
| **解除** | 仓库自带 WebDAV 回归对端：`scripts/webdav_test/README.md` + `webdav_server.py` + 自签证书（SAN 含 `10.0.2.2`）。执行 `python webdav_server.py`（`root=scripts/webdav_test/data`，`auth pctest / piggy123`）后复测：<br>• WebDAV `https://10.0.2.2:8443` → **HTTP 404**，214 ms（可达）<br>• 随后 App 启动检查不再报错，`全量上传/全量下载` 行恢复可点 |
| **安全动作** | 启动服务前已把服务端既有数据整体备份到 `%TEMP%\piggycount-sync-test\webdav-server-data-backup`（53 个文件），避免本轮上传覆盖历史槽位后无法回溯 |

> 结论：**WebDAV 测试的初始失败是测试环境（服务端未运行）问题，不是应用缺陷**；配置（URL/凭据/remotePath）自始至终完好。

## 6. 问题分析

### 6.1 【缺陷·轻】转账行分类字段在快照中两端不对称（与 S3 轮同源）

| 项 | 内容 |
|---|---|
| 现象 | 恢复端转账行 `category_id` 恒为 NULL；两端快照 payload 因此字节不同（8/8），但 `contentFingerprint` 相同、diff 判无变化 → 不告警、不收敛、无声 |
| 跨后端验证 | **S3 与 WebDAV 表现完全一致**（同为 8/8、同为「仅转账行差异」、同为指纹相同）→ 缺陷在**共享的序列化/恢复链路**，与后端实现无关 |
| 根因（证据链） | ① **导出侧** `lib/cloud/transactions_json.dart:160,177-178` 未对转账归空（转账虚拟分类在快照 `categories` 全量数组里，`transactions_json.dart:300-353` 无 transfer 过滤）；<br>② **分类解析正常** —— 全量恢复 `lib/services/data_import_service.dart:1592-1612`（`'kind\|name'` 查 categoryCache）与 diff 合并 `lib/cloud/sync_diff_service.dart:828-829`（经 `_resolveCategoryId`，同文件 1019-1026）都能命中虚拟转账分类；<br>③ **写库时被显式丢弃（两处对称写死）** —— **全量恢复** `lib/services/data_import_service.dart:1757` `categoryId: d.Value(tx.type == 'transfer' ? null : categoryId)`（本轮「下载」/「全量下载」实际路径）；**增量合并** `lib/cloud/sync_diff_service.dart:860`；<br>④ **指纹侧** `lib/cloud/sync_fingerprint.dart:16-17, 86-88, 134-137` 对转账忽略该两项；<br>⑤ **diff 侧** `lib/cloud/sync_diff_service.dart:166-171, 418-427` 两侧归空比较；<br>⑥ 次要放大点 `data_import_service.dart:1601`（transfer 永不补建分类）；⑦ 不自愈（`seed_service.dart:841-861 migrateTransferTransactions` 仅升级/首次 seed 触发）；⑧ `sync_diff_service.dart:164-165` 注释声称「导出侧归空」与实现不符。<br>完整链路、测试覆盖盲区（`sync_diff_category_and_zero_amount_test.dart:180` 的不实注释、契约 fixture 期望）与修复方案见《S3同步功能测试报告_20261002.md》§6.1。 |
| 影响 | 业务数据无损；但快照字节级不可比、契约存在静默不对称，且一旦该字段进入指纹/被赋予语义将立即演变为「指纹永久 different 但无变更可应用」的 S11 同构故障 |
| 建议 | 导出侧与 apply 侧口径二选一对齐（转账输出空 **或** 恢复端回填虚拟转账分类 id），并在 `test/cloud/sync_contract_coverage_test.dart` 增加该口径门禁；**不得直接改测试通过**。详见《S3同步功能测试报告_20261002.md》§6.1 |

### 6.2 数据差异原因说明（用户要求「如发现数据不一致，分析并记录差异原因」）

| 差异 | 原因 | 是否缺陷 |
|---|---|---|
| 转账行 `categoryName/categoryKind`（8/8 账本） | §6.1：导出侧未按「转账归空」口径序列化，恢复端按设计写 NULL | **缺陷（轻）** |
| R2 合并路径下 `transactions` 4960 vs 5000 | SYNC-05：合并默认不应用「云端删除」，需显式勾选；全量下载（覆盖语义）可收敛 | 预期设计 |
| R2 中账本改名 / `monthStartDay=15` 未自动跨端 | 该账本未被列入「云端有更新」候选（`startup_sync_checker.dart:501-512` 只收 `cloudNewer`，`different`/unknown 不弹窗），故未进入合并；全量下载（覆盖语义）可收敛 | 设计边界（详见 S3 报告 §6.2） |
| 启动检查只列 1 个账本 | 仅「云端净新增」的账本进入合并弹窗；纯删除/纯元信息变更不列 | 预期设计 |
| 「状态获取失败」状态行 | 夹具清表导致 `current_ledger_id` 指向已不存在的账本 | 夹具副作用（健壮性可优化） |
