# S3 同步功能测试报告（2026-10-24）

## 1. 结论

**通过（PASS）**。在双端从空库起步、8 个账本 × 约 5000 笔交易的规模下，S3 全量上传 / 全量下载 / 自动同步 / 立即备份 / 定时备份 / 从备份恢复均跑通；5 轮「A 端变更 → 上传 → B 端冷启动 → 全量下载」的强校验，以及恢复后与提醒功能测试后的两次终态收敛，同步契约内字段均为 **0 非预期差异**。

测试过程中**未删除、未重置、未改写任何云服务凭据或 E2EE 密钥**：两端 `FlutterSecureStorage.xml` 的 sha256 与测试前逐字节一致（A `af1a6744…` / 2269B，B `17d8f173…` / 5805B），S3 凭据、WebDAV 凭据、加密密钥、自动同步开关均保持原位；仅按测试步骤通过 UI 切换了「当前云服务」这一运行时选择。为实测定时备份与提醒去重，临时调整过本地 `backup_time` / 冷却时间戳 / 预算提醒水位，测试后均已恢复或仅保留正常成功标记（详见 §5.4、§5.6），不涉及云端凭据与密钥。

## 5. 专项功能验证

### 5.1 全量上传 / 全量下载
- R1、R2~R5、Z、F 共 7 次「全量上传」，每次均出现两层危险确认（倒计时结束才可点），完成后进入 `SyncDiff.inSync`。
- 7 次「全量下载」均以 8/8 账本导入结束；R1 首次导入日志：`云端新账本导入完成 8/8 个`。
- 下载导入明细：`TxImport` 每本 5001 笔，`BudgetImport` 3 条、`RecurringImport` 3 条、`SavingsGoalImport` 1 条、`RateOverrideImport` 完成，失败 0。

### 5.2 自动同步
- 测试前 `auto_sync=true`。预算提醒用例新增 88888 元支出后，18:09:51 触发预算通知，18:09:54 日志出现 `Starting upload: ledger_433218b8-…json`，未手动点上传即完成自动上传。
- S3 专项脚本另以 77.77 元新增交易验证「自动同步开启 → 等待 20s → 云端出现更新」，通过后由「从备份恢复」回滚。

### 5.3 立即备份
- 页面显示「最近备份：2026-10-24 · 成功」，备份包为 `PiggyCount-2026-10-24.zip`。
- 日志：`备份完成: PiggyCount-2026-10-24.zip 账本=8 附件=7 (跳过=0, 附件总量=128KB, 整包=2.1MB)`；备份为 E2EE 密文包。

### 5.4 定时备份
- 定时开关开启、时间设为 22:00；为实测真实触发，临时把本地 `backup_time` 改为 `00:00`、`backup_auto_last_attempt_ms` 清零（只改本地备份偏好，不碰任何 `cloud_*` / `piggycount_enc_*` 键），冷启动后等待调度器。
- 18:12:32 日志：`备份完成: … 账本=8 附件=7 … 整包=2.1MB` + `定时备份完成`；随后把 `backup_time` 恢复为 22:00，`backup_auto_last_date` 保留当日成功标记（正常去重）。

## 6. 一致性判定口径与结果

- **契约内字段**：账本、账户、分类、标签、交易、预算、周期规则、汇率覆盖、持仓、储蓄目标、自定义字段、附件元数据，逐字段比对 **0 非预期差异**。
- **设计内不同步 / 预期差异**：
  - `deleted_transactions`（回收站）只在本机：A 端 R4 后 3 行、B 端 0 行，符合设计；
  - `transaction_attachments.created_at` 9 行设备时间差异，属契约外字段；
  - 持仓行情缓存仅 A 端有，属设备本地缓存；
  - 每轮 40150 / 终态 40158 行「契约外字段差异」涉及 8 张表，均为 `created_at` 等设备本地列，比对脚本明确标注为预期。
差异原因说明：

| 差异项 | 观测 | 原因 |
| --- | --- | --- |
| 附件 `created_at` | 每轮 9 行 | 附件导入时由各端本地写入，属契约外字段，不参与同步 |
| 回收站 `deleted_transactions` | A 3 行 / B 0 行 | 回收站为设备本地表，设计上不上云、不进备份 |
| 持仓行情缓存 | A 2 行 / B 0 行 | `quote_price` 为设备本地行情缓存，不进快照 |
| 契约外字段差异 | 每轮约 40150 行 / 终态 40158 行，涉及 8 表 | `created_at` 等设备本地列，比对脚本标注为预期 |
| 分类数 29→28 | R4 | 脚本重复点击期间删除未引用的种子分类「测-转账」（触发点未能还原），B 端全量下载后同样 28，两端一致 |
| 恢复后 77.77 回归 | Z 轮 | 恢复只覆盖本地，云端仍保留恢复前自动上传的数据，启动检查按「云端更新」合并 |

- 结论：**同步契约内完全一致**；差异均落在设计声明不同步的列/表，或因测试脚本操作产生的、已双端一致的数据演化。

## 7. 问题与观察

1. **R4 测试脚本自检误判（测试工具问题，非产品缺陷）**：`mut_r4.py` 的左滑删除在「删除后行文本仍匹配其他行」时重复点删除，自检返回 `soft_delete=False`，但实际两次软删均已落库（回收站 3 行、321.09 不在明细）。重复点击期间还观察到未被任何交易引用的种子分类「测-转账」被删除（分类数 29→28）；具体触发点在现有 UI 自动化日志中无法还原。该变更在 B 端全量下载后同样为 28，两端一致。后续脚本应给删除行加唯一 syncId 定位，避免重复点击。
2. **从备份恢复只覆盖本地**：恢复后云端仍保留恢复前自动上传的新增交易，A 端下次启动会按「云端更新」合并回来。这是既有设计，但用户若期望「恢复 = 云端也回滚」，需要在 UI 文案或流程上进一步明确。
3. **启动合并弹窗未处理时定时备份一直让位**：`SyncRestoreGuard.isBusy` 在「云端有更新」弹窗等待用户选择期间保持为真，调度器每分钟打 `恢复进行中，本轮定时备份跳过`。互斥本身正确（避免半恢复态打包），但日志文案把「等待用户确认合并」写成「恢复进行中」，容易误导排查。建议后续区分 `waiting-merge` 与 `restoring` 两种状态。
4. **预算提醒按周期去重**：同一预算同一周期只推一次，属预期；重复测试需重置本地水位，报告已说明仅改本地键。
5. 未发现数据丢失、重复交易、账本缺失、E2EE 解密失败等同步缺陷。
