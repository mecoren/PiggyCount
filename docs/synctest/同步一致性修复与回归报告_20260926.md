### 1.1 关键设计约束（P0 最容易写错的地方）

`ImportAccount.name` / `ImportCategory.name` 是**必填字段（恒非 null）**。若用「非 null 即需更新」判定，每轮合并都会对全部实体做无意义 UPDATE 并登记假 change。因此两处改动都是**与本地实际值比较的差异判定**，并由单测锁死：

- `账户名相同 → 不产生无意义 local_changes 写入`
- `分类名相同 → 不产生无意义写入`
- `目标名已被别的账户/分类占用 → 保守跳过改名，且不抢占对方 name 映射`

### 1.2 刻意不做的事（Ponytail 最小改动纪律）

| 项 | 结论 | 理由 |
|---|---|---|
| 在同步预览弹窗里新增「账本名不同 / 币种不同」明细行 | **跳过** | 计划中设想的落点（`sync_diff_service.dart:401-411`）实为**逐笔交易**的差异文案收集处，并不存在账本级元数据 diff 通道；要新增需打通 `computeDiff` → `SyncPreview` → 预览弹窗三层结构 + l10n，属于为一行提示新增一条管线。账本改名后用户已能在同步页看到「云端有更新」并在合并后看到账本名变化，收益不足以支撑该改动。需要时可另开任务补 |
| 改 SYNC-05 的 `deleted` 默认不勾选 | **明确不做** | 属防误删设计，本次仅改善可见性 |
| 为 P3 标记落盘持久化 | **不做** | 会增删 `FlutterSharedPreferences.xml` 键，破坏云配置完整性回归口径；改用会话内 provider |
| 给逐行 tag 更新新增 `updateTagsBatch` 仓储接口 | **改为更小方案** | 复用既有批量读 `getTagsForTransactions` + 只写变化行，避免改 `BaseRepository` 接口（多处实现与 mock） |

## 2. P2 性能定位（先采集，后修复）

### 2.1 埋点与采集方法

- 在 `_applySyncChangesInternal` 内把原先覆盖整段的大 `Stopwatch` 拆为**分阶段计时**（categories / accounts / tags / customFields / recurrings / budgets / rates / added / modifiedMain / modifiedTags / deleted），每账本输出一行 `[perf] ledger=N phase=full ...`；
- `importAccounts` 内对单次 `updateAccount` 抽样，输出最慢 3 次；
- tag 循环内抽样最慢 3 行；
- **采集纪律**：合并期间不执行 `uiautomator dump` / `screencap`（会阻塞 App UI 线程，污染耗时观测）——上一轮的 226s/30-54s 观测即受此影响，本轮起复测均在无 UI 自动化干扰下进行。

### 2.2 采集结果（修复前，单账本 1407 条 modified，WebDAV）

```
[perf] ledger=2 phase=full categories=18ms accounts=21855ms tags=312ms customFields=0ms
       recurrings=44ms budgets=15ms rates=46ms added=41ms modifiedMain=1438ms modifiedTags=5553ms
[perf] 慢写 top3: 401ms(历史-储蓄卡CNY-1) 397ms(医疗-储蓄卡CNY) 387ms(储蓄卡)
[AccountImport] 账户导入完成: 新增=0 更新=61 耗时=36974~54086ms   （连续 4 个账本）
```

**结论**：单账本合并约 29.3 s，其中

| 阶段 | 耗时 | 占比 | 性质 |
|---|---|---|---|
| **accounts** | **21 855 ms** | **75%** | 61 个账户各开一次 `db.transaction`；**账户是 user-global，每个账本的快照都带同一份** → 8 个账本重复写 8 遍，7/8 为纯冗余 |
| modifiedTags | 5 553 ms | 19% | 1407 行逐行 `updateTransactionTags`（每行一次事务，代码注释早已标注「量大时需专门的 batch tag-update 接口」） |
| modifiedMain | 1 438 ms | 5% | 单事务批量 UPDATE，**不是瓶颈** |

**单位成本机制（由写链路只读审计补齐，与上述耗时完全吻合）**：成本正比于**顶层事务提交次数**，而非 CPU。

- 合并路径 `_applySyncChangesInternal` **没有外层事务**，于是每个 repo 写方法自带的 `db.transaction()`（`local_repository.updateAccount` = `local_repository.dart:2257`、`updateTransactionTags` = `:3298`）都成为**顶层提交**；
- 对照全量恢复路径：`data_import_service.dart:1826-1846` 用**一个外层 `db.transaction`** 包住「清空 + 导入」，内部事务退化为 savepoint（`:1815-1816` 注释原文），**只提交一次**；
- 库配置 `db.dart:636-649`：`journal_mode=WAL` 且 `synchronous` 保持默认 **FULL**（该处注释即写明「WAL+FULL 仍然每次提交 fsync」），且 DB 跑在**第二个 isolate**（`db.dart:636`）⇒ 每次顶层提交 = isolate 往返 + fsync。

因此两个热点恰好就是**提交次数最多的两个循环**：61 个账户各一次（+ `updateAccountSortOrders` 又一次）与 1407 行 tag 各一次。修复后这两个循环的**无变化行全部不再写**，提交次数塌缩为每账本个位数（见 §2.3），耗时随之塌缩 —— 这正是「fsync × 提交次数」而非「算法复杂度」的直接证据。

> 附带排除项：审计确认**不存在**「每写一次就重算账本指纹 / 重导出账本」的路径。`onLocalContentGeneration` 唯一监听者 `transactions_sync_manager.dart:2494-2516` 只清内存指纹缓存（不导出、不算指纹），且抑制上下文下 `change_tracker.dart:180` 已提前 return，回调根本不触发；`exportTransactionsJson` 只在 getStatus 缓存未命中（`TSM:2660/2676`）、上传（`TSM:1176`）、备份（`cloud_backup_service.dart:203`）时发生。故两项耗时**纯属写路径成本**。

### 2.4 勘误：「`modifiedTags` 固定读成本」的假设被证伪（随后由补充修复 ② 解决）

报告初版把 `modifiedTags` 残留的 ~320~650 ms 归因为「一次批量读 `getTagsForTransactions` 的固定开销」。**该归因是错的**，实测证伪：

在真实快照（`FIX1_B2.sqlite`，`transaction_tags` 11 947 行）上对本就等价于 drift 生成语句的 JOIN 做对照计时（`B1_tag_query_bench.py`）：

| 场景 | 中位耗时 | 最大 |
|---|---|---|
| 取 6 个 transaction_id 的 tag（**有索引**） | **0.014 ms** | 0.026 ms |
| 同上的对照（删索引后） | 0.858 ms | 1.051 ms |
| 取 102 个 transaction_id 的 tag（**有索引**） | **0.056 ms** | 0.233 ms |
| 同上的对照（删索引后） | 0.885 ms | 1.216 ms |

即：**该查询在毫秒以下，与 id 个数几乎无关，根本不可能产生 0.3~1.0 s**。

真正原因（随后被 P1 修复直接证实）：`modifiedTags` 是紧跟在 `updateTransactionsBatchBySyncId`（一个大批量事务）之后的第一个 `await` 段 —— **上一个事务的提交尾巴（isolate 往返 + WAL fsync）被归因到了下一段计时**。证据：

- `accounts` 阶段「61 个账户里只有 1 个真实更新」耗时 350~625 ms（P1 后 **15~32 ms**）—— 一次顶层提交的真实价格；
- `modifiedTags` 在**零写库**（全部 skip）情况下仍报 254~1 064 ms，P1 后降到 **1~14 ms**；
- 二者之和在各账本间相对稳定（~0.5~1.4 s），说明是同一笔「提交尾巴」在相位边界上来回搬运。

结论：残留成本属于**写/提交路径**（顶层提交次数 × fsync），不是读路径 —— 正是下面的补充修复 ②。

> 命名说明：§1 的 P0/P1 指**改名类**四项（账户/分类改名、账本 name+currency）；本节新发现的缺陷沿用现场沟通里的编号 —— **补充修复 ①（索引缺陷）** 与 **补充修复 ②（合并外层事务）**。

### 2.5 补充修复 ①（索引缺陷）+ ②（合并外层事务）实测收益

**① 索引缺陷**：全新安装库缺失 6 个索引（详见 §2.6）。修完后设备端 `EXPLAIN` 由 `SCAN` 变 `SEARCH ... USING INDEX`，对照测量 0.86 ms → 0.014 ms（**16~61×**）。它**不是** `modifiedTags` 残留的主因（见 §2.4），但修好了多条日常读路径。

**② 合并 apply 补外层事务**：在 `TransactionsSyncManager.applyPreviewChanges` 把整个 apply 包进 `db.transaction`，与全量恢复路径（`DataImportService._restoreLedgerFromJsonTx`）口径对齐 —— 内部各写方法的事务降级为 savepoint，**每个账本只提交一次**。

| tags | 312 | 0~7 | 0~12 |

### 2.6 补充修复 ① 详情：6 个索引在全新安装库里永久缺失

**缺陷**：`lib/data/db.dart` 里这 6 个索引**只在 `onUpgrade` 的历史分支创建**，`onCreate` 从未创建：

| 索引 | 版本 | DDL 位置 |
|---|---|---|
| `idx_transaction_tags_transaction` | v10 | `db.dart:840` |
| `idx_transaction_tags_tag` | v10 | `db.dart:842` |
| `idx_budgets_ledger` | v11 | `db.dart:857` |
| `idx_budgets_category` | v11 | `db.dart:859` |
| `idx_budgets_ledger_type` | v11 | `db.dart:861` |
| `idx_attachments_transaction` | v12 | `db.dart:876` |

因此**新装库**（走 `onCreate`）与**版本已越过 v12 的存量库**（`from < 10/11/12` 永不成立）都永久缺失。三重取证：

1. **实测索引集合**：全新安装库只有 **23** 个索引，上述 6 个全部不在其中（`A2_index_audit.py` 对照「源码声明的索引」vs「实际存在的索引」）；
2. **查询计划**：`EXPLAIN QUERY PLAN` 对 `WHERE transaction_id IN (...)` / `WHERE transaction_id = 1` 均报 **`SCAN`**（全表扫描）；
3. **影响面**：合并路径每账本 tag 批量读、按标签筛交易、预算用量统计、附件角标与孤儿附件 GC 全部全表扫描 —— 规模随数据线性退化。

**修复（两个动作缺一不可）**

1. `onCreate` 补建（`:1742-1744`，调用 `_createV48RepairIndexes()`）→ 只救**新装用户**；

## 6. 已定位为「非缺陷」的现象

| 现象 | 结论 |
|---|---|
| S3REG3 残留 `month_start_day` 差异（A=29 / B=28） | **测试夹具越界值**。`month_start_day` 口径为 1..28（`ledgers` v27 schema 注释、`local_ledger_repository.updateLedger` 与 `_applySyncChangesInternal` 均 `clamp(1,28)`）。造数脚本每轮 `+1` 累积到 29，属应用自身产生不了的值；导入侧 clamp 到 28 → 双端必然不一致。已修正造数脚本为 28→1 循环，S3REG4 随即 0 差异。**产品侧行为正确（不该接受越界值）**。 |
| 上一轮观测到的 `[SyncDiff] 批量更新: size=739 耗时=226603ms` | **是"提交次数 × fsync"的极端样本，但受测量方式放大**：该数值覆盖「1 次主表批量事务 + 739 次逐行 tag 顶层提交」，且当时并发跑了 `uiautomator dump`（阻塞 App UI 线程）。同规模（1407 行）在无并发 dump 的干净环境下，修复前 `主表+tag` 合计 6 991 ms → 补充修复 ② 后 **27 ms**。故本次以**分阶段埋点 + 对照测量**为准，不再引用该单点数值。 |
| 全量恢复路径 `AccountImport 更新=61` 仅 391~4 524 ms（同函数、同设备） | 与合并路径的差异根源是**顶层提交次数**：合并路径无外层事务，61 个账户各一次顶层提交（fsync）；恢复路径被外层事务包住、内部为 savepoint，只提交一次。补充修复 ② 之后两条路径量级一致（15~36 ms）。 |
| 判定"6 个索引缺失导致 `modifiedTags` 残留 ~0.5 s" | **该归因被实测证伪**（见 §2.4）：有索引后该查询仅 0.014~0.056 ms。索引缺失是**真实缺陷**（§2.6，多条日常读路径全表扫描），但它不是那 0.5 s 的原因；那 0.5 s 是提交尾巴的归因错位，由补充修复 ② 解决。 |

### 11.2 残留风险：附件物理文件删除发生在事务提交之前（本轮不修）

路径：`local_transaction_repository.dart:1871` 开事务 → `:1948` 调 `_gcUnreferencedAttachmentFiles` → `:2071-2085` 删文件 + 缩略图。

- 该调用**原本就在事务内**，但那时事务紧接着提交（窗口 ≈ 微秒级）；补充修复 ② 把外层事务拉长到整个账本 apply 后，窗口变成「主表/附件阶段 → tag 循环 → 删除阶段 → 提交」，对 5000 行合并是**秒级**。
- 若该窗口内进程被杀（或异常逃逸触发回滚），附件行会被回滚恢复，而文件已删 → 行指向不存在的文件。
- **缓解因素**：① 行上仍保留 `localSha256`（v34 内容寻址锚点），附件二进制同步会按 `attachments/<sha256>.bin` 补齐，属自愈路径；② 启动回填任务 + 维护页孤儿文件 GC 兜底；③ 触发还需「本次合并确实移除了附件」，概率低。
- **精确修法**（仓库内已有同款纪律）：参照 `transactions_sync_manager.dart:118-121` 的 `_pendingAttachmentJobs`「**恢复/导入事务提交后入队**」写法 —— 让 `updateTransactionsBatchBySyncId` 只**收集**待删文件名（不在事务内删文件），由 TSM 在 `db.transaction(...)` 返回后统一 drain。
- **本轮不做**的理由：候选集合要从仓储层传出，属接口级改动（`TransactionRepository` 接口 + 实现 + 测试替身）；收益是关闭一个秒级窗口内的极低概率事件，且已有自愈兜底。若后续进一步扩大事务范围（例如把 added 阶段也纳入外层事务），应优先做此项。

### 11.3 未做设备验证的 1 项：`SyncDiff.different` 指引文案

已核实方向判据的**权威实现**（本地 path 依赖，可读可改）：`packages/flutter_cloud_sync/lib/src/manager/cloud_sync_manager.dart:624-682`。指纹不一致时：
