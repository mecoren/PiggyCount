## 1. V3A：三类型 × 取值形态 —— 通过 ✅

**夹具** `modify_cf_v3.py`：把三类型**都铺到 8 个账本**（补齐 6 个缺失的 `date` 定义 → 24 个定义，每类型 8 个），每账本取 8 行、按 **8 种取值形态轮转**写入三类型值。

| 形态 | text | amount | date |
|---|---|---|---|
| 0 | 中文与符号 `✓` | `0.0` ← **金额 0 合法** | `2026-03-15T00:00:00.000` |
| 1 | emoji `🎉` | `-12.5` | `2019-12-31T23:59:59.999` |
| 2 | 普通文本 | `100.0` ← 整数值 | `2024-02-29T12:00:00.000` ← 闰日 |
| 3 | **多行** `\n` | `99.9` ← 尾随零归一路径 | `1999-01-01T00:00:00.000` |
| 4 | **90 字长文本** | `999999999999999.0` ← `<1e15` 整数分支 | `2038-01-19T03:14:07.000` |
| 5 | 含 **`U+0001`**（canonical 分隔符） | `1000000000000000.0` ← **正好 `1e15`**，浮点分支边界 | `2000-02-29T00:00:00.000` |
| 6 | 含 `=` | `0.01` | `2026-12-31T23:59:59.000` |
| 7 | 引号 `"` 与反斜杠 `\` | `-0.01` | `1900-01-01T00:00:00.000` |

**结果**（A 上传 8/8 → B「下载同步」每账本 `修改=8`、8×8=64 全应用）：

```
[1] 定义 A=24 B=24   type=amount 8/8  type=text 8/8  type=date 8/8
    仅A=0 仅B=0 同syncId但内容不同=0
[2] 有值交易 A=112 B=112  ★应用口径不一致 (交易,字段) 对 = 0
[3] 按类型有效覆盖: amount 112 行/14 取  text 112 行/14 取  date 76 行/8 取
[GATE-OK] 所有 require 字段本轮均被有效覆盖：['custom_values_json']
```

**一个必须交代的坑**：Python `json.dumps(1e15)` → `1e+15`，而 Dart `jsonEncode(double)` → `1000000000000000.0`。夹具若直接用 Python 序列化，形态 5 会造出**假差异**（`compare_sync_final.py` 的 `_json_canon` 对数值字面量敏感）。已用 `dart_num()` 逐字面量对齐。

## 3. V3C：改类型 / 删除 / 空值语义

**夹具** `modify_cf_v3c.py`（每账本）：把 `待改类型` 由 `text` **改类型**为 `amount`；**删除** `新增金额` 定义并**按仓储行为连带清值**；另取 1 行写**显式空对象** `{}`。

### 3.1 结果总览

| 子项 | 结果 |
|---|---|
| **改类型** text→amount | ✅ **传播正确**（`同syncId但内容不同=0`，两端均为 amount；值不变，符合"值列类型无关"的设计） |
| **空值语义**（显式 `{}`） | ✅ **符合「空即缺失」**（见 §3.2） |
| **删除定义** | ❌ **未传播** → 缺陷 **D-4** |
| **清空字段值** | ❌ **未传播，且被回滚** → 缺陷 **D-3** |

B 端「下载同步」对 8 个账本全部报 **`修改=0, 删除=0, 新增=0`** —— 零变更，而 A 端实际改了 8 个类型、删了 8 个定义、清了 16 行值。

### 3.2 空值语义（通过，且是"空即缺失"的设备端证据）

`{}` 探针的链路已按代码推导并实测吻合：

- 导出 `transactions_json.dart:172,203`：先 `decode()` 规范化，**仅非空才写键** → 显式 `{}` 在云端**不产生 `customValues` 键**；
- 导入 `data_import_service.dart:992-995`：缺键 → `customValues=null` →「保持本地原值」；落库 `:1719` 走 `encode()`，空 map → 列写 **NULL**。

→ A 端保留 `{}`、B 端为 NULL，**应用 canonical 口径两者等价（都归一到 `''`）**，云端不携带该键。raw 列不同属规范化，不是缺陷。

## 4. 两处真实缺陷

### 4.1 D-3：清空自定义字段值无法传播，且会被云端旧值静默回滚

**机制（三处代码，逐条实测确认）**

| 环节 | 事实 |
|---|---|
| 导出 | `transactions_json.dart:203` —— `if (customValues.isNotEmpty) 'customValues': customValues` → **清空后不写键** |
| 差分 | `sync_diff_service.dart:503` —— `if (cloud.customValues != null && …)` → **缺键不比、不覆写**（策略②） |
| 指纹 | `sync_fingerprint.dart:128` —— 用 `canonical()` 参与白名单 → A 为 `''`、B 为 `'<sid>=7.25\x01'` → **两端指纹不同** |

→ 合成症状：**指纹说不同、diff 说无变化** —— 与 `sync_diff_service.dart:352-353` 注释里自己写的警告一字不差：

> ⚠️ **新增字段一律用 ①**。错用 ② 会让「云端真的删掉了该属性」也传不下来 → 两端指纹不同而 diff 为空 → 永久不收敛（**D-2 的机制**）。

`customValues` 正被列在策略 ② 的清单里（第 350 行）。而它**不像** `originalAmount` 那样有"旧客户端不写键"的真实历史包袱 —— 导出侧"仅非空才写键"是**确定性**的，所以 ② 在这里只会放大问题，不会防到任何东西。

**实测影响（决定性证据）**

| 步骤 | 观察 |
|---|---|
| A 删定义/清空值 → 上传 | 8/8 `Post-upload verify passed` |
| B「下载同步」 | 8 账本**全 `修改=0`**（零变更，A 的改动被忽略） |
| B 合并后**统一回传** | 把云端覆盖成 **B 的旧状态**（A 的清空被云端回滚） |
| B 端状态 | 8 账本 `SyncDiff.inSync`（B 看着"已同步"，实际云端已被它改回去） |
| **A 端再走「下载同步」** | 每账本 **`修改=2`**（8×2=16）→ **A 刚清空的 16 个值被静默恢复** |
| 终态 | A 定义 40 → **48**、有值交易 144 → **152**：**用户的删除与清空被丢弃**，两端"收敛"到 B 的旧状态 |

**用户可见后果**：清空某个自定义字段值 → 对端看不到；对端同步一轮后，**云端与A端都把这个值恢复了**（用户操作被回滚且无任何提示）。

#### 修复（已于当日实施并设备端复验通过）

**改法比预想的更小：只改导出侧一行，diff 侧无需改动。**

导出的 `customValues` 改为**始终写键**（含空对象）。这样 `_compareTx` 里那句
本就存在的 `cloud.customValues != null` 守卫，**天然从策略②变成策略①**：

| 快照形态 | 语义 | diff 行为 |
|---|---|---|
| `customValues: {}`（新版导出） | "这行确无值" | 严格比较 → 本地有值则判 modified → 可清空本地 ✓ |
| 缺 `customValues` 键（真·旧快照） | 旧客户端不认识该字段 | 守卫拦下 → 保持本地已填值 ✓ |

两者由"**键是否存在**"自然区分，**不需要 payload 版本判断**，也完整保留了旧快照的安全性。

关键前提（已由既有用例锁定）：指纹白名单用的是 `CustomFieldValueCodec.canonical()`，
**缺失与 `{}` 都归一到空串**（`sync_fingerprint.dart:128`）—— 所以"始终写键"**不会**
引入原注释担心的"缺失 vs 显式空"永久 outOfSync。原注释的担忧来自照搬
`originalAmount` 范式，但 `originalAmount` 的指纹走 `toString() ?? ''`（`null`→`''`、
`0`→`'0.0'`，确实不同），两者性质不同。

**验证**

| 项 | 结果 |
|---|---|
| 新增回归测试 | `test/cloud/sync_diff_custom_values_clear_test.dart`（5 项：清空判 modified / 应用后真清掉且收敛 / 旧快照缺键仍安全 / 解析层区分枢轴 / **端到端守门用例**） |
| **回退验证** | 临时把导出改回旧写法 → **3 项变红**，含端到端守门用例（证明它不是摆设） |
| 全量套件 | `flutter test` **1610 项通过**（+5） |
| 静态检查 | `flutter analyze` 改动文件 **No issues** |
| **设备端复验**（只清值、不动定义，保证可归因） | A 清空 16 个值（有值交易 152→136）→ 上传 8/8 → **B「下载同步」每账本 `修改=2`**（8×2=16，修复前恒为 `0`）→ 应用后 `有值交易 A=136 B=136 仅A=0 仅B=0`、应用口径不一致 **0** |
| **不再被回滚**（决定性） | 回传后 A 端再走「下载同步」→ **`变更已应用 = 0`**（修复前是 `修改=2×8`，把 16 个值全恢复） |
| 门禁 / 云配置 | `[GATE-OK] custom_values_json`、`CFG_OK` |

### 4.2 D-4：删除自定义字段定义在增量路径不传播

**机制**

| 路径 | 行为 |
|---|---|
| 全量恢复 `restoreLedgerFromJson` | **镜像删除**（`custom_field_sync_test.dart` 有用例覆盖） |
| 增量合并 `sync_diff_service.dart:627-633` | 直接调 `importCustomFields(...)`，而它是 **upsert-only、无删除分支**（`data_import_service.dart:827-867+`） |

**实测**：A 删掉 8 个定义后上传，B「下载同步」不删本地定义（`仅B=8`）；随后 B 回传又把它们写回云端，A 再同步时**又被重新导入**（A 定义 40 → 48）。

**定性**：这与 `ImportData` 对 budgets 的"upsert-only（旧快照误删的风险 > 删除不传播的不便）"是同一取舍，**可能是刻意的**；但**恢复路径做镜像删除、增量路径不做**，两条路径口径不一致，且用户视角是"删掉的字段又出现了"。**建议产品明确取舍**：要么增量也镜像删除（需处理"旧快照缺该定义段"的误删风险），要么在 UI 上说明"删除字段需用全量下载同步"。

> **本轮未改动**（与 D-3 不同：D-3 的修复是纯增益——把"不可表达"变成"可表达"，不动任何既有安全性；
> 而让增量路径镜像删除会引入"快照缺该段时误删本地字段"的真实风险，属产品决策，不擅自改）。

## 5. 工具口径提示（与产品无关）

`compare_sync_final.py` 的 `_json_canon` 用 `json.dumps(json.loads(x))`，对**数值字面量敏感**（`0` 与 `0.0` 判不等）；而应用权威口径 `CustomFieldValueCodec.canonical()` 规定 `1`/`1.0`/`1.00` **同串**。两者不同口径 → 可能造出伪差异。

本轮新增的 `cf_check.py` **按应用口径**比对，并同时输出另两种口径作对照（本轮"口径分歧"计数为 0，因为夹具已按 Dart 字面量对齐）。
