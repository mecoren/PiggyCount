## 6. 问题分析

### 6.1 【工具·已修】R1 比对报「契约漂移」（`exit=3`）——比对器与 SPEC 脱节，非产品缺陷

**现象**：`S3R1_CMP exit=3`，比对器判定「SPEC 与 Dart 实现脱节」。

**根因**：`scripts/sync_regression/compare_sync_final.py` 未同步 v11 契约新增的 `refundSyncId` / `reimburseStatus` 两字段 —— 其 `FK_MAP_TABLES` 缺 `transactions`、`COL_KEYS` 缺 `refund_of_id→refundSyncId` 与 `reimburse_status→reimburseStatus`。

**修复**（仅测试工具）：补齐上述三处映射与 SPEC 声明。修后 **R2–R5 全部 `exit=0`**，R1 复算亦 `exit=0`。

**结论**：对齐/防漂机制本身正常；本轮为**测试工具滞后**，不涉及生产代码。

### 6.2 【工具·已识别】`S3R4_00_mutate exit=1` —— 变更脚本自检时序误判

**现象**：`mut_r4.py` SUMMARY 报 `soft_delete=False`。

**取证**：DB 行数证据证明两行均已被软删 —— R3_A `tx=40011` → R4_A `tx=40010`（= 40011 + 1 新增 − 2 软删）；且 R4 比对 `exit=0`，B 端同步结果与 A 端一致。

**根因**：变更脚本对「软删是否生效」的自检在 UI 时序上取到了删除动作完成前的帧。

**结论**：工具自检误判，非产品缺陷；变更实际已落地并被正确同步。

### 6.3 【观察·未定位】分类 `测-转账`（`b20c86b1`）在 R3_A→R4_A 之间消失

**现象**：R3→R4 的 A 端变更集中出现 `categories 消失 1`（`b20c86b1`，旧值 `name='测-转账', kind='transfer'`），与 R4 变更脚本预期动作不完全对应。

**取证**：该变化**在两端同步后一致**（R4_CMP `exit=0`，B 端行为「缺失 0 / 取值不同 0」），即**不构成同步缺陷**。

**归因**：触发者未能从现有证据定位（可能是注入期 `测-*` 分类族的软删/清理被延迟落库，也可能与其他变更动作的批量清理耦合）。

**影响**：仅影响 A 端自身的数据口径，对两端一致性无影响。

### 6.4 【设计行为】回收站（`deleted_transactions`）两端不同

R1–R5 均为 `A=1~4 / B=0`。回收站是刻意的**设备本地态**：归档行进本地 `deleted_transactions` 表，不进快照 / 不进备份（`lib/cloud/` 零引用）。A 端软删的记录不会出现在 B 端回收站。

### 6.5 【设计行为】契约外字段差异 40151 行为何属预期

差异集中在 `created_at` / `updated_at` / `created_by_user_id` / `last_edited_by_user_id` / `is_shared` / `member_count` / `owner_user_id` / `cloud_file_id` / `cloud_sha256` / `tag_sync_ids_override` —— 均为设备本地写入时刻 / 本机身份 / 云端定位信息 / 覆盖语义索引列，**不进同步契约**，比对器已单列，不计入不一致。
