## 6. 问题分析

### 6.1 【缺陷】S3 增量上传（条件写 If-Match）在阿里云 OSS 上恒失败

| 项 | 内容 |
|---|---|
| 现象 | A 端「上传」（增量按钮）对 8 个账本**全部失败**，连续 **3 次尝试**（19:14:39–19:15:06、19:28:51–19:29:16、19:41:07–19:41:30）均 `上传失败: 1…8`；对照「全量上传」路径 8/8 全部成功 |
| 日志原文 | `PutObject(conditional) 网络错误，第 1/2 次安全重试: Write failed` / `第 2/2 次安全重试: Connection reset by peer` / `Broken pipe` / `Read failed` |
| 根因 | `packages/flutter_cloud_sync_s3/lib/src/s3_client.dart` 的条件写**降级判据只认「HTTP 400 + NotImplemented」**；阿里云 OSS 在写请求体阶段直接断连（`Write failed` / `Broken pipe`），不返回 400，**降级分支永不触发**。而 `s3_storage_service.dart` 硬编码 `supportsConditionalWrite => true`，导致每次写都带条件头并必然失败 |
| 影响 | S3 后端**增量上传不可用**；但快照同步的**全量上传 / 下载 / 合并链路完全正常**，功能可通过全量上传路径收敛（本轮即如此收敛） |
| 建议 | 将降级判据从「HTTP 400 + NotImplemented」扩展为「连接层失败（broken pipe / connection reset / write failed）亦可降级一次」，或对已知不支持条件写的 OSS 端点关闭 `supportsConditionalWrite` |

### 6.2 删除类变更的既定语义（SYNC-05，预期行为）

R2 中 16 条删除在合并方「一键应用全部」时**默认不勾选**（防误删设计），因此对端**故意保留**这 16 行，`StartupSyncChecker` 的**防删除复活守卫**亦跳过自动回传。收敛走「另一端全量上传 + 再合并」路径完成。**这不是数据不一致，而是用户未显式勾选删除时的设计结果**——若需真正删除对端数据，必须在变更预览中显式勾选删除项。

### 6.3 过程记录（非缺陷）

- 测试起点后端基线即为 `s3`（上一轮残留），本轮 S3 阶段**未做后端切换**，故 `cloud_active_type` 全程恒为 `s3`。
- 早期遗留的 17:15–17:37 服务端 / 应用日志属**上一轮会话残留**，不计入本轮窗口（本轮 S3 阶段窗口为 19:01–20:13）。
