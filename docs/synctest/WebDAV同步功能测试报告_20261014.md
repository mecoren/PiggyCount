### 6.1 定时备份「真实触发」实测（12/12 全绿）

## 7. 服务端审计：DELETE 与 .tmp（硬性约束 / 安全）

审计源：`scripts/webdav_test/wd_wdphase_20261014.err`（服务进程逐请求一行）。审计脚本：`wd_audit.py`（只读日志、不动数据），产物 `WD_audit_summary.txt`。

**审计窗口**：`20:47:02 ~ 21:43:36`（自服务启动后首条请求起；首条为**测试前 OPTIONS 探针**，如实披露）。**请求总数 1548**。

**方法分布**


| 审计项 | 值 | 判定 |
|---|---|---|
| DELETE 次数 | **1** | ⚠️ 见下方定性 |
| 临时对象 PUT/MOVE 次数 | 145（`.tmp.<ms>_<n>` 命名，MOVE 落正式名） | 正常原子发布流程 |

**唯一 DELETE 定性（`WD_delete_analysis.md`）**

```
[20:50:57] DELETE /piggycount/attachments/36b7793d3c602595490fc5dfe7298e19e45297ef690af19e461731e09febd036.bin.tmp.1791982255945_6
```

- **目标性质**：名称模式 `<sha>.bin.tmp.<毫秒>_<序号>`，为**客户端自身的上传临时对象**，与正式对象 `<sha>.bin` 严格区分；认证身份为客户端凭据 `pctest`。
- **根因**：`packages/flutter_cloud_sync_webdav/lib/src/webdav_storage_service.dart:505-512` `_atomicPublish` **外层 catch** 的临时自清理（源码注释原文「清理临时文件，避免远端残留半成品」）：`temp PUT → overwrite MOVE` 抛错时删除自己刚落下的临时对象。
- **触发原因**：同一 sha `36b7793d…` 被账本 1 / 4（去重行）/ 8 **并发上传**（3 个临时名 `…943_0 / …945_6 / …950_7`），两路 MOVE 成功、一路失败（并发覆盖同目标被服务端锁/竞态挡下；`_isOverwriteUnsupported` 有意不含 423 Locked，源码 :978 注释）→ 失败路自清理。
- **精确对齐证据**：App 日志 `附件: 1791982257445 [CloudSync] 附件对象上传失败 sha256=36b7793d…` + `附件对象上传完成(账本 8): 上传=0 跳过=0 失败=1`；`1791982257445 ms = 20:50:57.445`，与该 DELETE **同毫秒**，失败对象 sha 与 DELETE 目标 sha **完全相同**。
- **无损性**：正式对象 `attachments/36b7793d….bin = 24979B` 已由并发成功 MOVE 落位；7 个 sha 全部存在；磁盘 `.tmp`=0；**未删除任何云端数据 / 备份对象**。

**结论**：审计脚本因「存在 1 次 DELETE」判 `VERDICT FAIL`（其判定式为「DELETE==0 且 `.tmp`==0」）。报告如实披露**原始计数 = 1**：该次 DELETE 属客户端上传失败路径的**自身临时清理**，**不构成对云端数据或备份的删除**；硬性约束「测试过程中不删除任何云备份配置」**未被违反**（云配置三个 guard 文件与 E2EE 密钥逐字节未变，见 §2 / §8）。`piggycount-bak/` 3 个备份包完整保留为最直接的反证。
