## 5. 差异分析与原因说明

### 5.1 未发现产品缺陷

WDR1~WDR4 四轮（含 P0/P1 改名类变更在增量合并路径的落库）**未出现任何非预期差异**。
唯一非零差异出现在刻意构造的 WDDEL 删除边界轮，且**属设计内行为**，并具备明确替代路径（见 §5.2）。

### 5.2 差异项分析：远端删除不自动镜像到本地（**设计内行为 / 防误删**）

**现象**：A 端删除的 16 笔交易在 B 端仍存在；合并日志显示删除被跳过；B 端云同步页给出待处理提示。

**运行期证据链**：
```
[SyncDiff] 差异计算完成: 新增=3, 修改=6, 删除=2      ← 差异引擎正确识别出 2 条删除
[SyncDiff] 变更已应用:   新增=3, 修改=6, 删除=0      ← 删除默认未被勾选 → 未应用
[StartupSyncCheck] 账本 <名> 存在未应用的云端删除，本轮跳过回传以防删除复活（下次启动将再次提示）
同步页状态行：有 2 条云端删除待处理（默认不自动应用；以云端为准请用下方「全量下载」）
```

**代码根因（与实现一致）**：

| 证据 | 位置 | 说明 |
|---|---|---|
| `SyncChange(...) : selected = selected ?? (type != SyncChangeType.deleted)` | `lib/cloud/sync_diff_service.dart:50` | `deleted` 类变更默认未勾选 |
| 「一键应用全部」只应用**已勾选**差异 | `lib/cloud/startup_sync_checker.dart`（`_applyAll`） | 未勾选 → `删除=0` |
| 合并后若存在未应用删除则跳过回传（日志文案「存在未应用的云端删除，本轮跳过回传以防删除复活」） | `lib/cloud/startup_sync_checker.dart` | 防止「删除复活」 |
| 待处理删除计数（会话内 provider）+ 同步页逐账本状态行标记 | `lib/cloud/startup_sync_checker.dart:932/947/1130`（`recordPendingCloudDeletes`）、`lib/providers/sync_providers.dart:267`（`pendingCloudDeletedProvider`）、`lib/pages/cloud/cloud_sync_page.dart:821` | **P3 修复**：把「删除未生效」从一行汇总文案提升为逐账本持续可见标记（会话内有效，**不写 SharedPreferences**） |

**可替代路径（已实测收敛）**：云同步页「**全量下载**」→ `fullRestoreAllRemoteLedgers` → `downloadAndRestoreToCurrentLedger` → `restoreLedgerFromJson`（`clearLedgerTransactions` + `importTransactionsJson` + `_mirrorDeleteAbsentEntities`）。本轮 WDDELFD 走该路径后 **8/8 成功、双端 exit=0**。

**定性**：**设计内行为**（防误删保护 + 明确的替代路径 + 可见性提示），**不构成数据损坏**；「一键应用全部」的命名仍可能被理解为「完全对齐云端」，建议在 UI 措辞上进一步区分「合并」与「覆盖」。

### 5.3 已排查并确认「非问题」的现象

| # | 现象 | 排查结论 |
|---|---|---|

### 11.3 `created_by_user_id` / `last_edited_by_user_id` 定性

**结论：这不是「文件式后端下功能未跨设备传播」，而是「该功能在当前代码里根本没有启用」。**

代码级证据（全仓 grep，排除 `*.g.dart`）：

| 维度 | 证据 | 说明 |
|---|---|---|
| 写入方 | 仅 `local_transaction_repository.dart:693`（`markTxAuthor` 内部） | 而 `markTxAuthor` **全仓只有定义、无任何调用方**（`local_repository.dart:1349` 仅为转发；`.workbuddy/` 下是副本） |
| 读取方 | **零**（唯一命中是注释本身） | 没有任何 UI/统计/导出读取该列 |
| 云载荷 | `lib/cloud/**` 对该字段**零引用** | 快照（`transactions_json.dart`）不携带 → 导入端自然为 NULL |
| 字段来源 | `db.dart:134` 注释：`// v24: 共享账本"谁记的"显示` | 属共享账本场景的**预留字段** |
| 成员库 | `ledger_members`（`db.dart:515`：「server 端 `LedgerMember` 表的本地副本」）在 `lib/cloud/**` **零引用** | 文件式后端没有服务端成员库，也不存在"应传而未传" |

**因此：**

1. 本轮 A 端所有非空值 **100% 来自测试脚本**（`inject_16384_sync_test_v2.py:39 OWNER="dev-owner-16384"`；`modify_r2.py` 的新增/修改同样写 `OWNER`）——B 端在 WDUPD2 后也出现了 25 条自己脚本写的值，可反向印证；
2. B 端为 NULL **不构成缺陷**：两端都从未被应用写入过该字段；
3. 之前报告把它归为「云同步契约外字段」是**正确但不够准确**的表述，更准确的是「**未启用字段**」。

**建议**：若计划启用「谁记的」，需要同时补齐 (a) UI 层调用 `markTxAuthor`、(b) 云载荷字段 + 指纹白名单（参照 `originalAmount`/`customValues` 的**仅非空才写键**防漂移范式）、(c) 文件式后端下的成员身份解析方案；否则建议在 `db.dart:134` 处明确标注「预留，未启用」。

### 11.4 闭合验证：B 回传覆盖云端后，A 再合并会不会清空自己的值？——**不会**

**链路**：A 改+上传(21:16) → B 合并+**回传**(21:18) → B 改+B 上传(21:21) → A 落后被拦截(21:22) → **A 合并云端(21:24)**。

**A 端快照测量（合并前后）**

| 时点 | transactions | `created_by_user_id` 非空 | `last_edited_by_user_id` 非空 | `updated_at` 非空 |
|---|---|---|---|---|
| 合并前（`WDUPD4_premerge_A.sqlite`） | 40117 | **5109** | **5042** | 48 |
| 合并后（`WDUPD4_postmerge_A.sqlite`） | **40142** | **5109（零变化）** | **5042（零变化）** | **939** |

- 行数 **+25** 证明合并**确实生效**（拿到了 B 新增的 25 笔），不是"没合并所以没变"；
- 两个身份字段**逐值零变化** → **无数据丢失风险，闭合验证通过**。

**代码级原因**：合并路径 `sync_diff_service.dart:718-744` 构造 `TransactionUpdateBySyncIdData` 时**不包含** `createdByUserId` / `lastEditedByUserId`；落库走 `local_transaction_repository.dart:1874-1910` 的 `db.update(..., TransactionsCompanion(...))` —— **按字段部分 UPDATE**，未列出的列保持本地原值。

**同时暴露的机制（契约外，非缺陷）**：`updated_at` 由 48 → 939 行。原因是 v40 迁移建有 6 个 `trg_*_touch_updated_at` 触发器（实测确认存在于 `sqlite_master`），**任何 UPDATE 都会把 `updated_at` 刷成本机当前时刻** → 它是「本机写时钟」，必然跨端不同，且被 `transactions_sync_manager.dart` 一带用作方向/信任提示（P1-12 已引入 `localUpdatedAtTrusted` 缓解）。这解释了 §10.2 中 `updated_at` 的全部差异。
