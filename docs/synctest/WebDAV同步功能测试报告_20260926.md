| 项目 | 内容 |
|---|---|
| 测试产品 | PiggyCount（Flutter / Drift 本地库 + 云同步） |
| 测试模块 | 云同步 — **WebDAV 后端（自定义云服务）** |
| 测试日期 | 2026-09-26（独立执行，运行目录 `scripts/live_db/run_20260926/`；当日 S3 轮之后连续执行） |
| 测试方式 | 双 Android 模拟器端到端回归：**3 轮同步**（R1 空库全量 → R2 修改后增量 → R3 全量下载收敛），服务端**带 8 个既有槽位对象起步（零删除约束）** |

## 5. 一致性对比与差异分析

### 5.1 差异项 1/2 — 远端删除不镜像到本地（**设计内行为**）

**现象**：A 端删除的 16 笔交易在 B 端仍存在；B 端合并日志明确显示删除被跳过。

**代码根因**：

| 证据 | 位置 | 说明 |
|---|---|---|
| `SyncChange.selected = selected ?? (type != SyncChangeType.deleted)` | `lib/cloud/sync_diff_service.dart:39` | **`deleted` 类变更默认未勾选** |
| `preview.changes.where((ch) => ch.selected)` | `lib/cloud/startup_sync_checker.dart:917` | 「一键应用全部」只应用**已勾选**差异 |
| `SyncApplyResult.deletedCount` 仅统计已选删除项 | `lib/cloud/sync_diff_service.dart:728-761` | 未勾选 → `删除=0` |
| UI 提示「这些删除本轮不会生效，如需删除请到云同步页手动处理」 | `lib/cloud/startup_sync_checker.dart:1009-1011` | 设计上引导用户改用云同步页 |

**运行期证据**：`[SyncDiff] 差异计算完成: 新增=3, 修改=6, 删除=2` → `[SyncDiff] 变更已应用: 新增=3, 修改=6, 删除=0`。

**可替代路径**：云同步页「**全量下载**」→ `fullRestoreAllRemoteLedgers` → `downloadAndRestoreToCurrentLedger` → `restoreLedgerFromJson`（`clearLedgerTransactions` + `importTransactionsJson` + `_mirrorDeleteAbsentEntities`，`lib/services/data_import_service.dart:1788-1814`）。实测 R3 走此路径后删除**完全生效**（双端 40017 一致）。镜像删除仅在 `remoteImport.version >= 8` 时生效（`data_import_service.dart:1802`），本轮快照为 v8+。

**定性**：设计内行为（防误删保护 + 明确替代路径），**不构成数据损坏**。

### 5.2 差异项 3 — 账本 `name` 不参与增量合并（**实现边界**）

**现象**：R2 后 B 端账本名仍为「投资理财账本」，A 端已是「投资理财账本·W2」。

**代码根因**：
- 增量合并路径 `_applySyncChangesInternal`（`lib/cloud/sync_diff_service.dart:446-771`）**从不调用 `updateLedger(name:)`**；该路径只覆盖账户/分类/标签/自定义字段/周期/预算/汇率与 `month_start_day`（`sync_diff_service.dart:497-508` 是唯一写账本处）。
- 账本 `name` 只在**全量恢复路径**写入（`lib/services/data_import_service.dart:408-418`）。

**实测佐证**：R3 走「全量下载」后账本名双端一致 ✅；`month_start_day` 在增量合并路径即已同步 ✅。

### 5.3 差异项 4/5 — 账户 / 分类改名不生效（**导入器实现缺口，建议修复**）

**现象**：账户改名、分类改名在**增量合并与全量下载两条路径上均不生效**；而同为 user-global 的**标签改名却正常同步**。该现象在 S3 与 WebDAV 两个后端上**表现完全一致**，可判定为**与后端无关的本地导入实现问题**。

**代码根因（三类实体导入实现不一致）**：

| 实体 | 命中已存在实体时的更新字段 | 位置 | 是否含 `name` |
|---|---|---|---|
| `account` | `type / currency / initialBalance / creditLimit / billingDay / paymentDueDay / bankName / cardLastFour / note / hidden / syncId` | `lib/services/data_import_service.dart:574-587` | ❌ **无 `name`** |
| `category` | 仅在 `syncId` 不匹配时 `updateCategory(id, syncId:)` | `lib/services/data_import_service.dart:660-674` | ❌ 完全不参与 |
| `tag` | 显式 `if (tag.name != existingTag.name) → updateTag(id, name:, color:, sortOrder:)` | `lib/services/data_import_service.dart:909-918` | ✅ 有 |

**实测佐证**：三轮中 `tags` 始终 `[OK]`；`accounts` / `categories` 的 name 在增量合并与全量下载后**均保持 B 端旧值**。

**定性**：**实现缺口**，影响「在 A 端重命名账户/分类后同步到 B 端」这一常见场景。建议：
1. `importAccounts` 的 `updateAccount(...)` 补上 `name: acc.name`；
2. `importCategories` 命中分支按 `name` 差异执行 `updateCategory(id, name: ...)`；
3. 为三类 user-global 实体统一「可更新字段清单」，避免策略再次分叉。
