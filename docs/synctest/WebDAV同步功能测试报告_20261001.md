## 7. 差异分析与原因说明

本轮**未发现数据不一致**。以下为需要说明的行为/原因：

1. **删除类变更默认不应用（SYNC-05，既定设计）**：合并方「一键应用全部」只应用默认勾选的 `added/modified`，`deleted` **默认不勾选**（防误删）；因此 R2 的 16 条删除在合并方**故意保留**，且 `StartupSyncChecker` 的**防删除复活守卫**跳过自动回传（日志：`存在未应用的云端删除，本轮跳过回传以防删除复活`）。收敛由「另一端全量上传 + 再合并」完成，两轮均正常收敛、终态完全一致。**若需真正删除对端数据，必须在变更预览中显式勾选删除项**——这是设计取舍，不是同步失败。
2. **本轮删除数较 S3 阶段少一次**：R3 采用 `NO_DELETE=1` 造数（删 0 / 增 25），用于验证「纯新增 + 修改」路径的传播与不重复，故 R3 未触发删除守卫。
3. **WebDAV 条件写（方案 C）在客户端实现且工作正常**：见 `packages/flutter_cloud_sync_webdav/lib/src/webdav_storage_service.dart` —— `supportsConditionalWrite => true`，条件写**在客户端完成**（PROPFIND 读 ETag → PUT 到 `.tmp` → MOVE with Overwrite 头，412 时拒绝），不依赖服务端 If-Match。因此增量上传 8/8 成功。
4. **与 S3 的根因对照**：S3 阶段增量上传恒失败，根因是其条件写**降级判据只认「HTTP 400 + NotImplemented」**，而阿里云 OSS 在写请求体阶段直接断连（`Write failed` / `Broken pipe`）**不返回 400**，降级分支永不触发；`s3_storage_service.dart` 又硬编码 `supportsConditionalWrite => true`。**同一套上层逻辑在两个后端表现相反，定位在 S3 客户端条件写实现**，非同步框架缺陷。
