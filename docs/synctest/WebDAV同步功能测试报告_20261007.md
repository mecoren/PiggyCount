## 6. 问题分析

### 6.1 【环境】WebDAV 端点误指真实坚果云，造成「假性落盘缺失」

见 §1。**测试环境问题，非应用缺陷**；上传链路与 503 幂等重试行为均符合预期（对限流做了重试，未丢数据）。

> ⚠️ **数据影响提示**：`WDR1` 首跑（08:54，端点为坚果云）确实把本轮的 8 个账本快照写入了坚果云 `/piggycounttest`。该路径下同名槽位已被本次测试数据覆盖，请使用者自行确认该目录是否为专用测试路径。

### 6.2 【显示·轻】「测试连接」对自签证书恒失败，但不影响同步

| 项 | 内容 |
|---|---|
| 现象 | 云服务页点「测试连接」→ 弹「测试失败」，详情：`Handshake error in client (OS Error: CERTIFICATE_VERIFY_FAILED: unable to get local issuer certificate (handshake.cc:320))` |
| 根因 | `lib/cloud/` 的 WebDAV provider 对 dev 测试服务器有证书放宽（`_isDevTestServer(uri)`：`kDebugMode && (host=='10.0.2.2'\|\|host=='127.0.0.1') && port==8443`，走 dio 链路）；而 `cloud_service_page.dart` 的 `_testConnection` WebDAV 分支用**裸 `http.Client()`**，**不经过该放宽** → 对自签服务器必然握手失败，服务端**根本没收到 OPTIONS** |
| 影响 | `_connectionTestResults` 仅驱动状态徽章，**不 gate 任何同步动作**；本轮 6 次上传/下载全部成功即证 |
| 建议 | 让 `_testConnection` 复用 provider 的同一客户端（或同一 `_isDevTestServer` 判定），避免「明明能同步却提示连接失败」的误导 |

### 6.3 【工具·中】`boot()/dismiss_blockers` 竞态导致首次同步空等 12.9 分钟

| 项 | 内容 |
|---|---|
| 现象 | B 端 R1 首次同步卡死 **12.9 分钟**，RSS 从 548MB 涨到 604MB，除 `[mem]` / `[Backup] 恢复进行中` 外**零日志**；8 个账本 JSON 早在 **09:55:43** 就下载完毕，之后再无请求 |
| 排查 | B 端 UI dump 停在「发现云端账本」弹窗（跳过 / 下载 / 关闭）；`[TxImport]` 最后一条属 S3 阶段 |
| 根因 | `scripts/sync_regression/flows.py` 的 `dismiss_blockers()` 返回 True 的条件是「无 MODAL_MARKERS 残留 **且** 有『我的』」。**冷启动时弹窗尚未渲染**，条件即刻成立 → 函数在弹窗出现前就返回，`b_first_sync.py` 于是打印「已点『下载』」但实际没点 |
| 处置（跑动中救场） | 手工 `input tap 787 1594` 点「下载」→ **10:08:30** 导入真正开始（`[AccountImport] 开始导入账户: 61 个`），**10:08:37** 落库完成 → `WDR1_CMP exit=0` |
| 影响 | 仅影响 harness 的自动化可靠性；**未在运行中改动共享脚本**，缺陷留档 |
| 建议 | 判据改为「**等待弹窗出现**（有界超时）→ 无模态残留 **且** 目标元素可见」；`boot()` 之后应显式等待首个确定性元素，而不是靠「无残留」反推就绪 |

### 6.4 【工具·轻】「立即备份」的完成判据是假阳性

| 项 | 内容 |
|---|---|
| 现象 | 判据 `if "最近备份" in xml and "尚无记录" not in xml` 因 S3 阶段留下的同日记录**恒真** → 会在备份尚未落盘时即报成功 |
| 处置 | 改用**服务端落盘**作为真证据：`PROPFIND piggycount-bak/ → MKCOL → PUT ...zip.tmp → MOVE`，文件 `PiggyCount-2026-10-07.zip` **3,891,707B** 存在 |
| 建议 | 判据不要依赖「同日历史记录」这类可被前序用例污染的 UI 文本，改为观察「本次操作的进行中态 → 消失」或直接以云端对象为证据 |

### 6.5 【文案歧义·轻】备份完成日志的字节数未标注归属（与 S3 轮同源）

`[Backup] 备份完成: PiggyCount-2026-10-07.zip 账本=8 附件=7 (跳过=0, **128KB**)`，
而「从备份恢复」列表里同一对象显示 **3.7 MB**、云端实测 **3,891,707 B**。

定位见 S3 报告 §6.1：该数字是 `attTotalBytes`（**仅去重附件的原始字节和**，`cloud_backup_service.dart:273/355`），
7 个附件 = `131212 B = 128.1 KB`，**数值正确、文案缺主语**（同文件 `:341` 写的是「附件总量」）。

### 6.6 【风险·中】从备份恢复后方向断言与内容事实相反（`localNewer`）

| 项 | 内容 |
|---|---|
| 场景 | ④ 自动同步把 `88.88` 推上云端（云端账本 1 = 5003 条）；⑤ 从备份恢复把本地回滚到备份时点（本地 = 5002 条）。**本地内容少 1 笔，但日志报 `SyncDiff.localNewer`** |
| 证据 | `[CloudSync] 指纹不一致 本地: 5b34b832 云端: a1187c72 数量 本地5002/云端5003` → `Sync status: SyncState.outOfSync` → `同步状态: 1 -> SyncDiff.localNewer` |
| 机理 | `packages/flutter_cloud_sync/lib/src/manager/cloud_sync_manager.dart:629-642`：**可信墙钟分支优先于 count 分支**。恢复把本地账本 `updatedAt` 写成**恢复时刻**（10:34），晚于云端 metadata 的 `updatedAt`（10:31:34）→ `localUpdatedAt.isAfter(cloudUpdatedAt)` 成立 → `localNewer`（`message='Local data is newer (timestamp)'`）。按 count 兜底的分支（`:667-678`，会正确判 `cloudNewer`）**根本没走到**；只有墙钟被调用方声明不可信（`:643-666`）才会退回 count |
| 实测后果 | UI 据此给出「本地较新」的上传指引。**本报告 §4 的收敛轮即照此执行**：全量上传后云端 40012 被回退到 40011，**④ 那笔 88.88 在云端消失**。由于该笔在本地已被恢复回滚、云端是**唯一副本**，此路径构成**静默数据丢失**（无任何告警） |
| 静默性 | `lib/cloud/startup_sync_checker.dart:501-512` 只把 `cloudNewer` 列入「云端有更新」候选 → `localNewer` **不弹窗**，用户不会被提示 |
| 判定 | 「从备份恢复 → 以本地为准 → 回退云端」在语义上自洽，**不判定为同步功能缺陷**；但「内容倒退 + 时间戳前移」这类操作会产出**与事实相反的方向断言**，且失败模式静默 |
| 建议 | 二选一：① 恢复路径把本地账本 `updatedAt` 保持为**备份内的时间**（而非恢复时刻），让方向断言与内容一致；② 或为恢复路径显式打「本地为权威」标记，并在 UI 明确告知「继续上传将把云端回退到备份时点」。**本次未改任何生产代码**，仅登记 |
