## 6. 问题分析

### 6.1 【文案歧义·轻】备份完成日志的字节数未标注归属，易被读成整包体积

| 项 | 内容 |
|---|---|
| 现象 | 日志 `[Backup] 备份完成: PiggyCount-2026-10-07.zip 账本=8 附件=7 (跳过=0, **128KB**)`；而「从备份恢复」列表里同一个对象显示 **3.7 MB**，云端实测 **3,891,707 B** —— 相差约 30 倍 |
| 根因（已定位） | `lib/cloud/backup/cloud_backup_service.dart:273` 在附件循环里累加 `attTotalBytes += len`（**仅附件**、按去重对象计）；`:353-355` 输出时只写 `_fmtBytes(attTotalBytes)`，**省略了「附件总量」主语**。<br>验证：7 个去重附件原始字节和 = `14009+16197+17184+18485+20427+21573+23337 = 131212 B = 128.1 KB` —— 与日志完全吻合 |
| 判定 | **数值正确、文案有歧义**，非数值缺陷。同文件 `:341` 的同类告警写的是「附件总量 …」，说明作者本有明确表达，此处属疏漏 |
| 影响 | 仅影响排障可读性；不影响备份内容与恢复正确性（恢复 8/8 成功，且恢复后数据与备份时点逐字段一致，见 §6.5） |
| 建议 | 把该字段补成 `附件总量 ${_fmtBytes(attTotalBytes)}`，并另打一条 `整包大小 ${_fmtBytes(zipData.length)}`，两者分开 |

### 6.2 契约外字段差异 5150+ 行为何属预期

差异**只**落在 8 张表的**契约外字段**上（`created_at` / `updated_at` / `created_by_user_id` / `last_edited_by_user_id` / `is_shared` / `member_count` / `owner_user_id` / `cloud_file_id` / `cloud_sha256` / `tag_sync_ids_override`）：

| 字段族 | 为何不同 |
|---|---|
| `created_at` / `updated_at` | 设备本地写入时刻，**不进同步契约**（快照不搬运），恢复端按本地时间重新生成 |
| `created_by_user_id` / `last_edited_by_user_id` | 本机用户身份，单机场景恒为本机；不参与跨端语义 |
| `is_shared` / `member_count` / `owner_user_id` | 共享账本元数据，由共享协议单独承载，不在快照契约内 |
| `cloud_file_id` / `cloud_sha256` | 云端对象定位信息，由上传方生成 |
| `tag_sync_ids_override` | 覆盖语义的本地索引列，由 `transaction_tags` 关系表承载 |

→ 逐字段比对器**按契约口径**判定，这些字段被显式列为「契约外，预期差异，不计入不一致」。四轮结论均为「**无非预期差异**」。

### 6.3 回收站（`deleted_transactions`）两端不同，属设计行为

R2/R3/R4 中 A 端回收站有 1–2 行、B 端恒为 0。

回收站是**刻意的设备本地态**：归档行进本地 `deleted_transactions` 表，**不进快照**（`lib/cloud/` 零引用），因此既不上云也不进备份。A 端删除的记录不会出现在 B 端回收站，属设计行为（UI 侧已有 `recycleBinLocalOnlyNote` 说明条）。

### 6.4 每账本交易数比注入值多 1

`5000 → 5001`：周期规则在「当期」被物化出一笔实例，属造数夹具与业务规则共同作用的结果，两端一致，非缺陷。
