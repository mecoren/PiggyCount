## 2. 测试步骤

### 2.1 数据清理阶段
1. 两端卸载重装含新代码的 dev 包(`adb install -r app-dev-debug.apk`)。
2. 仅删除本地数据库与附件目录(`app_flutter/piggycount.sqlite*`、`app_flutter/attachments/*`),**不触碰 `shared_prefs/`(云配置所在)**;重装/清库前后各备份一次 `FlutterSecureStorage.xml` + `FlutterSharedPreferences.xml` 至 `scripts/live_db/pretest_backup/`。
3. 验证:清库后两端 `cloud_active_type` 均为 `s3`,凭据完好。

### 2.2 测试数据准备(仅 A 端 16384)
1. A 端启动生成全新空库(验证 `PRAGMA user_version = 42`,含本次 v42 周期账单币种列)。
2. 拉取空库 → `inject_16384_sync_test.py` 注入:
   - 6 账本:默认账本、**历史回忆账本(2013-2015 历史数据)**、日常消费账本、海外旅行账本、创业公司账本、家庭共用账本(各 1000 笔)
   - 48 账户(每账本含**微信零钱/支付宝**账户;海外账本含 USD/JPY/EUR/HKD 多币种账户)
   - 29 一级分类 + 19 二级分类、15 标签、1748 条标签链接、18 预算、18 周期交易、9 条汇率覆盖、7 个真实 JPEG 附件(内容寻址)
   - 全部实体写入 `local_changes`(6143 条),覆盖微信/支付宝真实商户备注(扫码/外卖/打车/红包等)
3. 注入库与附件经 base64 流式推送回设备(adb push 在本环境大文件静默失败,已绕过)。

### 2.3 同步操作
1. **A 端(同步到云端)**:我的 → 同步 → 「全量上传」→ 双重危险确认(3 秒倒计时)。
   日志证据(节选):6 账本串行 `Starting upload → Post-upload verify passed → Upload completed`,附件对象上传 2+1+1,最终 `上传完成: 6`。
2. **B 端(同步云端)**:启动后 StartupSyncChecker 弹「云端发现账本」,点「下载」恢复全部云端账本;日志 `云端账本导入完成 ... inserted=1001 ×n`,`StartupSyncChecker: 云端新账本导入完成 17/17 个`。
   (B 端首次下载得到 17 个云端槽位 —— 含本次 6 个 + S3 桶内上次测试遗留的 11 个旧槽位。)

### 2.4 数据验证
- 对比工具:`scripts/compare_sync_final.py`(按 syncId 对齐身份,不依赖本地自增 id)。
- 首轮比对发现:云端遗留旧槽位与本次新槽位**同名并存**,B 端「历史回忆/日常消费」两个名字从旧槽位恢复导致 syncId 不一致 —— 属测试环境遗留干扰(真实用户账本 syncId 稳定不会出现)。

## 3. 测试结果

**通过。** S3 快照同步在 6006 笔交易、6 账本、48 账户、29+19 分类、15 标签、1748 标签链接、18 预算、18 周期、9 汇率覆盖的规模下,两端数据完全一致。附件对象(4 个)上传成功(注:快照同步范围按设计不含附件下载恢复,附件在备份包路径覆盖)。

## 4. 问题分析

### 4.1 已知边界(非缺陷):ledgers.is_shared / member_count 不随快照同步
- 现象:「家庭共用账本」在 A 端 `is_shared=1, member_count=2`,恢复到 B 端为 `0/1`。
- 根因:快照 JSON 的账本字段仅含 `name/currency/monthStartDay`(`lib/cloud/transactions_json.dart:445`),`is_shared/member_count` 属于已下线的 PiggyCountCloud 实时协同协议的共享元数据,快照同步(路径 A)设计上就不携带。
- 影响:纯快照用户不会构造出共享属性(注入脚本为测试造的),真实场景无影响。建议:若未来共享账本概念回归,需把这两个字段纳入快照 schema;当前保持现状即可。

### 4.2 测试环境干扰:云端同名旧槽位
- S3 桶内存在上次测试遗留的 11 个旧账本槽位,与新上传的 6 个同名并存;启动发现对话框把 17 个全部列出,B 端一键下载后与 A 端 syncId 集合不一致。
- 处置:通过账本管理页云端卡片按 slotKey 精选下载;比对时按 syncId 对齐自动排除。
- 建议(用户可见的改进点):「云端发现」/「全部恢复」对**同名账本**应提示存在多槽位(或展示 ID/更新时间供用户甄别),避免一键下载引入陈旧副本。本次实测云端卡片有 ID 与余额元数据,具备甄别信息。

### 4.3 环境问题(与被测功能无关)
- 本机 `adb push` 推送文件 > 数百 KB 时静默失败(报成功但文件不存在),改用 base64 流式传输绕过;模拟器 shell `cat` 二进制流会截断,同样需 base64。
- 运行中拉取 sqlite 文件会得到损坏副本(WAL 活跃),需 force-stop 后 `VACUUM INTO` 快照再取。

## 5. 复现路径(关键节点)

1. 清库:仅删 `piggycount.sqlite*` 与 attachments,保留 shared_prefs。
2. 注入:`python scripts/inject_16384_sync_test.py`(前置:从设备拉空库)。
3. A 端全量上传:我的 → 同步 → 全量上传(两次确认)。
4. B 端下载:启动弹窗「下载」或账本管理页云端卡片逐个下载。
5. 比对:`python scripts/live_db/compare_sync_final.py <A快照> <B快照> --label S3`。
