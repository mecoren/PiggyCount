## 6. 问题分析

### 6.1 【缺陷·轻】导出侧「转账归空」口径缺失，导致快照字节级永久不对称

| 项 | 内容 |
|---|---|
| 现象 | 8/8 账本的快照 payload 两端字节不同；逐字段定位：**唯一差异字段**为转账行的 `categoryName` / `categoryKind` —— 源端为 `"Transfer"` / `"transfer"`，恢复端为 `null` / `null`。`contentFingerprint` 两端**相同**，`diff` 也判**无变化** → 不告警、不收敛、无声。 |
| 复现 | S3 与 WebDAV 两后端**完全一致复现**（WebDAV 见另一份报告），故缺陷位于**共享的恢复/序列化代码路径**，与后端无关。 |
| 链路（证据，已逐行核实） | ① **导出侧** `lib/cloud/transactions_json.dart:160,177-178`：`catInfo = t.categoryId != null ? cats[t.categoryId] : null` 后直接输出 `categoryName/categoryKind`，**未按 `isTransfer ? '' : …` 归空**；转账虚拟分类出现在快照 `categories` 全量数组（`transactions_json.dart:300-353` 无 transfer 过滤），故源端转账行携带 `"Transfer"/"transfer"`；<br>② **分类解析本身是对的**：全量恢复路径 `lib/services/data_import_service.dart:1592-1612` 用 `'${tx.categoryKind}|${tx.categoryName}'` 查 `categoryCache`，diff 合并路径 `lib/cloud/sync_diff_service.dart:828-829` 经 `_resolveCategoryId`（同文件 1019-1026，同款 `kind|name` 查表）——**两条路径都能命中虚拟转账分类**；<br>③ **写库时被显式丢弃（两处对称写死，覆盖两条恢复路径）**：<br>　• **全量恢复（added）** `lib/services/data_import_service.dart:1757` `categoryId: d.Value(tx.type == 'transfer' ? null : categoryId)` ← **本轮 R1「下载」与 R2「全量下载」实际走的就是这条**（`sync_diff_service.dart:746-757` 的合并新增分支同样汇入 `importTransactions`，故也经此处）<br>　• **增量合并（modified）** `lib/cloud/sync_diff_service.dart:860` `categoryId: cloud.type == 'transfer' ? null : categoryId`<br>④ **指纹侧** `lib/cloud/sync_fingerprint.dart:16-17, 86-88, 134-137` 对转账**刻意忽略**该两项（"避免跨设备分类缺失导致指纹漂移"）；<br>⑤ **diff 侧** `lib/cloud/sync_diff_service.dart:166-171, 418-427` 两侧归空比较 → 合并路径也判「无变化」；<br>⑥ **次要放大点** `lib/services/data_import_service.dart:1601` `if (categoryId == null && tx.type != 'transfer')` —— transfer 即使 cache miss 也**绝不**补建分类；<br>⑦ **不会自愈**：`lib/services/data/seed_service.dart:841-861 migrateTransferTransactions()`（由 `lib/data/db.dart:984-988` v14 迁移与 `seed_service.dart:796-802` 调用）只在老库升级 / 首次 `ensureSeed` 触发，**恢复端两条路径都不经过**，NULL 永久留存；<br>⑧ `lib/cloud/sync_diff_service.dart:164-165` 注释断言「**导出侧**与指纹侧都按 `isTransfer ? '' : …` 归空」——与 ① 的实际实现**不符**（注释描述的是应有行为）。 |
| 影响 | 业务数据无损（转账本就无分类语义，UI 显示正常）；但：<br>1) 快照**字节级不可比**，差分/取证工具会把 8/8 账本判为「有差异」，掩盖真实差异；<br>2) 契约存在**静默不对称**：一旦未来把转账分类纳入指纹白名单（或给转账加分类级语义），立刻升级为「指纹永久 different / 用户点下载却无变更可点」的 S11 同构故障；<br>3) 恢复端的转账行 `category_id` 恒为 NULL，只能靠 `SeedService.migrateTransferTransactions()`（仅欢迎页 seed 流程触发）回填，跨端语义不自洽。 |
| 已有测试覆盖现状 | • `test/cloud/sync_diff_category_and_zero_amount_test.dart:169-188` 只锁定 **diff 侧**归空；其第 **180 行注释**「导出侧对 transfer 归空：categoryName/Kind 都是 null」是**与实现不符的假设**（该测试用 `cloudTx(type: 'transfer')` 构造，本就传 null，从未校验真实导出）；<br>• `test/cloud/sync_contract_coverage_test.dart:263-300` 的契约 fixture 把转账行期望写成 `category_id=NULL` + `categoryName/categoryKind=null`；<br>• **没有任何测试**锁定「导出侧对转账归空」或「导入/恢复会把 transfer 的 `category_id` 清成 NULL」——这正是本缺陷能长期存活的原因。 |
| 建议 | 优先 (a)，并补上缺失门禁（**不得改测试来通过**）：<br>**(a) 导出侧与指纹/diff/恢复三侧对齐（推荐）** —— `transactions_json.dart:177-178` 转账行输出空（等价于对该两行加 `t.type == 'transfer' ? null : …`）。与既有断言不冲突：契约 fixture 本就把转账行期望写成 NULL/null；<br>**(b) 恢复侧与导出对齐** —— 去掉 `data_import_service.dart:1757` 与 `sync_diff_service.dart:860` 的 transfer 强制 null，改为回填虚拟转账分类 id。代价：需同步改 `sync_contract_coverage_test.dart:263-300` 那批 fixture 期望（`category_id=NULL` → 非空），影响面更大；<br>**(c) 显式豁免** —— 在契约文档与契约覆盖测试中声明「转账分类字段不参与快照对称性」。<br>补门禁：① 新增「导出侧转账行 `categoryName/categoryKind` 与恢复侧口径一致」断言；② 新增「恢复后 transfer 行 `category_id` 与导出语义一致」断言；③ 修正 `sync_diff_category_and_zero_amount_test.dart:180` 的不实注释。 |

### 6.2 观察项（非缺陷，建议登记）

| 项 | 现象 | 判定 |
|---|---|---|
| **纯元信息变更的账本不进启动候选** | R2 中「改名 + `monthStartDay=15`」的账本（第3册）**未**出现在「云端有更新」弹窗里（只列了净新增的第1册），因此改名/月起始日**不会自动跨端**；手动「全量下载」后才收敛 | **设计边界**（非缺陷，但影响可用性）：`lib/cloud/startup_sync_checker.dart:501-512` 只把 `SyncDiff.cloudNewer` 的账本计入候选，`SyncDiff.different`（direction=unknown）**仅记日志不弹窗**（避免脏数据误弹）。而 `ledgerName` 虽进指纹（`sync_fingerprint` M2），方向仲裁仍可能判 unknown → **纯改名 / 纯月起始日的单向变更无法自动传播**。建议：把「本地无独有交易改动 + 云端账本名/月起始日不同」这类确定性单向差异纳入候选（或在云同步页/`我的`页显著标注待处理），否则用户无从知晓需手动下载。另注：`sync_diff_service.dart:674-676` 注释所述「改名回写」修复只在账本**已被选中合并**时生效 |
| 启动检查只提示「云端更新」的账本 | R2 中仅「第1册（净新增）」被列入合并弹窗；纯删除账本、纯改名账本未被提示 | 与 SYNC-05 / 方向仲裁（本地有独有改动 → 方向 unknown）设计一致，属预期 |
| `current_ledger_id` 指向不存在账本 | 造数用 `wipe` 清表后自增 id 继续增长，`current_ledger_id` 陈旧 → 首页显示「新建账本」、`我的`页同步状态行显示「状态获取失败」、同步页在状态查询中处于忙碌态（`全量上传/下载` 行不可点） | **测试夹具副作用**（真实用户清库走欢迎页重建，不会产生 id 空洞）；仅提示健壮性可优化：`currentLedgerIdProvider` 恢复时应回落到实际存在的账本 |

### 9.6 残留风险（同批已一并修复）

导出侧 `items` 的稳定排序原为 `happenedAt` → **本地自增 `id`**（`transactions_json.dart:63-67`）。两端 `id` 序列独立，因此**同一账本内两笔 `happenedAt` 完全相同的交易，在两端可能导出为不同顺序** → payload 字节不同；而指纹的排序键是 `happenedAt→type→amount→categoryName→categoryKind→note`（内容全序化），故**指纹相同** —— 与 §6.1 完全同构的「静默字节不对称」。

**已修**：兜底键改为内容派生链 `syncId → type → amount → note → id(仅本机内兜底)`。新增 **Tier 4 门禁**（同 `happenedAt` 两笔在两端以相反顺序插入 → 导出必须逐字节一致）—— 修复前该用例失败，修复后通过。指纹口径不受影响（指纹的 items 排序本就与载荷顺序无关）。

### 9.7 第二批门禁暴露的**第二处缺陷**：停用预算在恢复端被启用（已修）

新增 **Tier 5 富字段闭环**门禁（账本元信息 / 多币种 / 原始金额 / 自定义字段值与定义 / 标签关联 / 预算 / 周期规则 / 汇率覆盖 / 四种交易类型 / 账单标记，`export → restore → export` 逐字节一致）后，立刻暴露第二处导出↔恢复不闭合：

| 项 | 内容 |
