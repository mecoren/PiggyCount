## 5. 问题分析

### 5.1 已知设计边界（非缺陷）：`ledgers.is_shared / member_count` 不随快照同步

- **现象**：「家庭共用账本」在 A 端 `is_shared=1, member_count=2, my_role=owner`，恢复到 B 端为 `is_shared=0, member_count=1`。
- **根因（代码级证据）**：快照 JSON 的账本元数据块仅含
  `version / exportedAt / ledgerId / ledgerName / currency / ledgerSyncId / monthStartDay / count`
  —— 见 `lib/cloud/transactions_json.dart:437-458`（`version: 9`）。
  `is_shared / member_count / my_role` 属已下线的 PiggyCountCloud 实时协同协议的共享元数据，
  路径 A（快照同步）设计上不携带。
- **影响**：真实用户若从不使用协同协议，不会构造出共享属性；本轮该字段由测试注入脚本人为设置。
  纯快照用户无实际影响。
- **建议**：若未来共享账本概念回归，需将这两个字段纳入快照 schema 并提升 `version`；当前保持现状即可。
- **历史印证**：2026-09-08 的两轮测试（S3 / WebDAV）在同一字段上呈现完全相同的表现，进一步确认是设计边界而非实现缺陷。

### 5.2 测试环境治理：云端残留同名旧槽位（本轮已消除）

- 清理前 S3 远端存在上一轮测试的 5 个同名账本槽位。由于"全量上传"不清理云端独有账本，直接上传会产生
  同名双槽位，B 端"一键全部下载"后与 A 端 syncId 集合不一致（2026-09-08 轮曾出现 17 槽位干扰）。
- 本轮通过 §2.3 的 syncId 对齐使上传**就地覆盖**旧槽位，B 端发现的云端账本数**恰好为 6**，环境干净、
  比对结果无干扰。
- **产品侧改进建议（用户可见）**：「云端发现」/「全部恢复」对**同名不同源账本**应提示存在多槽位，
  或直接展示槽位 ID / 更新时间供用户甄别，避免一键下载引入陈旧副本。

### 5.3 环境/工具问题（与被测功能无关，本轮已绕过）

| 问题 | 现象 | 处置 |
|---|---|---|
| `adb shell cat` 读取二进制 | 输出被做 `\n → \r\n` 转换，拉取的 sqlite 报 `database disk image is malformed` | 改用 **`adb exec-out`**（二进制安全），字节数与设备端完全一致 |
| `adb push` 大文件 | 既有报告记录"静默失败"；实测根因是传入了 MSYS 风格路径 `/d/...`，adb 无法 stat | 改用 **Windows 原生路径** `D:/...`，2.6MB 文件稳定推送成功 |
| `adb shell` 输出行尾 `\r` | 循环中用 `ls` 输出拼路径导致 `cp: bad 'xxx.jpg\r'` | 管道加 `tr -d '\r'` |
| `run-as ... sh -c "rm -rf path/*"` | glob 未展开，报 `Needs 1 argument` | 改为对目录本身 `rm -rf`（应用会自动重建） |
| 运行中拉取 sqlite | WAL 活跃，副本损坏 | `force-stop` → 设备端 `sqlite3 "... VACUUM INTO '...'"` → `exec-out` 拉取 |
| `inject_16384_sync_test.py` 缺依赖 | `ModuleNotFoundError: No module named 'PIL'`（附件生成段，前序数据已回滚，库保持干净） | 在隔离 venv 安装 Pillow 12.3.0 后重跑 |
