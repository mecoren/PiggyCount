## 2. V2：探针实测（结果：发现 2 处真实缺陷）

### 2.1 探针设计（`modify_v2probe.py`，与 V1 行集互斥）

| 组 | 构造 | 行数 | 事前预期（由代码读出的假设） |
|---|---|---|---|
| **E** | **只改** `category_id`，不动任何其它可比字段 | 32 | **不传播** |
| **G** | 改 `category_id` **+** `amount`（对照组） | 32 | 传播（金额触发 modified，分类被一并带上） |
| **F** | `original_amount = 0`（挑当前为 NULL 的行） | 24 | **不传播** |

E 的事前依据：`sync_diff_service.dart:280-400 _compareTx` 比较了 type/amount/happenedAt/note/account/tags/exclude 标记/currencyCode/nativeAmount/originalAmount/customValues/3×override/attachment，**唯独没有比较 category**。
（同文件 349-350 对 `excludeFromStats` 明确写过「不比较则 B 端 diff 识别不出 modified，标记永不跨设备同步」——同款论证，说明分类更像漏项而非有意取舍。）

F 的事前依据：`sync_diff_service.dart:370-372`
```dart
if (cloud.originalAmount != null &&
    (local.originalAmount ?? 0) != cloud.originalAmount) { ... }
```
本地 NULL + 云端显式 `0` 时 `(null ?? 0) == 0` → 判为相同 → 不应用。而导出侧 `0` 是**非空**（会写键）、NULL 不写键（`transactions_json.dart:198`）→ 两端指纹 `''` vs `'0.0'` 不同 → 该行永不收敛。可达性：编辑器直接 `double.tryParse`（`amount_editor_sheet.dart:1362-1364`），用户输入 `0` 即为 `0.0`。

### 2.2 实测结果（`V2_probe_verify.txt`）

```
[E] 仅改分类 32 行：A==B 0 行，**不一致 32 行**        ← 预期命中
      tx=11  A分类=测-工资-年终奖  B分类=测-工资-月薪
      tx=12  A分类=测-餐饮-午餐    B分类=测-旅行-酒店
[G] 分类+金额 32 行：A==B 32 行，**不一致 0 行**       ← 对照组成立
[F] original_amount=0 24 行：A==B 0 行，**不一致 24 行**  ← 预期命中
      tx=14  A.original_amount=0.0  B.original_amount=None
```

B 端「下载同步」日志中每账本 **修改 = 4**（= G 组 4 行/账本），**E 与 F 组一行都没进 diff**。

**总逐字段差异 = 56 = 32（E）+ 24（F）**（`V2_compare_result.txt`）。

### 2.3 稳定分歧：增量路径无法收敛（决定性验证）

B 回传后 A 端冷启动出现「云端有更新 → 一键应用全部」弹窗。对 A 执行「一键应用全部」：

- `变更已应用` **= 0 条**（E/F 同样检测不到）
- 但 `合并后回传完成 = 8` 个账本（A 把自己的值又覆盖回云端）
- **再比对：56 行分歧原样保留**（`V2A_probe_verify.txt`，E 32 / F 24 一字未变）

> **结论**：这两类改动**不是「暂时没同步」，而是端到端不可收敛** ——
> 两端各自保留自己的值，指纹持续不一致，每次启动都提示「方向无法判定」；
> 增量合并、一键应用全部都无法修复，用户只能靠「全量下载」或「全量上传」以**整端为准**强制覆盖（会丢掉另一端的其它正常改动）。

### 2.4 缺陷清单

| # | 缺陷 | 位置 | 复现 | 影响 |
|---|---|---|---|---|
| **D-1** | **交易「分类」变更不参与增量 diff 判定** → 仅改分类的编辑永不跨设备传播 | `sync_diff_service.dart:280-400 _compareTx` | E 组 32/32 不一致；G 组证明分类列本身可同步 | 用户 A 改明细分类 → B 端永远看不到，且需整端覆盖才能收敛 |
| **D-2** | **`originalAmount` 的 NULL↔`0` 被 `?? 0` 掩蔽** → 云端显式 `0` 传不到本地 | `sync_diff_service.dart:370-372` | F 组 24/24 不一致 | 原始金额填 `0`（如赠品/折扣 0 元）的明细跨设备不同步；指纹持续不一致 |

**修复建议**

1. `_compareTx` 增加分类比较：用 `categoryKind|categoryName`（与 tags 同款、跨设备 rename 稳定的锚定口径），或 `categorySyncIdOverride` 之外的 `categorySyncId`；参考同文件 349-350 对 exclude 标记的论证。
2. `originalAmount` 比较去掉 `?? 0` 兜底，改成「云端有该键就比较（含 0）」，与 `currencyCode`/`override` 的 `cloud != null &&` 范式一致；`nativeAmount`（同在第 364-365 行用了 `?? 0`）建议一并复核。
3. 验收时把「字段有效覆盖度体检」纳入每轮门禁（`field_coverage.py`），避免再次出现「全 NULL ⇒ 平凡通过」。

## 3. 一次夹具假差异的归因（§7 不变量，非缺陷）

V1 首跑出现 **32 行不一致**，差异落在 `category`/`account` 两列（override 本身两端一致），行数恰好等于 override 造数行数。

**根因**：`data_import_service.dart:1527-1533`、`sync_diff_service.dart:683-696`、`sync_engine_apply.dart` **三处一致地实现了 §7 不变量**：

```dart
// 共享账本 override 与本地 int id 互斥（§7 决策，与 SyncEngine 一致）：
// override 非空时 categoryId/accountId/toAccountId 一律留 null，
// 避免本地主表同名分类/账户被误解析导致「override + int 双写」。
final categoryId = hasCatOverride ? null : _resolveCategoryId(cloud, categoryCache);
```

首跑夹具在**已有 int 外键**的行上写了 override，违反该不变量；导入/合并侧按设计把它规整为「override-only」，于是 B 的 int 为 NULL 而 A 仍非空 → A≠B。

**定性：夹具问题，不是同步缺陷**（反过来看，这恰好证明实现方在坚守不变量）。修正夹具（写 override 的同时把 int 置 NULL）后 V1 全绿。已在 `modify_v45.py` 内注释固化。

## 4. 其他静态发现

### 4.1 `transactions.tag_sync_ids_override` 不跨设备传播，且比对脚本口径有误

- **实现在此列上缺位**：`lib/cloud/**` 对 `tagSyncIdsOverride` / `tag_sync_ids_override` **零引用** —— 导出端（`transactions_json.dart`）只写 `categorySyncIdOverride`/`accountSyncIdOverride`/`toAccountSyncIdOverride`（207-212），指纹白名单（`sync_fingerprint.dart:141-143`）同样只有这三个，导入端（`data_import_service.dart:997-999`）也只有这三个。该列仅被 UI hydration 读取（`local_transaction_repository.dart` §7）。
- **比对脚本口径不一致**：`compare_sync_final.py` 的 SPEC 把 `tag_sync_ids_override` 列为**契约内**字段 → 若造数会必然假失败。**故 V1/V2 均刻意不造该列**。
- **建议**：要么补实现（导出/指纹/导入三处），要么把该列从比对 SPEC 的「契约内」移出并注明「预留未实现」。

### 4.2 `addTransaction` 的兜底与注释口径不一致（功能等价，待产品确认）

| 位置 | 表述 |
|---|---|
| `local_transaction_repository.dart:473-474,493` | 「原始金额未填则**落库兜底为记账金额**」→ `originalAmount: d.Value(originalAmount ?? amount)` |
| `amount_editor_sheet.dart:45-47` | 「**不在此处做 `?? amount` 兜底**，保留『是否手填』这一事实供差异统计使用」 |
| `db.dart:173-177` | 「刻意不回填存量行 —— 物理 NULL 才能区分『未填写』与『手填了相同值』」 |
| `data_import_service.dart:1708-1715` | 「**原样落库，绝不 `?? amount` 兜底**」 |

净效果：**「用户未填原始金额」在新数据上落 `= amount`、在导入/存量数据上落 `NULL`**，两种表示并存。读侧 `COALESCE` 使 UI/统计无感知，指纹也能各自收敛（本报告 V1 已证），但「未填写」这一事实在新建路径上不可表示。
**定性：注释/口径不一致（非行为缺陷）**，需产品确认「每条明细都有原始金额」是否为最终口径；若是，应同步修订编辑器与 db.dart 的表述。

### 4.3 目录内两处工具口径修正（本次已补）

- `field_coverage.py` 增加「有效覆盖度」判定（全 NULL ⇒ 标 ★平凡通过），支持传参指定快照；
- 新增 `extra_tables_check.py`，补 `compare_sync_final.py` 未覆盖的 `custom_field_definitions`；
- `probe_verify.py` 首版误用**本地自增 id**关联双端行（本地 id 早已不同序，结论全错），已改为按 `sync_id` 关联 —— 提醒：任何跨设备比对都必须以 `sync_id` 为身份。

## 7. D-1 修复：交易「分类」纳入增量 diff 判定

| 项 | 内容 |

| 位置 | `lib/cloud/sync_diff_service.dart` |

## 8. D-2 修复：去掉 `?? 0` 掩蔽（`originalAmount` + `nativeAmount`）

| 项 | 内容 |
|---|---|
| 位置 | `lib/cloud/sync_diff_service.dart:364-372`（改前） |

## 12. `created_by_user_id` 闭环验证（回答「B 回传覆盖云端 → A 再合并会不会把 A 的值也清空」）

**实测（`created_by_closure.txt`）**

| 步骤 | A 侧 `created_by` 非空 | 结论 |
|---|---|---|
| 基线（A 本机注入的 `dev-owner-16384`） | **5075** / 40083 | — |
| B 侧（经导入落库） | **0** | A 的值确实没传给 B |
| **A 端「下载同步」（增量合并）**：88 行 modified 被应用后 | **5075 → 5075** | ✅ **不会被清空** |
| **A 端「全量下载」（以云端覆盖本地）** | **5075 → 0** | ⚠️ **会被清空** |

**机制（代码级，解释了为什么两条路径结论相反）**

- 增量合并：该列**从不出现在任何写入结构里** —— 导出端 `transactions_json.dart` 无 `createdByUserId` 键；合并用的 `TransactionUpdateBySyncIdData` 无该字段；`updateTransactionsBatchBySyncId` 不写该列。**结构上不可能写它**，故任何 modified 行都不会被清空。
- 全量下载：走 `DataImportService.importData` **重建**交易行，而 `txCompanion.insert` 不含 `createdByUserId` → 新行为 NULL → 本机值丢失。
- 顺带说明：这也解释了为什么 B 侧恒为 0 —— 云端快照根本不携带该列。

## 13. 「created_by_user_id 不传播」是否符合预期？—— 结论与建议

**事实（代码级，全部实测确认）**

| 检查 | 结果 |
|---|---|
| `lib/cloud/**` 引用 `createdByUserId` / `createdByUserId` 快照键 | **零**（导出/指纹/解析三处都没有） |
| `markTxAuthor(...)` 调用方 | **零**（`lib/pages`、`lib/widgets`、`lib/services` 全目录零命中；仅 `local_transaction_repository` 有实现、`local_repository` 有转发） |
| 读取方（UI / 统计 / 报表） | **零** |

→ 这是一个**完全休眠的预留字段**（共享账本 v24 引入，配套 `ledger_members` / `shared_ledger_*` 一套共享账本能力，而该能力在文件式后端下同样未接线）。

**判定**

| 若产品意图是… | 是否符合预期 | 需要做什么 |
|---|---|---|
| **本机视角**（每台设备只记自己记的，"谁记的"不外传） | **不传播符合预期** | 无需改动传播链路 |
| **跨设备可见**（B 端要看到 A 端记的） | **不符合预期** | 需补三处实现：导出写键、指纹白名单加键、解析读键 + `markTxAuthor` 接线到写入路径 |
| （两者都不论）**「全量下载」清空本机值** | **不符合任何一方的预期** | 本机专属信息不该被远端覆盖清空；建议全量恢复时按 `syncId` 回填本机专属列，或把该列纳入快照 |

**建议**：`created_by_user_id` / `last_edited_by_user_id` 属**待产品确认**项，优先级低（字段休眠、当前无用户可见影响）；但若将来启用，必须同时处理上表第二行（传播）与第三行（全量恢复清空）—— **只做前者会被后者反复抹掉**。
