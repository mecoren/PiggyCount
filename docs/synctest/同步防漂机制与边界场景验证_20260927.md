## 1. P0：指纹白名单 ↔ `_compareTx` 覆盖字段 的穷举一致性检查

### 1.1 为什么必须做成"穷举"

「指纹有、diff 没有」这类缺陷此前**已出现三次**，形状完全相同：

| 次序 | 字段 | 发现方式 |
|---|---|---|
| 1 | 附件清单（审计 S11） | 人工排查 |
| 2 | `categoryName/categoryKind`（D-1） | 人工排查 |
| 3 | `recurringSyncId`（P1-2） | **本次由本测试自动抓出** |

光给每个字段各补一个用例不够 —— 白名单里还有 20 个键。所以清单**由实现派生**：

```
test/cloud/sync_contract_coverage_test.dart
  deriveFingerprintKeys()
    └─ 读 lib/cloud/sync_fingerprint.dart，按大括号配平截取事务段 return map
       → 正则提取全部键（22 个）—— 新增字段自动进入检查范围，无处可藏
```

### 1.2 两层断言 + 可复核豁免

| 层 | 断言 | 覆盖 |
|---|---|---|
| **Tier 1** | 指纹必须随该键变化 | 22/22 |
| **Tier 2** | `computeDiff` 必须报 modified | 21/22 严格 + 1 豁免 |

Tier 2 允许一张**显式豁免**（写在用例里，必须写明可复核理由）。当前唯一豁免：

> `tagSyncIds` —— 标签身份由 `importTags` 元数据合并收敛（按名/syncId 采纳云端身份），
> 且交易与标签的关联走本地 `tag_id`，因此该键**不需要** diff 报 modified。

豁免并非"放行"：测试仍会跑它并断言**没有** modified —— 一旦行为改变（开始报了）会立刻失败，提示删除豁免。

### 1.3 三条防漂断言

1. **夹具必须穷举覆盖白名单** → 新增同步字段若不补夹具，直接红：
   > `指纹白名单里有键没有配套夹具：{...} —— 新增同步字段时，请补"只改该字段"的用例，否则该字段可能"指纹有、diff 没有"`
2. 夹具不得包含白名单以外的键（白名单删字段时同步清理）；
3. 豁免必须写明非空且足够长的理由。

### 1.4 它抓到的第一个洞（→ P1-2）

初版夹具修正到位后（见 §1.5 的两次夹具自坑），Tier 2 对 `recurringSyncId` 报出：

```
recurringSyncId → 产出 modified  [E]
  Expected: <1>   Actual: <0>
  ...实际 changes=[]
```

即：**该键在指纹白名单里，但 `computeDiff` 返回空变更**。

### 1.5 过程中的两次夹具自坑（记录以防重犯）

| # | 现象 | 根因 |
|---|---|---|
| 1 | Tier 2 大面积"通过"却毫无鉴别力 | `_with()` 里**大部分可选参数漏写 `= _unset` 默认值** → 每个用例都先吃到一条「备注: "A" → ""」的伪差异 → `modifiedCount` 恒为 1 |
| 2 | 同上 | 默认云端带 `tagNames:['报销']` 而本地无标签 → 所有用例都带一条标签伪差异 |

**修法**：给 `_with()` 每个可选参数都加 `= _unset`；默认云交易与默认本地状态**完全对齐**（含"都没有标签"）；并把 `实际 changes=<diffDetails>` 写进断言消息 —— 正是它把上面两处暴露出来的。

## 2. P1-2：`recurringSyncId` —— 第三个同构洞（已修复）

### 2.1 证据（为什么它是洞而不是设计取舍）

| 环节 | 事实 |
|---|---|
| 指纹白名单 | `sync_fingerprint.dart` 含 `'recurringSyncId': it['recurringSyncId'] as String? ?? ''` |
| 导出侧 | `transactions_json.dart` 写 `if (t.recurringId != null && resolved.isNotEmpty) 'recurringSyncId': …` |
| **diff** | `sync_diff_service.dart` 里 `recurringSyncId` **只出现在 added 导入路径**（`recurringSyncIdToId`），`_compareTx` 完全没有它 |
| 后果 | 两端指纹不同而 diff 为空 → 状态卡永久"有差异"、点「下载同步」点不出变更、merge-then-publish 回传覆盖云端形成 ping-pong |

### 2.2 修复必须**成对**（这是本轮最容易做错的地方）

只加"检测"不加"应用"会把体验从「静默不同步」恶化成「每轮都提示有变更、点了也没用」。故改了 4 处：

| # | 位置 | 改动 |
|---|---|---|
| 1 | `sync_diff_service.dart computeDiff` | 经 `getRecurringTransactionsByLedger` 建 `本地规则 id → syncId` 映射，**语义与导出侧一字不差**（解析不到＝无锚点） |
| 2 | `sync_diff_service.dart _compareTx` | 新增 `(localRecurringSyncId ?? '') != (cloud.recurringSyncId ?? '')`，**严格比较、不加 `cloud != null` 守卫**（导出侧"无锚点不写键"是确定性的，不存在 `originalAmount` 那种旧快照缺键的历史包袱——与指纹逐字同口径） |
| 3 | `transaction_repository.dart` | `TransactionUpdateBySyncIdData` 新增 `d.Value<int?>? recurringId` **三态**（null=不改动 / Value(null)=清空 / Value(id)=写入）—— 用三态而非"可空即清空"，避免未涉及该字段的调用方静默清掉锚点 |
| 4 | `local_transaction_repository.dart` + `sync_diff_service.dart` 合并构建器 | 批量更新写入该列；合并侧把 `cloud.recurringSyncId` 解析成本地 id 后传入 |

### 2.3 验证

- `sync_contract_coverage_test.dart`：`recurringSyncId` 从"Actual 0"转为通过；
- 新增 2 项收敛测试：**云端有锚点→本地写回**、**云端无锚点→本地清空**，两者都断言"应用后再 diff 为空"；
- 全量套件 1605 项通过。

## 3. P3 边界场景（首次验证）

### 3.1 P3-10 云端删除镜像

11 轮以来造数脚本一直用 `NO_DELETE=1`，删除语义**一次都没测过**。本轮首次：

| 步骤 | 观察 |
|---|---|
| A 端删除 16 笔（每账本 2 笔，均无附件）并上传 | 8/8 `Post-upload verify passed` |
| B 端「下载同步」 | 每账本 `差异计算完成: 删除=2`；预览显示「**删除 2 条**」，按钮是「**应用 0 项**」且 `clickable=false`；行**默认不勾选** |
| 不勾选直接放行的结果 | 比对 `仅A=0 仅B=16 字段差异=0` → **B 保留了那 16 笔**（安全语义成立） |
| 显式点「全选」再应用 | 每账本 `批量删除: syncId 路径 size=2 实删=2`；8 个账本共实删 16 |
| 最终 | `40067 笔共同行 仅A=0 仅B=0 字段差异=0` |

**结论**：SYNC-05「删除默认不勾选」在设备端成立；用户显式勾选后删除通路可用；两条路径都收敛。

### 3.2 P3-11 附件「仅改附件」端到端

此前只有 Dart 单测（审计 S11 的修复）。本轮设备端：

### 3.3 P3-12 三项异常场景

**(a) 双端并发编辑同一账本（不同行）**

夹具用 `sync_id`（两端一致）挑**不相交**的逻辑行：A 改每账本第 1 笔（金额+`[A并发]`），B 改第 2 笔（备注+`[B并发]`）。

| 时点 | A 端 | B 端 |
|---|---|---|
| A 上传后、B 合并前 | `[A并发]`=8 | `[B并发]`=8 |
| B「下载同步」后（每账本 `修改=2`） | 不变 | **`[A并发]`=8（拿到 A 的改动）、`[B并发]`=8 → 0（本地改动被回退）** |

**发现（产品级）**：并发场景下「下载同步」会**把下载方的本地独有改动回退成云端值** —— 且这是**默认全选 + 一键应用**的路径。产品文档写的是「两台设备同时编辑同一个账本，后上传的会覆盖先上传的改动」，实测方向是**先上传的（A）盖掉后编辑的（B）**，因为 B 走的是"下载"方向。UI 有预览（显示「修改: 本地值 → 云端值」），但用户不细看就会丢本地改动。**与文档"应避免并发编辑同一账本"一致，但建议在预览里对"本地独有改动"做显式警示。**

**(b) 合并中途强杀（中断恢复）**

| 步骤 | 观察 |
|---|---|
| A 造成 8 账本各 1 处变更（标记 `[KILL2]`）并上传 | A: 8/8 |
| B「下载同步」进行到 18s 时 `am force-stop`（不给收尾机会） | 只应用了 1 个账本 |
| 中断后 B 的库 | `integrity=ok uv=48`；`[KILL2]` 分布 = `行数=1 涉及账本=[1]` → **前缀式应用，无半应用账本** |
| 重启后重试「下载同步」 | **只补做剩余 7 个账本**（已完成的账本自动 `inSync` 跳过）→ 8/8 收敛 |

**结论**：逐账本事务 + 重启可续传成立；中断不损坏库、不留脏状态。

**(c) 断网（停掉 WebDAV 服务端）**

| 步骤 | 观察 |
|---|---|
| 停掉服务端 → B 冷启动 | 弹「**8 个账本同步状态检查失败（网络或超时），请检查网络后重试**」+「确定」 |
| 关键点 | **没有误报"已是最新"** —— 与 `startup_sync_checker.dart` 的 P1-3 注释一致（失败账本绝不静默计入"已是最新"） |
| 重启服务端 → B 冷启动 | 无任何错误文案，恢复正常 |

> 顺带确认：**8443 端口已可非提权重绑**（`REBIND_OK`）。开机时它曾落在 Windows 动态保留段（需 `net stop winnat` 释放），而停过一次之后 winnat 不再回收该端口 —— 故本轮的"停服务端"测试才可行。

## 4. P1-3：`tag_sync_ids_override` 是死字段（已定性，未删列）

### 4.1 证据（跨文件追踪）

| 检查 | 结果 |
|---|---|
| 全仓写入方（`lib/`、`test/`、`packages/`） | **零**（`tagSyncIdsOverride:` / `=` 只命中 Drift 生成代码 `db.g.dart`） |
| 实际读取方 | **零** —— `_hydrateSharedOverridesFull` 读的是 **`transaction_tag_overrides` 表**（按 `tx.syncId` 查），与该列无关 |
| `lib/cloud/**` 引用 | 零（导出/指纹/解析三处都没有） |
| 唯一提及 | 一句**过时注释**（声称 hydration 按该列读） |

### 4.2 处置与**未删列的理由**

| 选项 | 评估 |
|---|---|
| 删列（建议过的方案之一） | 需要 v49 schema 迁移 + Drift 代码重生成；而该列零写入零读取，**运行时收益为 0**，风险（旧 Android 的 `DROP COLUMN` 支持、别处引用面）却不小 → **不做** |
| 补实现（另一方案） | 该列没有任何写入方，补导出/指纹/解析只会让一个恒为 NULL 的列参与同步 —— 解决不了"共享账本标签 override 不传播"的真问题（那是 `transaction_tag_overrides` 表需要进快照，属另一件事）→ **不做** |
| **实际采用** | ① `db.dart` 该列改写成明确的"预留未实现（死列），不要使用"+ 启用前提（三处必须同时补，且比对脚本会在补的那一刻报 `[DRIFT]`）；② 修正 `local_transaction_repository.dart` 那句过时注释，指明真实数据源 |

**遗留（需产品决定，非本轮范围）**：`transaction_tag_overrides` 表**有真实写入方**（`transaction_editor_page.dart` 的 Editor 路径）与多个读取方，但**不进云快照/指纹/解析** → 共享账本的标签 override 在文件式后端下**不跨设备传播**。若要支持，需把该表纳入快照（比补一个死列更根本）。

## 5. P1-4：`_compareTx` 表驱动化 —— 我做了取舍（请复核）

原建议是「改成表驱动『字段 → (取值, 归一化器)』，并与指纹白名单共用同一份声明」。**我没有做机械重写**，理由：

| 考量 | 说明 |
|---|---|
| 真实风险已被闭合 | "漏比某字段"这个**唯一实际出过事故**的风险，已由 P0 的穷举测试从根上守住 —— 新增字段若漏比，测试直接红 |
| 两套语义并不相同 | 指纹侧是"归一成字符串做哈希"，diff 侧是"带容差的语义比较"（金额 ±0.001、时间精确到秒、JSON 走 codec 规范化）。共用一张表就要为每个字段挂两套归一化策略，本质仍是"27 段各自定制的逻辑"，只是换了个外壳 |
| 边际收益 vs 风险 | 收益主要是可读性；代价是改动 43KB 热路径里的 27 个比较分支 —— 回归面大、收益小 |

**替代做法（已落地）**：把两种比较策略**显式化**并写死在代码里，供后续维护者对号入座：

```
① 严格比较（缺键 = 无该属性）：type/amount/happenedAt/note/账户名/tags/
   exclude 标记/分类(kind+name)/周期锚点/attachments
② 缺键不改动（cloud.x != null && 才比）：currencyCode/nativeAmount/
   originalAmount/customValues/3×override
   ⚠️ 新增字段一律用 ①，错用 ② 会重现 D-2 的"指纹说不同、diff 说没变化"
两类都受 sync_contract_coverage_test.dart 穷举守护
```

D-2 恰恰就是"同族写法不一致"造成的（`?? 0` 与 `?? ''` 混用），把策略写清楚比把逻辑搬进表更能防复发。

**若你仍要表驱动**：P0 测试就是现成的安全网，可以放心做 —— 但请把这件事当独立重构排期，别和字段修复混在一轮。

## 6. P1-5：全量恢复不再清空「本机专属列」

### 6.1 问题与路径证据

| 环节 | 事实 |
|---|---|
| 实测 | A 端「全量下载」后 `created_by_user_id` 非空行 **5075 → 0**（交易行数不变） |
| 入口 | `cloud_sync_page.dart` → `fullRestoreAllRemoteLedgers` → `restoreLedgerFromJson` |
| 根因 | `data_import_service.dart` 的恢复事务体是**先 DELETE 再 INSERT**：`clearLedgerTransactions` + `importTransactionsJson`，而重建用的 `TransactionsCompanion.insert` **不含** `created_by_user_id` / `last_edited_by_user_id` |
| 语义 | 云端**从未对这两列表达过意见**（快照根本不携带它们）→ 恢复不该让本机值丢失 |

### 6.2 修复（方案 A：按 `syncId` 回填）

```
恢复前：_snapshotLocalOnlyTxColumns(db, ledgerId)   // 只收 syncId 非空的行
   ↓ clearLedgerTransactions（DELETE）
   ↓ importTransactionsJson（INSERT）
恢复后：_restoreLocalOnlyTxColumns(...)             // db.batch 批量回填，只写非空值
```
整个流程仍在**同一个 `db.transaction`** 内，与清空/导入/镜像删除原子一致。

### 6.3 验证

`test/cloud/restore_preserves_local_only_columns_test.dart`（2 项）：
- 恢复后 `created_by/last_edited_by` **按 syncId 保留**；旧值为 NULL 的行不做无用写；无 syncId 的行不参与回填（身份不稳定，属已知边界）；

## 9. 本轮暴露的**工具隐患**（已修，值得记一笔）

> **`push_db` 的旧写法会删掉设备库。**
> 原写法是 `rm -f 旧库 && cp 新库`：一旦 `cp` 失败（文件不存在 / run-as 失败 / 空间不足），设备上**既无旧库也无新库**。本轮实际踩到 —— 我改动运行器时漏改推送路径参数，A 端库被删空（`uv=0`、无 `ledgers` 表），靠夹具前快照才恢复。
>
> **修法**：`push → 拷到 .new → 校验 .new 存在且 >1MB → 原子 mv 覆盖`，任一步失败都**保留原库**并返回非 0；4 个脚本（`run_py_modify.sh` / `V_modify.sh` / `V2_modify.sh` / `V_restore.sh`）统一改用它。已用"推送不存在的文件"验证过防护生效。
