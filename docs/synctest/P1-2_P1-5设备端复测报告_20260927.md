## 1. P1-5：全量恢复不再清空「本机专属列」

### 1.1 方法

| 步骤 | 操作 |

**来源② 应用自身回填日志**：


3. 修复自身的日志行触发（`恢复后回填本机专属列`），且总量与独立核验一致。

> 即：**重建发生了，且本机专属列被按 `syncId` 原样搬回**。修复在设备端生效。

## 2. P1-2：`recurringSyncId` 跨设备传播

### 2.1 夹具设计（只改锚点，排除干扰）

`modify_anchor.py` —— 每账本改动 3 行，**不碰金额/备注/分类/附件**：

| 组 | 含义 | 行数 |
|---|---|---|
| SET | `recurring_id`: NULL → 该账本的规则 | 16（每账本 2） |
| CLEAR | `recurring_id`: 规则 → NULL | 8（每账本 1） |
| 合计 | 改动行 24，行集两两互斥（脚本内断言） | 24 |

路径：A 端造数 → A 端「上传」→ B 端「下载同步」（逐账本 diff 预览合并）→ B 端统一回传 → 双端快照核验。

### 2.2 检测侧：改动被识别（这正是修复前缺失的一环）

修复前的缺陷签名是「**指纹说不同、diff 说没变化**」——对端预览会是 `修改=0`。实测：

```
（8 个账本各一行）
[SyncDiff] 差异计算完成: 新增=0, 修改=3, 删除=0
[SyncDiff] 批量更新: size=3 成功=3 主表=4ms tag=14ms (tag 未变跳过 3 行) 合计=19ms
[SyncDiff] 变更已应用: 新增=0, 修改=3, 删除=0
```

**8 账本 × 3 = 24 项**，与夹具规格（2 SET + 1 CLEAR）× 8 完全吻合；`tag 未变跳过 3 行`说明只有锚点列在流动。

### 2.3 应用侧 + 语义核验（按规则 `syncId` 解析，而非本地 int）

`transactions.recurring_id` 是**本地 int 外键**，两端自增 id 天然不同序 —— 直接比必然误报。跨设备的正确口径是解析成 `recurring_transactions.sync_id`（即快照里的 `recurringSyncId`）再比（`anchor_check.py`）：

| 检查 | 结果 |
|---|---|
| 交易数 / 仅A / 仅B | 40067 / **0** / **0** |
| 锚点非空 | A=16  B=16 |
| **解析后锚点不一致行** | **0** |
| SET 组落点（两端均应 = 目标规则 syncId） | **16/16 正确** |
| CLEAR 组落点（两端均应为 NULL） | **8/8 正确** |
| （对照）按本地 int 直接比的"不一致"行 | 8 ← 全是两端 id 不同序的**伪差异**，印证口径必要性 |

契约逐字段比对：`[OK] transactions 逐字段 比对（40067笔共同行） 仅A=0 仅B=0 字段差异=0`；附件 `A=28 B=28` 一致。

覆盖度门禁（防「全 NULL 平凡通过」）：`transactions.recurring_id 16 16 OK`、`[GATE-OK] 所有 require 字段本轮均被有效覆盖：['recurring_id']`、`coverage exit=0`。

### 2.4 收敛验证（缺陷的另一半签名是「永久 ping-pong」）

合并并统一回传后，B 端**再走一次**「下载同步」：

| 观察 | 结果 |
|---|---|
| 8 个账本状态 | 全部 `SyncDiff.inSync` |
| `变更已应用` | **0** |
| `localNewer` / `cloudNewer` | 0 / 0 |
| UI 状态卡（冷启动后） | 「**已同步**（本地5008条）／上传：已同步／下载同步：已同步」 |

与缺陷签名（「状态卡永久显示有差异、点『下载同步』点不出变更」）**正好相反** → 无 ping-pong，已收敛。

## 3. 过程中暴露的两处工具问题（已修，与产品无关）

| # | 问题 | 影响 | 修法 |
|---|---|---|---|
| 1 | 夹具行集重叠：首版「**先施加 SET、再查 CLEAR**」，而 SET 给原本无锚点的行挂上了锚点 → CLEAR 的 `recurring_id IS NOT NULL` 把刚 SET 的行选了进来 | 断言 `CLEAR 行集重叠 tx=45095` 当场拦下，未产出错误结论 | 改为「**先选定两组候选 → 断言互斥 → 再统一施加**」 |
| 2 | `run_py_modify.sh`：夹具 `exit≠0` 时**仍无条件把产出文件推回设备** | 产出文件可能是"事务未提交/写到一半"的残库 | 增加 `RC≠0` 与产出文件缺失两道守卫，失败即 `exit 1` 且不动设备库 |

> 第 2 条的实际影响为零：那次的产出文件与基线**完全一致**（Python 未提交的事务在进程退出时回滚），半成品没有落库。但这是**运气**，已按守卫修掉。
