> ## ⚠️ 补充验证与更正（2026-09-27 追加，务必先读）
>
> 后续对「字段**有效覆盖度**」的体检发现：本报告 4 轮里的「逐字段差异=0」对下列 8 个字段**不构成证据** —— 双端全为 NULL/默认值，属 **平凡通过**：
>
> `transactions.original_amount`、`transactions.custom_values_json`、`transactions.category_sync_id_override`、`transactions.account_sync_id_override`、`transactions.to_account_sync_id_override`、`transactions.tag_sync_ids_override`、`recurring_transactions.template_field_values`、`recurring_transactions.end_date`
>
> 已另开 **V1/V2 两轮专项验证**补齐（在 WebDAV 后端上执行），结论摘要：
>
> 1. **`original_amount`（原始金额）确认同步正确**：造出 **212 行「原币 ≠ 记账金额」**真实数据（4 种交易类型 × CNY/外币 × 5 种取值形态）后，双端逐字段差异 = **0**；44 行「手填同值」也正确往返。同批 `custom_values_json`（含 18 个字段定义）、3 个 `*_sync_id_override`、`recurring.end_date`/`template_field_values` 均一致。
> 2. **发现 2 处真实缺陷（探针实测）**：
>    - **D-1 交易「分类」变更不参与增量 diff 判定** → 仅改分类的编辑永不跨设备传播（实测 32/32 不一致；对照组「分类+金额」32/32 一致）——`sync_diff_service.dart:280-400 _compareTx` 未比较 category；
>    - **D-2 `original_amount = 0` 被 `?? 0` 掩蔽** → 云端显式 0 传不到本地（实测 24/24 不一致）——`sync_diff_service.dart:370-372`。
>    - 两者均造成**稳定分歧**：A 端再执行「一键应用全部」后 56 行分歧原样保留，增量路径无法收敛，只能靠全量上传/下载以整端为准覆盖。
> 3. 另一处 WebDAV 轮特有观察：本轮 B 端走的是**云同步页 →「下载同步」手动逐账本预览合并**（而非启动「一键应用全部」）。原因是 V1 只做原地改字段、未增删行 → 双端 count 相等，B 端 `localUpdatedAtTrusted=false` → 方向仲裁退回 count 兜底 → `direction=unknown` → 启动检查**按设计不弹**合并框（`cloud_sync_manager.dart:643-666`、`startup_sync_checker.dart:509-522`）。属设计内行为，需用户在云同步页手动处理。
> 4. 另发现 `tag_sync_ids_override` 在 `lib/cloud/**` **零引用**（不导出/不进指纹/不导入，仅 UI hydration 读取），而 `compare_sync_final.py` 却把它列为**契约内**字段（口径错误）；`compare_sync_final.py` 亦未覆盖 `custom_field_definitions` 表。
>
> 5. **上述 D-1 / D-2 已修复并实机复验**（同日，仍在 WebDAV 后端上执行）：`sync_diff_service.dart` 的 `_compareTx` 补分类比较（口径与指纹白名单同源，transfer 归空）、去掉 `originalAmount`/`nativeAmount` 的 `?? 0` 掩蔽（保留"云端缺键不触发"的既有约定）。重装新构建后重跑 V2 探针：**E 组 32/32、F 组 24/24 全部转为一致**（修复前后对比见补充报告 §9）。新增 11 项 Dart 回归测试（反向验证：临时回退修复则其中 5 项精准变红）与 8 项比对脚本防漂测试；`flutter test` 全量 **1554 项通过**、`test/cloud` 358 项通过。
> 6. **比对脚本防漂重构**：`compare_sync_final.py` v4 改为「SPEC 声明 + 从 `lib/cloud` 实现派生 + 三向校验」，契约清单不再可能静默漂移（漂移即退出码 3）；同时修正 `tag_sync_ids_override` 口径、清理死代码、把 `recurring_id` 补为契约内。
> 7. **字段覆盖度已纳入每轮门禁**：`16_snap_compare.sh` 末尾自动跑 `field_coverage.py`，可用 `REQUIRE_FIELDS` 声明「本轮要验证的字段」，任一字段属平凡通过即 `COVERAGE_EXIT=4` 失败。
> 8. **另一处闭环实测**：`transactions.created_by_user_id`（「谁记的」）在文件式（WebDAV/S3）后端下**不跨设备传播**（`lib/cloud` 零引用、`markTxAuthor` 零调用方、零读取方 —— 属休眠的预留字段）。**增量合并不会清空本机值**（实测 5075 → 5075），但**「全量下载」会**（实测 5075 → **0**）—— 若将来启用该字段，传播与"全量恢复保留本机专属列"必须一起做。

### 1.3 环境问题与处置（重要，非产品缺陷）

**问题**：本轮测试开始时，宿主机 TCP **8443 落在 Windows 动态保留端口段（8378–8477，由 Hyper-V/winnat 保留）**内，非提权进程无法 `bind`（`WinError 10013`），导致 WebDAV 测试服务端无法启动；两端应用在 WebDAV 后端下冷启动弹窗提示「8 个账本同步状态检查失败（网络或超时），请检查网络后重试」。

**处置**（`start_wd_server_elevated.ps1`，已记录到 `start_wd_server_status.txt`）：

1. 提权 `net stop winnat`，释放动态保留段（释放后保留段仅剩 `3306 / 5357 / 6379 / 50000-50059`）；
2. 启动 WebDAV 测试服务端占用 8443（`8443 监听数 = 1`）；
3. `net start winnat` 恢复 NAT 驱动；恢复后 `8443 监听数 = 1`，**服务端未受影响**；
4. 连通性自检：`OPTIONS https://127.0.0.1:8443/piggycount/ -> HTTP 200`，`PROPFIND` 正常列出 8 个槽位对象。

**结论**：属**测试宿主环境**（端口保留）问题，与产品代码无关；服务端恢复后两端「同步状态检查失败」弹窗随即消失。

### 5.2 差异项逐条定性（均为「预期 / 契约外」）

| # | 差异项 | 涉及行数（R1 → W4） | 定性 | 依据 |
|---|---|---|---|---|
| 1 | `transactions.created_by_user_id` | 5000 → 5075 | **云快照不携带的契约外字段** | 该列全仓**无写入方**（`markTxAuthor` 只有定义、无调用方）、无读取方，`lib/cloud/**` 零引用（`db.dart:134` 标注为共享账本 v24 预留字段）；A 端非空值全部来自本轮**注入/造数脚本写死的假用户** `dev-owner-16384`，B 端保持 NULL |
