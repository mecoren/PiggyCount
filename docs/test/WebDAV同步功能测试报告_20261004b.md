### 5.5 【铁证】E2EE 附件三段式 sha256 验证

| 环节 | 结论 | 数值 |
| --- | --- | --- |
| A 端落盘附件内容 sha256 | **== 文件名**（明文内容寻址键） | **7/7 相等** |
| B 端落盘附件内容 sha256 | **== 文件名** | **7/7 相等** |
| 服务端 `.bin` 对象内容 sha256 | **≠ 文件名**（存的是密文） | **7/7 不等** |

示例（`07dd…ab6`）：

```
文件名（=明文sha） : 07dd2f6385aca43cfeead146e31cbcdb6a345b617a0d0c6336647d488bb72ab6
A 端内容 sha256    : 07dd2f63…ab6   ✅ 相等
B 端内容 sha256    : 07dd2f63…ab6   ✅ 相等
服务端内容 sha256  : edcfe97ac3dcd2df…  ✅ 不等（密文）
```

且 A/B 两端 7 个物理文件**逐字节一致**（`att_check.py`：`7 个 vs 7 个，全部一致 ✅`）。

> 若只看"服务端 sha256 与文件名不符"会误判为 bug —— 这**恰恰证明**服务端存的是密文，
> 而 B 端能解密回与文件名逐字节相同的明文。三段合起来才构成「密文往返无损」的完整证据。

## 6. 问题分析（含差异原因说明）

本轮**未发现任何非预期不一致**。以下 4 类"差异"经回源码核实**均为设计内行为或测试构造性现象**，
逐条给出证据与成因。

### 6.1 `categories` 29 → 28：转账分类被动合并 —— **设计内自愈，非缺陷**

**现象**：WDR1/WDR2 两端均 29 个分类；WDR3 起两端均 **28** 个，且**同一分类**消失
（`sync_id=88e2935d-d33c-4fc6-9ac0-0a836b4dcbf5`，名称 `测-转账`）。**两端同步收敛，不存在分叉。**

**实测数据（A 端）**

| 快照 | `kind='transfer'` 的分类 |
| --- | --- |
| WDR1 / WDR2 | 2 条：`id=1 转账 (1af0228e-…)`、`id=29 测-转账 (88e2935d-…)` |
| WDR3 / WDR4 / WDR5 | 1 条：`id=1 转账 (1af0228e-…)` |

**代码级根因**：`lib/data/repositories/local/local_repository.dart:2056` 的
`getTransferCategory()` —— 干净数据下 transfer 分类应恰为 1 条；发现 **>1 条时被动合并**：

```dart
final all = await _categoryRepo.getAllTransferCategories();
if (all.length <= 1) { return _categoryRepo.getTransferCategory(); }
final keeper = all.first;                 // 保留 id 最小者
final dupes  = all.sublist(1);
// 1) transactions.categoryId 从 dupes 改写到 keeper
// 2) budgets / recurring_transactions 上引用的 dupe 也搬到 keeper
// … 再删除 dupes
```

**触发时机（为什么是 WDR3）**：该方法是**懒触发**的 —— 只有调用它的页面才会执行合并。
WDR3 的操作路径是「我的 → 资产 → 点账户 → 进入账户详情页」，
而 `lib/pages/account/account_detail_page.dart:1384` 会 `ref.watch(transferCategoryProvider)`，
正是这条读取触发了合并。**WDR2（记账页/交易详情页）与 WDR4（账本管理）都不会走这里**，
所以计数在前两轮保持不变。

> **S3 轮同位复现**：`S3同步功能测试报告_20261004b.md` 记录 R3 同样出现 `categories 29→28`，
> 而 S3 R3 也是"改账户"轮次、同样是打开账户详情页触发 —— **两轮成因完全一致，可互为交叉验证**。

**定性**：**测试数据构造性现象 + 产品设计内自愈**，不是同步缺陷。成因很明确：
种子注入脚本额外造了一条 `kind=transfer` 的「测-转账」分类，而 App 自身已有一条规范「转账」分类，
于是出现 2 条；App 在首次读取转账分类时按既定策略合并为 1 条，合并结果经快照正常传播，
**两端都收敛到同一状态**。生产环境不会出现重复 transfer 分类，故正常用户不会遇到。

### 6.2 `deleted_transactions` A=1 / B=0 —— **刻意设计，非缺陷**

| 轮次 | A `transactions` | A `deleted_transactions` | B `transactions` | B `deleted_transactions` |
| --- | --- | --- | --- | --- |
| WDR1 | 40008 | 0 | 40008 | 0 |
| WDR2（软删 1 笔） | 40008 | **1** | 40008 | **0** |
| WDR3 | 40008 | **1** | 40008 | **0** |
| WDR4 / WDR5 | 40008 | **1** | 40008 | **0** |

**成因**：软删把行从 `transactions` 移入本机 `deleted_transactions`
（`lib/data/repositories/local/local_transaction_repository.dart`），而该表**不进快照**：
全仓 `lib/cloud/` 下对该表 **0 处引用**。因此：

- **删除的数据效果正确传播**（快照导出的是已移除该笔的 `transactions`，两端主表逐字段一致，
  不存在"删了又复活"）；
- **回收站记录不传播** → B 端回收站为空，用户无法在 B 端恢复该笔。

**这是文档化的刻意设计**：`lib/pages/maintenance/recycle_bin_page.dart` 顶部类文档明确写着
「回收站**只在本机**：归档行不进快照……对端要感知这笔删除，走的仍是原本那条路 ——
本地有/云端无的 diff 项」。即**删除的语义传播、归档的"原件"不传播**。

本次比对脚本已用 `DEVICE_LOCAL_TABLES` 单列块显式呈现该表（**不计 issues / 不影响退出码**），
避免 `exit=0` 被误读为"全表逐字节一致"。

### 6.3 启动同步检查的两种表现：内容差异静默 / 元数据差异弹窗 —— **S3 轮结论在 WebDAV 完整复现**

本轮 5 轮的 B 端冷启动表现形成完整对照，**与 S3 轮结论一致**：

| 轮次 | B 端本地 vs 云端差异性质 | 冷启动表现 |
| --- | --- | --- |
| WDR1 | B 端为空库，云端 8 本全新 | 弹「发现云端账本」→ 点「下载」导入 |
| WDR2 | 1 本账本**内容**不同 | **无弹窗**（静默） |
| WDR3 | 8 本账本**内容**不同（账户是 user-global） | **无弹窗**（静默） |
| WDR4 | 1 本账本**元数据**（名称）不同 | **弹遮罩**：`云端账本信息与本地不同`<br>`账本名：默认账本 → Default-R4RENAMED`<br>`启动检查不会自动合并（避免覆盖你的本地改动）。请到「我的 → 云同步」手动下载同步。` |
| WDR5 | 无差异 | **无弹窗**（静默） |

**代码级解释**（`lib/cloud/startup_sync_checker.dart`）：

- 内容差异 → 指纹不一致但新旧方向判不出来（`direction=unknown`）→ 进 `unknownDiffLedgers`，
  **不作为下载候选**；`candidates.isEmpty` 且无元数据差异时走 `controller.dismiss()`（静默），
  `_lastRunOutcome = SyncOpOutcome.softFail`。
- 元数据（账本名）差异 → 进 `metaDiffLedgers` → 走 `controller.info(title/texts…)`，
  弹出带具体改名明细的遮罩。
- `unknownDiffLedgers` 的提示文案（`startupSyncCheckUnknownDiffHint`，4 语）
  **只在"有候选"那条分支里渲染**，所以内容差异场景下**不可达**。

**影响与定性**：无候选时静默是**设计内**（避免在判不出新旧时乱动数据），
但**用户完全没有被告知"有账本与云端不一致"** —— 这是可讨论的体验盲区，**不是同步正确性问题**：
本轮 5 轮全部 `exit=0`，且用户从「我的 → 云同步」手动下载即可正常收敛。
该结论与 `S3同步功能测试报告_20261004b.md` §6.3 一致，本轮为**第二次独立复现**（不同后端）。

### 6.5 测试方法学踩坑（本轮新增/复核）

1. **服务端必须以后台任务方式启动**，并 `netstat` 复核 `LISTENING`；
   否则随该次 shell 调用被回收，App 报 `Failed to initialize WebDAV: Connection refused`。
2. **服务端日志需无缓冲**（Python 加 `-u`），否则重定向到文件时块缓冲、日志 0 字节。
3. **服务端目录必须清空后才能验证"首传"**：上一轮残留的 8 个同名账本会让本次上传变成
   原地覆盖、附件被"已存在"跳过，**测不到任何上传证据**。本轮改为**改名保留**
   （`data_pre_wd_20261004b/`，未删）后重开空目录，R1 才拿到 15 次真实 PUT。
4. **拉库必须连 `-wal`/`-shm` 一起拉**，且用 `adb exec-out`
   （`adb shell cat` 会把 `\n` 转成 `\r\n` 损坏二进制）。
   Drift 走 WAL，只拉主文件会静默丢最新提交。
5. **比对脚本必须传绝对路径**，否则 `sqlite3.connect` 新建空库、每列报"无此列"、
   退出码 3 伪装成"契约漂移"。
6. **`uiautomator dump` 的文本在 `content-desc` 上，`text` 恒为空** ——
   `grep 'text="…"'` 永远空手。这是本项目排查 UI 时最大的弯路。
7. **金额键盘的退格键是图标、无文本**：`uiautomator` 节点列表里看不到它，
   必须回源码（`lib/widgets/biz/amount_editor_sheet.dart:1350` `closeKey()`）
   得知它位于键盘第 4 行第 3 列。另外「完成」在金额为 0 时是**禁用**的（`clickable=false`），
   看到 `click=False` 不代表点错位置。
8. **`getTransferCategory()` 是懒触发**：只有真的走进"读转账分类"的页面才会合并重复分类，
   所以同类操作在不同页面上会得出不同的行数 —— 比较计数时**必须先确认触发路径**（见 6.1）。
9. **`shared_prefs` 的键存储类型不固定**：`cloud_active_type` 是 `<string>`，
   `piggycount_enc_enabled` 是 `<boolean … value="true"/>`。
   只按字符串形式写正则会把布尔键误判成"键丢了"（本轮已修 `final_state.py`）。
10. **不要用 `select *` 求哈希来判"两端是否一致"**：会把设备本地列算进去，
    10 张表全部报"不一致"而实际业务字段零差异。要用契约列（`wd_contract_fp.py`）。
