### 2.1 关于「云端已有旧账本」的处理（重要前提）

清理前云端并非空仓（上一轮遗留 8 个账本对象）。而 S3/WebDAV 是**文件式**后端：
「全量上传」只覆盖同名对象、**不会删除云端独有账本**。若直接注入 8 个新账本（syncId 不同），
云端会变成 16 个账本，B 端全量下载会把 16 个全导进来——**这不是同步 bug，而是测试构造问题**。

为在**不删除任何云端数据**的前提下让云端恒为 8 个账本，本轮把注入后 8 个账本的
`sync_id` 改写为云端现有的那 8 个（`align_ledger_syncids.py`，按 id 顺序一一对应），
上传即**原地覆盖**。验证有效：上传后 B 端启动发现弹窗显示的仍是 8 个账本，
且内容已全部换新（名称 `投资理财账本·R2·R3B` → `投资理财账本`，笔数 10008 → 5001）。

## 5. 问题分析

### 5.1 `transactions.note` 的 `NULL → ''` 归一化（预期行为，非缺陷）

**现象**：R2/R3/R4 中，凡「通过 UI 新建且未填备注」的交易，A 端 `note IS NULL`，B 端 `note = ''`。
全库统计：A 端 `note IS NULL = 1 / note = '' = 0`，B 端 `note IS NULL = 0 / note = '' = 1`（R3 为 2 笔）。

**根因（代码级）**：
- 导出：`lib/cloud/transactions_json.dart:211` `'note': _sanitizeString(t.note)`，
  而 `_sanitizeString`（同文件 `:16-17`）对 `null` 返回 `''`。
  对比同文件 `:170` 账户 note 用的是 `if (a.note != null) 'note': ...`（为 null 时直接不写该键），
  **交易 note 没有这层保护**，这是两端唯一的写法差异。
- 导入：`note: _readString(m, 'note')` 读到 `''` → 落库为 `''`。

**为什么同步引擎察觉不到**：`lib/cloud/sync_fingerprint.dart:138`
`'note': it['note'] as String? ?? ''` —— 指纹**刻意**把 `null` 与 `''` 归一为同一值。
同口径还覆盖 `categoryName` / `categoryKind` / 三个 `*SyncIdOverride`。
因此该差异对指纹/差异比对完全不可见，不会产生假「有更新」，也不会来回抖动
（首次同步后落库即 `''`，此后稳定）。

**影响评估**：仅字节级不一致，UI 表现一致（都渲染为无备注），属**设计内的等价归一化**。
若后续要做「两端 DB 严格逐字节相等」的断言，需要把 `note` 列入与指纹同口径的归一化白名单。

### 5.2 合并路径（一键应用全部）不传播实体删除

**现象**：A 端分类数 29 → 28（少了「测-转账」），R3 走**合并**路径后 B 端仍为 29；
R4 改走**全量下载**后 B 端收敛到 28。

**机制**：
1. R3 的 B 端走 `一键应用全部`，`SyncDiffService` 输出 `新增=1, 修改=0, 删除=0`，
   差异应用只做**新增/更新**，**没有删除语义**，所以 B 端多出来的分类不会被清掉。
2. `全量下载`（`DataImport` 恢复前清空账本）是**整体替换**语义，R2 已验证它能让分类 29=29 精确收敛，
   R4 进一步验证它能收敛 A 端删除分类后的状态。

**结论**：两种接收路径的收敛能力不同——**全量下载可收敛，合并不可收敛**。
这不是数据丢失（B 多一个未被引用的分类），但属于「用户以为同步了、其实没完全对齐」的行为差异。

### 5.3 `direction=unknown` 导致合并只应用了 1/8 个账本

**现象**：R3 B 端启动检查日志：

```
StartupSyncChecker: 账本 家庭共用账本 与云端指纹不一致但无法判断新旧（direction=unknown），不纳入启动下载候选
...（同样 7 个账本）...
StartupSyncChecker: 发现 1 个候选账本
```

8 个账本里只有「历史回忆账本」被判为 `cloudNewer` 进入候选，其余 7 个因
`direction=unknown` 被跳过，于是弹窗写「检测到 **1** 个账本有云端更新」。

**影响**：这是**防误覆盖**的设计（无法判定新旧时不自动合并），但用户看到「1 个账本」很容易
误以为其余 7 个已经同步。R3 的分类分叉（5.2）与该跳过行为叠加后才显现出来。
建议在 UI 上把「另有 N 个账本因无法判定方向未纳入本次合并」显式告知。

### 5.4 启动同步检查遮罩会阻断全部交互（设计内，但易被误判为卡死）

`lib/cloud/startup_sync_overlay.dart` 明确「遮罩强制阻断底层交互（`AbsorbPointer` +
`barrierDismissible:false`）」。实测在 R2/R4 冷启动时，该遮罩出现后所有 `input tap` 被背景层吸收，
表现为「点了完全没反应」，必须点遮罩上的「确定」才恢复。
第 5.5 条的 uiautomator 漏采会进一步放大这种误判。

### 5.5 自动化侧：`uiautomator` dump 会漏掉 Flutter 遮罩弹窗（测试工具缺陷）

R4 在 A 端冷启动时，「云端有更新」弹窗**实际已在屏幕上**（`screencap` 截图可见
「检测到 1 个账本有云端更新 / 一键应用全部 / 逐个确认 / 暂不合并」），
但连续多次 `uiautomator dump` 的 XML **只含底层首页、完全不含该弹窗**，
导致脚本判定「无弹窗」并反复空点。改用 `adb exec-out screencap` 截图肉眼确认后才定位。
**后续任何依赖 dump 判定遮罩的脚本，都必须有截图兜底**，否则会把「有弹窗」误判成「App 卡死」。

### 5.6 A 端「测-转账」分类的本地删除（**已在同日 WebDAV 轮定位根因**）

A 端在 R2→R3 之间（15:54:58 指纹仍为 29 个分类 → 15:59:45 变为 28 个）本地少了分类「测-转账」
（`kind=transfer`）。本轮当时只能定位到时间窗；**在同日 WebDAV 轮中已精确定位**，结论回填如下：

```
15:58:26 [LocalRepository] transfer 分类发现 2 条,合并 → keeper=1 dupes=[29]
```

根因是 `lib/data/repositories/local/local_repository.dart:2056` `getTransferCategory()` 的
**重复 transfer 分类被动合并**：库里存在 2 条 `kind='transfer'` 分类（App seed 的默认「转账」
+ 注入脚本建的「测-转账」）时，首次调用该方法即保留 id 最小的 keeper、删除其余 dupe。
WebDAV 轮同样命中（`18:59:24 ... keeper=1 dupes=[29]`），**跨后端可复现**。

已排除的因素：

- **无数据损伤**：该分类本就无人引用 —— 两端 4386 笔 transfer 交易的 `category_id` 全部为 NULL，
  `category_id` 指向不存在分类的孤儿交易数为 **0**。
- **不是孤儿清理器**：`lib/services/maintenance/orphan_cleaner.dart` 只挂在
  `lib/pages/maintenance/orphan_cleanup_page.dart` 手动页，本轮未触发。
- **不是同步侧**：A 端快照导出只是少了这条分类，删除发生在本地。

**为何没同步到 B 端（关键）**：该合并在 `changeTracker != null` 时本应为每个 dupe 记
`action: 'delete'`（`:2130-2138`），但实测两轮 `local_changes` **只有注入脚本写的 40170 条
`upsert`，一条 delete 都没有**。

**成因（已在代码中定位，属 CT-1 已知范畴）**：`lib/providers/database_providers.dart:40-44`
生产注入的是 `LocalRepository(db)`，**不传 `changeTracker`**；该文件 `:31-39` 已明确记载
「CT-1（2026-09-21 已处置）：不注入 tracker 意味着 local_changes 生产恒空」，
且 `TransactionsSyncManager` 两处读端已改用业务表代际 / v40 触碰列。
本报告实测数据与该结论完全吻合。

因此本项**不是新缺陷，而是「已知架构决策 + 一处未同步更新的注释与死代码」**：
`getTransferCategory()` 的 `:2107-2139` 整块在生产永不可达，
而 `:2061-2064` 的注释仍承诺「其它设备下次 pull 时也能自动擦掉脏数据」——该承诺不会发生。
需修的是**注释与死代码**，不是同步机制。

**严重性**：B 端的重复 transfer 分类会被 B 自己下次调用 `getTransferCategory()` 时清掉，
属 transient / 自我修复，不构成永久数据不一致（代码推理，本轮未在 B 端实测触发）。

详见 `docs/test/WebDAV同步功能测试报告_20261003.md` 第 5.4 节。

## 6. 测试方法学踩坑（供后续复测参考）

1. **拉库必须连 `-wal` 一起拉**。Drift 走 WAL 模式，App 运行期间的新提交可能还在
   `piggycount.sqlite-wal` 里。只 `cat piggycount.sqlite` 会静默丢行——
   本轮 R1 一度因此把 A 的 40008 笔看成 40000 笔，凭空多出 8 笔「仅 B 有」的假差异，
   还差点被当成同步 bug。正确做法：`exec-out` 拉 `sqlite` + `-wal` + `-shm` 三件套同目录落盘，
   由 Python `sqlite3` 打开时自动重放 WAL。
   另注：`adb shell cat` 会把 `\n` 转成 `\r\n`，**拉二进制必须用 `adb exec-out`**。
2. **比对脚本必须传绝对路径**。`compare_sync_final.py` 在 `cwd` 不是仓库根时找不到 `lib/`，
   会跳过契约派生校验；更坑的是若给错相对路径，`sqlite3.connect` 会**新建空库**，
   于是 `validate_spec` 把每一列都报成「无此列」，退出码 3 伪装成「契约漂移」。
3. **写入必须走 App**。绕过 Repository 直接改 DB 不产生 `local_changes`、也不触发内容代际失效，
   这种改动不会被上传，测试会得到「改了但没同步」的假阴性。
4. 模拟器会自发旋转到横屏导致坐标全变，每次操作前建议固定
   `settings put system user_rotation 0`。
