### 4.4 R1 观测到「人工全量上传 + 自动同步补传」两批 —— 自动同步的旁证

R1 的 A 端日志里出现**两批**上传（相隔约 30s，同一批 8 个对象）：

```
09:45:15  Starting upload ×8（人工「全量上传」，带 附件对象上传完成）
09:45:17  上传完成: 8
09:45:47  Starting upload: ledger_433218b8-…json   ← 第二批，逐本、无附件对象
09:45:48  Starting upload: ledger_45687b9f-…json
…（逐本 1..8）
```

原因是**测试开始时 A 端「自动同步账本」已处于开启状态**
（基线读取 `auto_sync = true`）。种子的 `local_changes`（40170 条）在 App 启动后触发了
账面变更代际失效 → 自动上传路径在人工全量上传之后又逐本补传了一轮。
这**不是缺陷**，属自动同步的正常工作；本轮 AS 轮即以此机制单独做成一个受控用例（见 4.0 / 4.3）。

## 6. 问题分析

本轮**未发现任何非预期不一致**。以下 4 类"差异/现象"经回源码核实**均为设计内行为或测试构造性现象**。

### 6.1 `deleted_transactions` A=3 / B=0 —— 刻意设计，非缺陷

| 轮次 | A `transactions` | A 回收站 | B `transactions` | B 回收站 |
| --- | --- | --- | --- | --- |
| R1 | 40008 | 0 | 40008 | 0 |
| R2（软删 1 笔） | 40007 | **1** | 40007 | **0** |
| R3 | 40007 | 1 | 40007 | 0 |
| R4（再软删 1 笔） | 40006 | **2** | 40006 | 0 |
| AS（再软删 1 笔） | 40005 | **3** | 40005 | 0 |

**定性：设计行为。** 依据 `lib/pages/maintenance/recycle_bin_page.dart` 类文档
——「回收站只在本机：归档行不进快照（`transactions_json` 只导 `transactions` 表），
所以它既不上云也不进备份」。即：**删除的语义（主表少一笔）传播，删除的「原件」（归档行）不传播**。

**影响**：删除效果能正确跨设备生效（A/B 主表逐字段一致，被删的 3 笔在 B 端主表均为 0 行，
不存在「删了又复活」）；但 B 端回收站为空，用户无法在 B 端恢复该笔（需回 A 端恢复后再同步）。
工具侧 `compare_sync_final.py` 的 `DEVICE_LOCAL_TABLES` 单列块把它显式打印为 `[OK*]`（不计入 issues、不影响退出码）。

### 6.2 R3 分类 29 → 28：`getTransferCategory()` 被动合并（已知行为，两端同步收敛）

R3 的 A 端契约内变化里，`categories` 消失了一条 `b20c86b1`（`name=测-转账, kind=transfer, sort_order=108`）。

**代码级根因**：`lib/data/repositories/local/local_repository.dart` 的 `getTransferCategory()`
存在**重复 transfer 分类被动合并** —— 库里同时有 App seed 的默认「转账」（`id=1`）与注入脚本建的
「测-转账」两条 `kind='transfer'` 分类时，首次调用即保留 id 最小的 keeper、删除 dupe。

**触发时机（为什么恰好是 R3）**：该方法是**懒触发**——只有调用它的页面才执行合并。
R3 的操作路径是「资产 → 点账户 → 账户详情/编辑」，正是这条读取触发了合并。

**与端一致性的关系**：本轮 R3 的 A 端合并后**立即走全量上传**（快照里已是 28 条），
B 端全量下载导入后同为 28 —— **两端同步收敛，不存在分叉**。被合并掉的是**无人引用**的分类
（4386 笔 transfer 交易的 `category_id` 全为 NULL，孤儿交易 0），不构成数据损伤。

> 该现象在 2026-10-04 的 S3 轮与 WebDAV 轮均已复现，成因完全一致，结论为
> **测试数据构造性现象 + 产品设计内自愈**，不是同步缺陷。生产环境不会出现重复 transfer 分类。

### 6.3 契约外字段差异（5000~5002 行）—— 预期差异，不计入不一致

| 表 | 差异列 | 性质 |
| --- | --- | --- |
| ledgers | `is_shared, member_count, owner_user_id, created_at, updated_at` | 设备本地/共享元数据 |
| accounts / tags / budgets / recurring / exchange_rate_overrides / attachments | `created_at, updated_at` | 设备本地时间戳 |
| transactions | `created_by_user_id, last_edited_by_user_id` | 本条由**哪台设备**录入 |

这些列**不在同步契约内**（`compare_sync_final.py` 的 SPEC 显式列出），两端天然不同且不影响业务语义。

### 6.4 启动期「纯内容差异」零提示 —— 沿用既有结论，非同步正确性问题

R2（1 本内容差异）、R3（8 本内容差异，账户是 user-global）、AS（1 本内容差异）的 B 端冷启动
**均无弹窗**（静默）；仅 R4 改的是**账本名（元信息）**时会弹「云端账本信息与本地不同」。
这与 `startup_sync_checker.dart`（`SyncDiff.different` → `direction=unknown` → 不纳入候选 →
`candidates.isEmpty` 且无元信息差异时 `controller.dismiss()` 静默）的刻意保守取舍一致，
结论与 2026-10-04 两轮完全相同（**第三次独立复现**）。用户从「我的 → 云同步」手动全量下载即可正常收敛。

### 6.5 云配置保全的判据说明（重要）
