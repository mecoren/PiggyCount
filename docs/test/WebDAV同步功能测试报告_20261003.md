### 1.1 测试环境搭建：端口 8443 被 Windows 保留（已解决，未改设备配置）

两台设备保存的 WebDAV 地址是 `https://10.0.2.2:8443`，但本机 **8443 落在 Windows 保留端口段
8355–8454**（Hyper-V/WinNAT 的 100 端口动态保留块），宿主 `bind()` 直接 `WinError 10013`；
释放该保留段需要管理员权限。

**采用方案：模拟器内 `iptables` DNAT 透明重定向**，宿主服务器改 listens 8088：

```bash
# 宿主机：python webdav_server.py --host 127.0.0.1 --port 8088
# 设备内（adb root 后）：
iptables -t nat -A OUTPUT -p tcp -d 10.0.2.2 --dport 8443 \
         -j DNAT --to-destination 10.0.2.2:8088
```

效果：**App 仍按原配置访问 `https://10.0.2.2:8443`，两台设备的 WebDAV 配置零改动**，
内核在出网前把 8443 改写到 8088，对 App 完全透明。证书侧双重保险：
`webdav_provider.dart` 的 `badCertificateCallback` 只校验 host（忽略 port），
而 `_isDevTestServer` 要求的 `port == 8443` 依然成立，两条路径都满足。

实测两台设备 `nc` 连通、App 内 `发现云端账本` 成功 PROPFIND 列出 8 个账本、TLS 自签证书放行 ——
证明 HTTPS + Basic Auth + PROPFIND 全链路在重定向下工作正常。
（重定向规则在模拟器内存中，重启即失效；复测时用 `wd_redirect.py add` 重新加即可。）

## 5. 问题分析

### 5.1 `transactions.note` 的 `NULL → ''` 归一化（预期行为，与 S3 轮完全一致）

**现象**：凡「UI 新建且未填备注」的交易，A 端 `note IS NULL`，B 端 `note = ''`。
WDR2 的 1 处、WDR3/WDR4 的 2 处，全部是本轮通过 UI 新建的 123.50 与 77.77 两笔。

**根因（代码级）**：`lib/cloud/transactions_json.dart:211` 导出时
`'note': _sanitizeString(t.note)`，而 `_sanitizeString`（同文件 `:16-17`）对 `null` 返回 `''`。
对比同文件 `:170` 账户 note 用的是 `if (a.note != null) 'note': ...`（null 时不写该键），
**交易 note 缺这层保护**，是两端唯一的写法差异。导入端 `_readString(m, 'note')` 读到 `''` 即落库为 `''`。

**为何同步引擎察觉不到**：`lib/cloud/sync_fingerprint.dart:138`
`'note': it['note'] as String? ?? ''` —— 指纹**刻意**把 `null` 与 `''` 视作同一值
（同口径还覆盖 `categoryName` / `categoryKind` / 三个 `*SyncIdOverride`）。
因此该差异对指纹与差异比对完全不可见，不产生假「有更新」，也不会来回抖动。

**影响**：仅字节级不一致，UI 表现一致，属**设计内的等价归一化**。

### 5.2 合并路径（一键应用全部）不传播实体删除 —— 与 S3 轮同因复现

**现象**：A 端分类 29 → 28，B 端走**合并**后仍为 29；改走**全量下载**后收敛到 28。

**机制**：`SyncDiffService` 输出 `新增=1, 修改=0, 删除=0`，差异应用只有新增/更新语义，
**没有删除语义**；`全量下载` 走 `DataImport`「恢复前清空账本」的整体替换，因此能收敛。

### 5.3 `direction=unknown` 导致合并只应用部分账本 —— 与 S3 轮同因复现

WDR3 B 端启动检查同样把多数账本判为 `direction=unknown` 而跳过，只对 1 个账本弹合并：

```
StartupSyncChecker: 1 个账本与云端数据不一致但方向未知，不弹更新提示，请到云同步页面手动处理
```

WDR2 中云端元信息变更（改名 + 起始日）也被识别并提示到同步页手动处理，行为与 S3 轮一致。

### 5.4 根因定位：A 端少掉的分类是「重复 transfer 分类被动合并」（本轮新定位）

S3 轮中这项只做到「可复现但触发路径未定位」。本轮通过 App 结构化日志精确锁定：

```
15:58:26 [LocalRepository] transfer 分类发现 2 条,合并 → keeper=1 dupes=[29]
15:59:45 [Fingerprint] 交易数: 5002, 账户数: 61, 分类数: 28, ...
```

WebDAV 轮同一条日志同样出现（`18:59:24 ... keeper=1 dupes=[29]`）。

**代码位置**：`lib/data/repositories/local/local_repository.dart:2056` `getTransferCategory()`。
当 `kind='transfer'` 的分类多于 1 条时，它**被动合并**：保留 id 最小的 keeper，
把引用 dupes 的 transactions / budgets / recurring_transactions 改写到 keeper，再删除 dupes。

**为什么本轮数据会命中**：注入脚本按账本创建了自定义 transfer 分类「测-转账」，
而 App 自身 seed 也会建一条默认「转账」，于是同一库里存在 2 条 transfer 分类，
首次调用 `getTransferCategory()`（记账转账流程等）即触发合并。

**数据影响：无。** 实测两端 4386 笔 transfer 交易的 `category_id` **全部为 NULL**，
指向不存在分类的孤儿交易数为 **0** —— 被删的「测-转账」本就无人引用。

**为何没同步到 B 端**：该合并在 `changeTracker != null` 时会为每个 dupe 记
`action: 'delete'`（`:2130-2138`，注释明确写「推到云端，同账号的其它设备下次 pull 时也能自动擦掉」）。
但实测两轮的 `local_changes` **只有注入脚本写的 40170 条 `upsert`，一条 `delete` 都没有**
（`chg_stat.py` 统计：action 分布仅 `upsert`）。

**成因（已在代码中定位，属 CT-1 的已知范畴）**：`lib/providers/database_providers.dart:40-44`
生产注入的是 `LocalRepository(db)` —— **不传 `changeTracker`**。该文件 `:31-39` 的注释已明确记载：
「ChangeTracker 随云端协同下线移除；快照备份路径不注入 tracker」，
并标注 **⚠️ CT-1（2026-09-21 已处置）：本行「不注入 tracker」意味着 local_changes 生产恒空**。
`TransactionsSyncManager` 的两处读端已分别改造（指纹校验位改用业务表代际、方向仲裁改用 v40 触碰列），
本报告的实测数据（40170 条 upsert / 0 条 delete）与该结论完全吻合。

因此本项**不是新发现的缺陷，而是「已知架构决策 + 一处未同步更新的注释与死代码」**：
`getTransferCategory()` 里 `:2107-2139` 的 `if (changeTracker != null) { … }`
整块在生产**永不可达**，而 `:2061-2064` 的注释仍在承诺一个不会发生的行为。
真正需要修的是**注释与死代码**，而非同步机制本身。

**严重性下调（重要）**：B 端持有同一条重复 transfer 分类，但 `getTransferCategory()` 是
**本地逻辑**——B 在下次走到转账相关流程时会跑同一套合并、同样删掉它。
因此该分叉是** transient / 自我修复**的，不会造成永久数据不一致
（此项为代码推理，本轮未在 B 端实测触发）。

### 5.5 自动化侧：uiautomator 会漏采 Flutter 遮罩弹窗

WebDAV 轮再次复现 S3 轮记录的问题：冷启动时「云端有更新」弹窗**实际在屏幕上**
（`screencap` 可见「检测到 1 个账本有云端更新 / 一键应用全部 / 逐个确认 / 暂不合并」），
但连续多次 `uiautomator dump` 只含底层首页，脚本判定「无弹窗」并反复空点，表现为 App 卡死。
另外「清空账本」这类**破坏性确认弹窗**的正文也不出现在 dump 里（只暴露「取消/确定」两个按钮），
一度导致按坐标盲点命中「清空账本」——已及时取消，未造成数据损失（该账本笔数核对无变化）。
**结论：涉及破坏性操作时必须截图确认，不能只信 dump。**

### 5.6 环境侧：WebDAV 落盘体积约为 S3 的 2 倍

同一账本，gzip 后载荷约 269KB；S3 直接存二进制约 270KB，WebDAV 落盘约 540KB。
原因是 WebDAV 后端把二进制包进 `pc-wdav-env-v1` 信封并 base64 编码后 PUT。
不影响正确性，但相同账本量下 WebDAV 的存储与流量约为 S3 的 2 倍，
选型时若在意存储成本或带宽应把这一点算进去。

| 幂等/收敛 | ✅ WDR4 复传 + 全量下载后完全收敛 |

**可交付判定：WebDAV 同步功能通过**，且与 S3 路径行为一致。

### 与 S3 轮的横向对照

| 现象 | S3 | WebDAV | 判定 |
| --- | --- | --- | --- |
| 基线全量同步字段差异 | 0 | 0 | 一致 |
| `note` `NULL→''` 归一化 | 有 | 有 | 同因（共享 `lib/cloud`） |
| 合并路径不传播删除 | 有 | 有 | 同因 |
| `direction=unknown` 跳过账本 | 有 | 有 | 同因 |
| transfer 分类被动合并 | 有（未定位触发） | 有（**已定位到 `getTransferCategory()`**） | 同因，WebDAV 轮完成定位 |
| `local_changes` 无 delete 记录 | 有 | 有 | 同因 |

**三项行为差异全部位于共享同步层，与后端实现无关**，因此对 iCloud 等其它文件式后端同样成立。

### 遗留建议

1. `transactions_json.dart:211` 的 note 导出补 `if (t.note != null)` 保护，与账户 note 写法对齐（或明确把 `note` 列入比对白名单）。
2. 合并接收路径补删除语义，或在 UI 显式提示「另有 N 个账本因方向未知未纳入本次合并」。
3. `getTransferCategory()` 的合并删除未进入 `local_changes`（`changeTracker` 为 null 的调用路径），
   导致 `:2061-2064` 注释承诺的「其它设备自动擦除」不成立 —— 需补齐登记或修正注释。
4. 若关注存储/带宽，评估 WebDAV 信封的 base64 编码开销（约为 S3 的 2 倍）。
