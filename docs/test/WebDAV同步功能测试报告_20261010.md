## 7. 问题分析

### 7.1 【前置环境·已处理】设备上既有的 WebDAV 配置是**垃圾值**，导致同步按钮禁用

**现象**：本轮开始时（清库、切后端都成功后）A 端同步页的「全量上传 / 全量下载」**不可点** ——
uiautomator 里表现为一个**不可点的合并卡片节点**（desc 同时含两个按钮文案，bounds `[43,1086][1157,1449]`），
编排在等待确认弹窗上停留 5 分钟以上、服务端 **0 次请求**。App 日志给出根因：

```
CloudSyncException: Failed to initialize WebDAV: DioException [connection error]:
  Failed host lookup: '1'
```

**取证**：打开「我的 → 云服务 → 自定义 WebDAV → 配置」，4 个字段的实际取值是
`URL=https://1`、`用户名=1`、`密码`（1 个字符）、`路径=/piggycounttest` —— 明确是**历史遗留的垃圾配置**，
而非本轮造成（`FlutterSecureStorage.xml` 与本阶段开始前的基线**逐字节一致**，见 §8）。

**处理**（**必需的前置修复**，否则无法执行用户要求的 WebDAV 测试）：
在 App 界面内把 4 个字段改为测试服务端的取值 `https://10.0.2.2:8443` / `pctest` / `piggy123` / `/piggycount`
（脚本 `_fix_webdav.py`，纯 UI 输入，不落任何文件、不碰其它条目）。

**改动范围（逐条目证据，`_secure_diff.py`）**：

| 端点 | 安全存储条目 | 新增 | 缺失 | **密文变化** | 密文逐字节相同 |
|---|---|---|---|---|---|
| 16384 | 5 → 5 | 0 | 0 | **仅 `cloud_webdav_cfg`**（612 → 640） | `cloud_s3_cfg / enc_key / enc_salt / enc_verifier` 4 条 |
| 16384 | KeyStorage 1 → 1 | 0 | 0 | **无** | AES key 1 条 |
| 16416 | 12 → 12 | 0 | 0 | **仅 `cloud_webdav_cfg`**（612 → 640） | 其余 **11 条** |
| 16416 | KeyStorage 2 → 2 | 0 | 0 | **无** | 2 条 |

即：**S3 云凭据与同步加密密钥（盐/密钥/校验子）全部未动**，只有 WebDAV 端点条目被修复。
修复后同步页两个按钮立刻恢复为各自可点的独立节点（`[79,1154][1121,1282]`），
且服务端随即收到来自 App 的 `PROPFIND /piggycount/`（`auth:Basic(user='pctest')`）。

### 7.2 【风险·中】备份恢复后方向判定（与 S3 报告 §7.1 同一根因）

现象、复算证据与修复方向完全同 S3 报告 §7.1：
`_localChangeEvidence` 把**全局表**（`accounts / categories / tags / exchange_rate_overrides`）的
`MAX(updated_at)` 与**逐账本**恢复地板比较，而逐账本串行恢复会顺带盖章全局表 ——
先恢复的账本因此把「恢复后写的账本留下的全局痕迹」当成「本机编辑证据」。
本轮 WebDAV 阶段复现同一日志形态（`同步状态: 1 -> SyncDiff.localNewer`，`WDX` 段）。

**同日已落地修复（2026-10-10）**：`_localChangeEvidence` 的证据列按域拆两组、各用各的恢复地板 ——
ledger-scoped 仍用本账本上次恢复（`rs_a`）；user-global（accounts / categories / tags /
exchange_rate_overrides）改用**任意账本**上次恢复（新增 `rs_g`）。地板缺失时两组全成立 →
与原语义逐位相同。守门测试 `test/cloud/local_change_evidence_test.dart` 新增 3 例（含对照断言），
全量 `flutter test` `+2167 ~1` 全绿、`flutter analyze --fatal-infos` 0 issue —— 详见
[S3 报告 §7.1](S3同步功能测试报告_20261010.md)（同一根因、同一修复）。

### 7.3 【环境·非产品】`测试连接` 按钮对自签测试服务器**必然失败**

`lib/pages/cloud/cloud_service_page.dart:1787` 的连接测试用**裸 `http.Client()`** 发 `OPTIONS`，
不带 provider 层的 dev 测试服务器证书放宽（`webdav_provider._isDevTestServer`），
故对自签服务器报：

```
测试失败: Handshake error in client (OS Error: CERTIFICATE_VERIFY_FAILED: unable to get local issuer certificate)
```

但**真实同步链路不受影响** —— provider 路径的 `PROPFIND` 正常到达服务端（服务端审计可见）。
属测试基础设施与 UI 判据的口径差异（值得产品侧知晓：用户若用自签服务器会看到「连接失败」，
但实际同步可用），**非同步正确性问题**。

### 7.4 【工具】「立即备份」的 UI 文案巡检假失败

`wd_extras_run.py` 以「同步页是否出现『最近备份』行」判定备份成功，而该行位于长列表下方、
UI dump 未渲染到时判为 `False`。App 日志与服务端审计均证明备份成功（§6.2）。
与 S3 阶段不同点是：S3 阶段该行恰好渲染在屏内，故判为 `True` —— 同一判据在不同滚动位置结果不同，
属**测试侧脆弱判据**。

### 7.5 【工具·已修】`compare_sync_final.py` 的 SPEC 漂移（同 S3 报告 §7.2）与 `round.py` 的按钮判据

* `compare_sync_final.py` 已在 S3 阶段修复（移除 v51 已 DROP 的 4 个共享账本 override 列），
  本轮 WebDAV 直接受益：**WDR1_CMP 起即为 `exit=0`**（无 S3 阶段那样的首次 `exit=3`）。
* `scripts/sync_regression/round.py`：为「后端不可用导致上传/下载按钮被禁用」这一现场增加**快失败判据** ——
  命中的节点不可点即直接打印诊断并判失败（`exit=2`），不再落在一个不可点的合并卡片上盲点、
  然后空等 3000s 超时。**正常态行为完全不变**（可点节点仍按原坐标点击）。

### 7.6 契约外字段差异（5151~5157 行/轮）—— 预期差异，不计入不一致

`created_at / updated_at`（本机写入时刻）、`created_by_user_id / last_edited_by_user_id`（本条由哪台设备录入）
等不在同步契约内的列，比对器以 `[OK*]` 单列呈现，不计入 issues。

### 7.7 回收站 `deleted_transactions` A=3 / B=0 —— 设计行为

同 S3 报告 §7.5：软删的归档行只在本机，**删除的语义传播、归档的「原件」不传播**。

### 7.8 `categories 29 → 28`（WDR4）—— 转账分类被动合并，两端同步收敛

同 S3 报告 §7.6，两端同步收敛到 28，属测试数据构造性现象 + 产品设计内自愈。

### 7.9 【收尾状态】切回 `s3` 后两端显示 `SyncDiff.different` —— 预期，且**未自动覆盖云端**

按「不删除/不擅自改写云备份」的原则，本阶段结束后把 `cloud_active_type` 切回会话前基线 `s3`
（未把本地数据自动上传到 S3）。切换后 A 端冷启动显示 8 本 `SyncDiff.different`：

* **原因**：两个阶段各注入了一套**独立**的 user-global 实体（holdings / savings_goals 每次注入生成新 `sync_id`）
  与 1 笔独立的 `99999`，故「本地内容」与「S3 云端上 S3 阶段的快照」确实不同（`user-global` 实体参与每本快照的指纹）。
* **处置**：**未做任何自动上传/下载**（避免未经用户确认改写云端备份）。用户在「我的 → 云同步」点
  「全量上传」或「全量下载」即可收敛 —— 这与 App 显示「有差异」的语义一致。
