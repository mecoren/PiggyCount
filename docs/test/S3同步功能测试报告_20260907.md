## 4. 同步操作与验证（步骤2b/2c）

### 4.1 A 端「同步到云端」（我的 → 云同步与备份 → 同步 → 上传）

- UI 路径：我的 → 云同步与备份 → 同步卡片 → **上传** → 确认「全部上传」。

- App 日志（CloudSync tag）逐账本记录：`Starting upload: ledger_<syncId>.json` → `Post-upload verify passed` → `Upload completed`，6/6 账本；附件对象上传 上传=7（含去重跳过）；快照 347~350KB/账本。

- 点击「下载」，12/12 个云端账本导入完成（12 而非 6 的原因见 §5）。

## 5. 异常现象与分析：B 端发现 12 个账本

**现象**：B 端启动检查发现 12 个「本机没有的账本」，全部下载后 B 端有 12 个账本、12,012 笔交易（每账本 ×2）。

**根因**：S3 桶内残留上一轮（2026-09-05）同步测试上传的 6 个旧槽位对象（`ledger_c49e4dc6…`、`ledger_a12da680…`、`ledger_3857215a…`、`ledger_b4caeb10…`、`ledger_68692956…`、`ledger_c999a27b…`），与本轮 6 个新槽位（种子重新生成，syncId 全部不同）并存。发现逻辑按「云端存在、本地无对应身份」正确返回 12 个。A 端当天对旧数据做过 3 轮上传（日志 ts 1788614906/1788617273/1788618392），旧对象确认为历史残留而非本轮写入。

**判定**：测试环境残留，**非本轮同步功能缺陷**——发现/导入逻辑面对「同名不同身份」账本的行为符合设计（槽位 key = syncId，身份不同即不同账本）。

**处置**：B 端 SQL 清理 6 个旧槽位账本（保留本轮 6 个新槽位），`PRAGMA integrity_check=ok`。S3 桶内 6 个旧槽位对象本轮未删除（保留云端事实现场；如需彻底清理，可在账本管理 → 云端账本 → 长按 → 删除云端账本，或后续测试轮开始前清桶）。

**改进建议**（App 侧可选）：发现对话框对「同名账本」按槽位 key 提示时间/指纹辅助用户辨别；或测试指南中要求每轮测试前清理云桶。

## 6. 已知偏差（非数据丢失）

### 6.1 家庭共用账本 `is_shared=0, member_count=1`（A=1/2 → B=0/1）

快照 JSON 协议 v9（`transactions_json.dart`）不序列化 `is_shared`/`member_count`/`owner_user_id`/`ledger_members`——这些是 v24 共享账本（云端协同，已下线）的遗留字段，纯快照同步（S3/WebDAV）设计上不传输。B 端导入时按默认值建账本。账本名称/币种/月起始日/交易数据不受影响。属**设计内行为**。

### 6.2 汇率覆盖 `rate` 文本形态差异（'9.0' vs '9'）

`exchange_rate_overrides.rate` 为 TEXT 列。注入端写入 `'9.0'`，App 导入端按 `str(rate)` 规范化后回写为 `'9'`。数值完全相等（float 归一后 0 差异），为**同值异形**，不影响汇率计算。
