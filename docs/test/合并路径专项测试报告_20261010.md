## 2. 测试基线的曲折（重要，影响对其他现象的理解）

原计划「两端各自全量下载」建立收敛基线，**失败**：下载后 A 端 8 本全部非 inSync
（7 本 `localNewer` + 1 本 `different`），日志给出关键行：

```
指纹不一致 本地: ad901fe5 云端: f995ba72 数量 本地5003/云端5003
```

—— 数量相同、内容不同。原因：**「全量下载（覆盖）」只覆盖交易与账本段，不覆盖本地独有的 user-global 实体**
（本轮 A/B 在本机经历过**另一阶段**的注入，`custom_field_definitions` 两端各 3 条但 syncId 互不相同）。
因此基线改用**发布式收敛**：`A 全量上传 → B 全量下载`，两端都成为「并集」，才拿到 8/8 `inSync` 的干净起点。

> 附带结论：跨阶段（或跨设备各自新建）的 user-global 实体差异**不会**被「全量下载」抹平；
> 想把某一端的内容作为权威，必须走「全量上传」发布。

## 3. 新发现的缺陷

### F-1【缺陷·已定位根因】同名不同 syncId 的自定义字段定义，被「全量下载（覆盖）」**删空**且云端的定义不落地

**现象**：B 端执行「全量下载」后 `custom_field_definitions` **3 → 0**（云端该账本带 3 条）；
该账本状态恒 `SyncDiff.different`（`本地 e8241a2f / 云端 bdbf6277`，笔数相同）；
交易侧的字段**值**仍在（5 笔），但定义没了 → 编辑表单无渲染位（值成孤儿、字段从 UI 消失）。

**根因链（代码级，证据充分）**
1. `importCustomFields`（`lib/services/data_import_service.dart:1072`）匹配顺序 `bySyncId[sid] ?? byName[field.name]`（`:1092`）：
   syncId 找不到时**退回同名匹配**；同名命中后只对齐 `name/fieldType/sortOrder`（`:1121`），
   **从不采纳云端的 syncId**；三者都无需变更时 `:1116` 直接 `continue`。
2. 紧随其后的 `_mirrorDeleteAbsentEntities`（同文件 `:2607-2613`）按 **syncId** 判定「云端已删」并删除
   （且云端列表为空时**删光本账本所有带 syncId 的行**）。
3. 于是「同名、syncId 不同」的定义：导入侧按名匹配**不新建**，删除侧认定「云端没有」→ **删掉** ⇒ 本地最终 **0**。

**反向验证（决定性对照）**
- A 端（本来就持有与云端同一套 syncId）再执行一次「全量下载」→ 定义**保留**、8/8 `inSync`
  ⇒ 说明**云端快照确实携带该段**，问题在下载端的「导入 ↔ 删除」配合；
- B 端随后走一次**合并路径**（云同步页下载同步）→ `custom_field_definitions` **0 → 3**、该账本转为 **`inSync`**
  ⇒ 合并路径（`importCustomFields` + `mirrorDeleteAbsentCustomFields` 顺序与口径自洽）**能修复**，恢复路径不能。

**可达性**：两台设备**各自新建同名自定义字段**（各自离线录入后再同步）即触发。
**影响**：账本永久 `different`；合并预览里**没有任何可勾选条目**（字段定义走静默镜像删除语义、不产出 diff 条目），
用户在该入口无路可修；本地字段从 UI 消失。

**修复方向（建议，未实施）**：`importCustomFields` 同名命中且 syncId 不同时**采纳云端 syncId**
（给 `repo.updateDefinition` 增加 syncId 能力），让「同名 = 同一字段」的身份先统一；或让镜像删除把「本次按名匹配过的行」视为存在。
补守门测试：`同名 + 不同 syncId + 覆盖下载 ⇒ 定义条数不变、syncId 收敛到云端`。

### F-2【缺陷】恢复（覆盖下载）路径的镜像删除**漏了 v52 持仓与 v53 储蓄目标** → 账本永久 `localNewer`

**现象（本轮终态）**：B 端账本 1 在 x 次「全量下载」后**仍为 `localNewer`**，
因为本地独有的储蓄目标「应急基金」（A 端已删、A 已发布到云端 = 云端没有它）**没有被覆盖下载清掉**：

```
MGfinal_B.sqlite: savings_goals=12  ledger1 目标: ['应急基金', '新手机基金']
（A 端 11 条；云端 = A 的发布内容）
```

**根因（代码级）**：`_mirrorDeleteAbsentEntities`（`lib/services/data_import_service.dart:2570-2717`）的镜像删除分支只覆盖
**预算 / 周期规则 / 自定义字段定义 / 分类 / 标签 / 账户**；**没有** `holdings`（v52）、`savings_goals`（v53）分支。
而合并路径**已有**这两个实体（`SyncEntityKind.holding` / `savingsGoal`，v11/v12 同批补齐）——
两侧口径不对称：合并路径认得「对端已删」，恢复路径不认。

**影响**：本地多出的持仓/储蓄目标在「全量下载」后残留 → 该账本**永久 `localNewer`**；
用户若照状态卡提示「上传覆盖」，就会把这些残留**推回云端**（= 让对端已删的实体复活）；
若反复下载则永远修不好。与 F-1 同属「永久不收敛且用户无路可修」家族。

**修复方向（建议，未实施）**：给 `_mirrorDeleteAbsentEntities` 补 `holdings` / `savings_goals` 两个分支
（持仓为 user-global、储蓄目标为 ledger-scoped，均无外部引用，可直接按 syncId 镜像；口径与既有 `budgets` 分支一致：
**只删「本地已有 syncId」的行**，无 syncId 视为本机新建未上传、保留）。
补守门测试：`本地多一条储蓄目标/持仓 + 覆盖下载 ⇒ 该行消失且账本收敛`。

## 4. 逐场景记录

### 4.1 场景 A：不勾选删除 + 应用（云同步页「下载同步」入口）✅ 通过

**前置**（A 端，UI 操作）：`我的 → 储蓄目标 → 应急基金 → 删除`（**单次危险确认**，3s 倒计时）
+ 明细页改一笔金额（`测-餐饮-晚餐` → `-¥33.33`）→ `同步页 → 全量上传`（8/8、逐本 `Post-upload verify passed`）。

**B 端预览**（`MGB_preview.xml`，结构示例）：

```
同步预览
  修改 1 条 | 删除 1 条
  全选            [checkbox] checked=False
  修改
    10-10 测-餐饮-晚餐 -¥33.33 | 金额: 99999.0 → 33.33, 折算金额: 99999.0 → 33.33   [checkbox] checked=True
  删除
    储蓄目标「应急基金」 | 云端已删除，勾选后一并删除本地                        [checkbox] checked=False   ← SYNC-05
  取消    应用 1 项
```

**动作**：不勾选删除条目，直接点「应用 1 项」。

**结果弹窗原文**（`MGB_result_skip.xml`）：

```
导入：1 条

有 1 个账本存在你未勾选的云端删除，已跳过回传（这些删除本轮不会生效，下次同步会再次提示）
```

**核对**

| 断言 | 证据 | 结果 |
|---|---|---|
| 本地目标未被删 | `MGb1_B.sqlite`：`savings_goals=12`、ledger1 仍含「应急基金」 | ✅ |
| 云端未被写回（不复活） | 全程无上传；B 端此后依旧 `localNewer`（云端仍无该目标） | ✅ |
| 用户被告知「已跳过回传」 | 上述结果弹窗文案 | ✅ |
| 副作用（预期内） | 合并同时把 A 的 3 个自定义字段定义导入 B（F-1 的账本 3 由此 **转为 inSync**） | ✅ |

### 4.2 场景 B：勾选删除 + 应用 ⚠️ 未完成（原因见 4.3）

计划链路：账本页 → 冲突弹窗「同步冲突」→「对比合并」→ 预览里勾选删除 → 应用 → 期望
「删除落地（B 的 12 → 11）+ 合并后回传放行 + 两端收敛」。
**未取得该状态**：进入执行时 B 的差异账本方向已变为 `localNewer`（见下），两个入口都不再呈现该条目。

### 4.3 为什么「勾选删除」这一步拿不到（两条入口的判据差异）

| 入口 | 触发判据 | 本轮实测 |
|---|---|---|
| 云同步页「下载同步」 | 逐账本 diff 预览（本轮首次进入时账本 1 为 `different` → **有预览**，即 4.1 那次） | 场景 A 之后账本 1 变 `localNewer` → **再点该入口已无该账本的预览**，App 自述「无候选账本，全部都是最新」 |
| 账本页「对比合并」 | `_handleLocalLedgerTap`：仅当 `syncStatus?.diff == SyncDiff.different` 才弹冲突框（`lib/pages/main/ledgers_page_new.dart:334-344`），否则**只切账本 + Toast** | 账本页卡片**不显示任何同步状态**，且 `localNewer` 时点击无冲突框 → 无法进入对比合并 |

> 观察（记为待确认 UX 风险）：**「不勾选删除 → 跳过回传」之后，该账本的实体删除条目在两个下载/合并入口都不再出现**
> （方向判成 `localNewer`，启动检查也把它排除在候选之外）。用户此时的可见出路只有
> 「全量上传（覆盖）」= 把对端已删的实体复活，或者手工删掉本地实体。
> 本轮只取得一次观测（`MGC2_preview_timeout.xml`、`MGC2_logcat2.txt`：`StartupSyncChecker: 无候选账本，全部都是最新`），
> 建议后续单独复测确认（例如显式构造 `different` 态后立刻走「对比合并」）。

## 7. 建议处置优先级

1. **F-2**（恢复路径补 `holdings` / `savings_goals` 镜像删除）—— 影响面最广：任何「本地有、云端无」的持仓/储蓄目标都会让账本永久 `localNewer`，且把用户推向「上传覆盖」= 复活对端已删实体。
2. **F-1**（导入侧同名命中采纳云端 syncId）—— 触发条件较窄（同名不同 syncId），但一旦命中是**本地字段消失 + 永久 `different`**。
3. **§4.3 的入口可达性**：确认「不勾选删除后该条目在两个入口都不再出现」是否为稳定的死路；若是，需要给用户一条明确出路（例如状态卡直接给出「重新对比合并」入口，或在 `localNewer` 下也提供「采纳云端删除」的操作）。
4. 补测：**账本页「对比合并」**与**启动「逐个确认」**两个入口（本轮未覆盖）。
