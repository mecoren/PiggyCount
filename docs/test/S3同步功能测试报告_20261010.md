## 7. 问题分析

### 7.1 【风险·中】备份恢复后方向仍误判 `localNewer`（复现；本轮定位到**与 2026-10-07 不同的新根因**）

**现象**（`S3_dir_verdicts_applogs.txt`）：备份恢复刚完成（10:13:49）后的同步状态刷新：

```
1791598430459 [CloudSync] 同步状态: 1 -> SyncDiff.localNewer
```

此刻**本地账本 1 = 40009 笔 / 云端 = 40010 笔**（云端多一笔来自 ⑥ 自动同步的 `77.77`），
按内容事实应为 `cloudNewer`。判 `localNewer` 会让同步页指引用户「上传覆盖」，
把只存在于云端的那一笔**静默抹掉**（本轮 ZC 轮实测：上传后云端 40010 → 40009）。

**根因（本轮实测复算，见 `_evidence_repro.py` / `_floor_probe.py`）**：

`_localChangeEvidence`（`lib/cloud/transactions_sync_manager.dart:1000-1044`）的证据查询里，
有两类表混在一起：

* **本账本作用域**：`transactions / budgets / recurring_transactions / ledgers(按 id) / custom_field_definitions / transaction_attachments` —— 都带 `ledger_id = ?`；
* **user-global 作用域**：`accounts / categories / tags / exchange_rate_overrides` —— **不带 ledger_id，取全表 `MAX(updated_at)`**。

而恢复地板 `rs_a` 取的是**该账本自己**的那行 `snapshot_restore/success`（逐账本写入）。
备份恢复是**逐账本串行**的，恢复后写的账本会**顺带盖章那些全局表**，于是对**先恢复的账本**而言，
「全局表的痕迹」落在**它自己的地板之后**。复算 ledger 1：

```
tx_u=1791598412  bg_u=1791598412  rc_u=1791598412  lg_u=1791598411  att_c=1791598412
ac_u=1791596646  ca_u=None  tg_u=None  cf_u=None  lc_c=None
ex_u = 1791598428   ← exchange_rate_overrides（全局表，无 ledger_id）
恢复地板 rs_a = 1791598414（ledger 1）        上传锚点 up_a = 1791598011
未推送 local_changes lc_n = 0
persistedAt = 1791598428  >  floor 1791598414   → persistedValid = true   （错）
persistedAt = 1791598428  >  anchor 1791598011  → 条件 c 成立 → trusted = true
⇒ at = 1791598428，方向判 localNewer
```

`exchange_rate_overrides` 那 3 行的 `updated_at` 全部等于 `1791598428`，而 **ledger 8 的恢复恰好发生在
`1791598428`** —— 即：**「恢复 ledger 8 时对全局表的盖章」被当成了「本机在恢复 ledger 1 之后编辑过内容」**。

**与 2026-10-07 报告 §6.1 的关系**：那条问题（当时标记为「`_purgeStaleLocalChanges` 未清悬挂行」）
已由 `e780cf3b` 修复，本轮 `lc_n = 0`（悬挂行清理**已生效**，日志亦有
`恢复后清理过期的未推送变更 …（含 … 悬挂行）`），**症状却仍在** —— 说明还有第二条独立通路。
修复方向：把「全局表证据」与「逐账本地板」的**口径对齐** —— 要么对
`accounts/categories/tags/exchange_rate_overrides` 改用地板 `MAX(ts) WHERE ledger_id = ? OR ledger_id IS NULL`
（即整轮地板，本轮该行为 `1791598429`，数据已存在，见 `sync_op_log` 第 92 行），
要么把这些全局表排除出本账本的方向仲裁。

**影响面**：用户「从备份恢复」或「整本下载恢复」后，只要该账本不是最后一个被恢复的，
就可能被引导去「上传覆盖」而丢弃云端较新副本。**备份恢复/云端整本恢复是唯一触发路径**，
正常编辑-上传场景不受影响（本轮 R2~R5 的方向判定与上传均正常）。

**备注**：该误判是**瞬时**的 —— 下一次成功上传/下载后即恢复 `inSync`（本轮 ZC/ZB 轮已收敛）。
但用户正是**在那一瞬间**看到同步页的指引。

**同日已落地修复（2026-10-10，取「整轮地板」方案）**：
`_localChangeEvidence` 的证据列**按域拆成两组**、各用各的恢复地板 ——
ledger-scoped（transactions / budgets / recurring / ledgers / custom_field_definitions /
transaction_attachments / local_changes）仍用**本账本**上次恢复（`rs_a`）；
user-global（accounts / categories / tags / exchange_rate_overrides）改用
**任意账本**上次恢复（新增 `rs_g`，`sync_op_log` 全表 `MAX(ts) WHERE scenario='snapshot_restore' AND outcome='success'`），
只有晚于它才算本机编辑。两块地板缺失时两组全成立 → 与原语义逐位相同（零行为变化）。
守门测试：`test/cloud/local_change_evidence_test.dart` 新增「整轮恢复地板」组 3 例
（逐账本串行恢复必须作废 / 地板之后的全局编辑仍承认 / 整轮地板不越界作废 ledger-scoped 证据），
其中第 1 例带**对照断言**钉死修复前后的差异。全量 `flutter test` `+2167 ~1` 全绿，
`flutter analyze --fatal-infos` 0 issue。

### 7.3 【环境·非产品】`adb shell` 的 grep 对中文模式段错误，导致提醒测试自评假失败

### 7.5 回收站 `deleted_transactions` A=3 / B=0 —— 设计行为，非缺陷

R4 打开账户详情页触发 `getTransferCategory()` 的重复 transfer 分类合并（保留 id 最小者），

### 7.7 R4 变更脚本自评 `soft_delete=False` —— 脚本判据问题，改动实际已生效
