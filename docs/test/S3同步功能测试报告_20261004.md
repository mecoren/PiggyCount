### 2.1 关于「云端已有旧账本」的处理（重要前提）

清理前云端并非空仓。而 S3 是**文件式**后端：「全量上传」只覆盖同名对象、**不会删除云端独有账本**。
若直接注入 8 个新账本（syncId 不同），云端会变成 16 个账本，B 端全量下载会把 16 个全导进来——
**这不是同步 bug，而是测试构造问题**。

为在**不删除任何云端数据**的前提下让云端恒为 8 个账本，本轮把注入后 8 个账本的 `sync_id`
改写为云端现有的那 8 个（`align_ledger_syncids.py --syncids cloud_syncids.txt`，按 id 顺序一一对应），
上传即**原地覆盖**：

```

id=2 历史回忆账本  <- 45687b9f-f853-599e-8cc4-43bcbc866e19
...
改写完成，账本数=8，distinct sync_id=8
```

> 说明：本轮 A 端启动日志显示 8 个账本均为 `云端指纹: 无`，即**桶内实际已无该对象**
> （上一轮 WebDAV 轮的收尾已把对象留在 WebDAV，S3 桶为空）。因此这次 syncId 对齐属
> **预防性**操作，不改变任何结论。

## 6. 问题分析

### 6.1 `deleted_transactions`（回收站）不参与快照同步 —— **刻意设计，非缺陷**【修订】

**现象**（本轮 S3 轮实测）：

| 轮次 | A `transactions` | A `deleted_transactions` | B `transactions` | B `deleted_transactions` |
| --- | --- | --- | --- | --- |
| R1 | 40008 | 0 | 40008 | 0 |
| R2（软删 1 笔） | 40008 | **1** | 40008 | **0** |
| R3 | 40009 | 1 | 40009 | 0 |
| R4（幂等复传 + 全量下载） | 40009 | **1** | 40009 | **0** |

**同日 WebDAV 轮完全复现**（WDR3/WDR4 均 A=1 / B=0），证明这是**共享同步层行为，与后端无关**。

**代码级根因**：

- 删除交易的本体实现在 `lib/data/repositories/local/local_transaction_repository.dart:811-820`：
  `db.into(db.deletedTransactions).insert(...)` **然后** `db.delete(db.transactions)…go()`。
  即软删 = 「回收站插 1 条 + 主表删 1 条」。
- 全仓检索 `deleted_transactions` / `deletedTransactions` 的引用文件为：
  `lib/data/db.dart`、`lib/data/db.g.dart`、`lib/data/repositories/transaction_repository.dart`、
  `lib/data/repositories/local/local_transaction_repository.dart`、
  `lib/services/maintenance/orphan_scanner.dart`、`lib/widgets/biz/transaction_list.dart`。
  **`lib/cloud/` 目录下 0 处引用** —— 快照导出/导入链路（`transactions_json.dart`）根本不读该表。

**影响评估**：

- **删除的数据效果能正确传播**：快照导出的是 A 端 `transactions`（已被移出被删笔），
  故 B 端导入后主表与 A 端逐字段一致（各轮 `transactions` 差异 0）→ **不存在"删了又复活"**。
- **回收站记录不传播**：B 端回收站为空，用户**无法在 B 端恢复**该笔（需回 A 端恢复后再同步）。

**【修订】这是刻意设计，不是待定方案。** 依据：`lib/pages/maintenance/recycle_bin_page.dart:25-27`
在该页面的类文档里**显式写明**——

> 回收站**只在本机**：归档行不进快照（`transactions_json` 只导 transactions 表），所以它既不上云
> 也不进备份。对端要感知这笔删除，走的仍是原本那条路——本地有/云端无的 diff 项，且按 SYNC-05
> 默认不勾选。

所以「A 删了、B 回收站空着」是设计好的：**删除的语义（主表少一笔）传播，删除的"原件"（归档行）不传播**。
初版把这条写成「新发现 / 或纳入协议」是**定性错误** —— 纳入协议会带来新的问题（归档行与主表需互斥、
两端各自恢复会造重复），并不比现状好。

**真正的缺口在 UI**：设计上说得清楚，用户界面上却**一个字都没提**。多设备用户看到「删除后可在回收站
找回」的提示，天然会以为 B 端也能找回。本轮已补一条说明条（`RecycleBinPage` 顶部 `_localOnlyNote`），
文案走 l10n 四语（`recycleBinLocalOnlyNote`）：
「回收站只在本机：它不参与同步，其他设备上删除的记录也不会出现在这里。」

**一致性工具侧的缺口也已补上**：`scripts/live_db/compare_sync_final.py` 过去完全不知道该表存在，
`exit=0` 只意味着「契约内字段一致」，却极易被读成「全表一致」。现新增
`DEVICE_LOCAL_TABLES` 单列块，打印双端 `deleted_transactions` 行数并注明「设备本地态，设计内不同步」，
**不计入 issues、不影响退出码**；同时把结论文案收窄为「完全一致（限同步契约内字段）」。
实测该块确实抓到了初版会漏掉的差异（S3 R4 / WDR3 均 A=1 B=0）。

### 6.2 R3 分类 `A=28 / B=29`（已知行为，非本轮新缺陷）

R3 唯一不一致为 `categories`：A=28 / B=29，B 端多出 `测-转账`（`kind=transfer`，
syncId `26127b2a-78c2-41a5-b9a4-f711f92efc46`）。

**根因**（20261003 轮已定位，本轮复现）：`lib/data/repositories/local/local_repository.dart`
`getTransferCategory()` 存在**重复 transfer 分类被动合并** —— 库里同时有 App seed 的默认「转账」
与注入脚本建的「测-转账」两条 `kind='transfer'` 分类时，首次调用即保留 id 最小的 keeper、删除 dupe。
A 端 R3 日志：

```
[LocalRepository] transfer 分类发现 2 条,合并 → keeper=1 dupes=[29]
```

该删除发生在**本地**（快照导出前），且因生产未注入 `ChangeTracker`
（`lib/providers/database_providers.dart` 的 CT-1 已知决策），`local_changes` 里没有对应 delete 记录。

**【修订】「不传播」的原因不是缺机制，而是设计上默认不勾选。**
初版写「合并路径不传播删除 / 合并路径不可收敛」，读起来像是缺能力 —— 核实后不成立：
`lib/cloud/sync_diff_service.dart:505-531` 的 `offer()` 会为**「云端缺席（对端已删）+ 本地还在」**
的账户 / 分类 / 标签 / 预算 / 周期规则 / 汇率覆盖产出 `SyncChange(type: deleted, entityDelete: …)`，
而 `:115` 明确写着这些删除类变更 **`selected` 默认为 false**：

```dart
}) : selected = selected ?? (type != SyncChangeType.deleted);
```

即：**候选一直都在，只是按 SYNC-05 口径不预勾选**（破坏性变更需用户显式确认）。R3 走合并、
用户没勾这一条 → B 端保留 29；R4 走**全量下载**（整体替换语义，不经勾选）→ 收敛为 28/28。
两种结果都是设计的预期表现，**不是缺陷**，也不需要"补删除语义"（该语义已由
`bf3cc900 feat(sync,ui): 合并路径补实体删除语义` 于 2026-10-03 落地）。

**影响**：B 端多出的是一个**无人引用**的分类（两端 4386 笔 transfer 交易的 `category_id` 全为 NULL，
孤儿交易数 0），不构成数据损伤；B 端自身下次调用 `getTransferCategory()` 时会清掉（自我修复）。

### 6.3 启动同步检查遮罩会阻断全部交互（设计内）

`lib/cloud/startup_sync_overlay.dart` 使用 `AbsorbPointer` + `barrierDismissible:false`
强制阻断底层交互。R3 冷启动时该遮罩出现后所有 `input tap` 被背景层吸收，表现为「点了完全没反应」，
必须点遮罩上的「确定」才恢复。自动化脚本必须显式处理，否则会把「有遮罩」误判成「App 卡死」。

### 6.4 自动化侧：「dump 漏采遮罩」是**误判** —— 真因是文案组缺失 + grep 错属性【修订】

> ⚠️ 初版本节结论（「`uiautomator dump` 会漏掉 Flutter 遮罩弹窗，需截图兜底」）**不成立，予以撤回**。
> 保留本节是因为这个误判本身很有代表性：它差点让「给测试脚本补截图 OCR」这种昂贵方案被当成正解。

**事实核对**：把当初存下的原始 dump 重新按 `content-desc` 检索，弹窗**一个字段都没漏**：

| 文件 | 语义树里实际采集到的弹窗字段 |
| --- | --- |
| `S3R4_a_16384_home.xml` | `云端有更新`、`检测到 1 个账本有云端更新，是否合并到本地？`、`一键应用全部`、`逐个确认`、`暂不合并` |
| `wdr_overlay_s3.xml` | 同上（正文为「检测到 8 个账本…」） |
| `wd_restore_16416_overlay.xml` | 同上 + 遮罩文案 `云端账本信息与本地不同` |

**为什么会看着像"没采到"**：Flutter 的文本落在 uiautomator 的 **`content-desc`** 上，
`text` 属性恒为空。当初排查时用 `grep 'text="…"'` 去 dump 里找，自然一无所获 ——
于是把「我 grep 错了属性」错归成了「工具采不到」。**这条坑本身值得记住**：
在本项目排查任何 UI dump，`grep text=` 必然空手，必须 `grep content-desc=`。

**真正的两个缺陷都在测试脚本 `flows.py` 里**：

1. **文案组不全**：`BLOCKERS` / `OVERLAY` 里根本没有「一键应用全部 / 逐个确认 / 暂不合并」，
   于是 `dismiss_blockers()` 对这组弹窗**完全无感**。
2. **「到首页」的判据太弱**（这条才是耗掉 6 轮的直接原因）：
   旧实现只判 `「我的」是否出现在 XML 里`。但**模态打开时底层页面元素照样在语义树里**
   （上表 `S3R4_a_16384_home.xml` 里「我的」就在，可弹窗也开着）。
   于是 `boot()` 返回 `True`（"首页就绪"），`open_mine()` 接着连点 6 轮全部被模态 barrier 吃掉，
   报「未进入我的」——**症状指向导航、病根在弹窗**。

**已修复**（`scripts/live_db/run_20261004/flows.py`，该目录被 `.gitignore` 忽略、属运行态资产）：

- 新增 `MERGE_BUTTONS` / `MERGE_POLICY`：「云端有更新」弹窗按调用方指定策略处理
  （`apply` 一键应用全部 / `each` 逐个确认 / `skip` 暂不合并），因为**三个按钮语义不同、选哪个决定测试口径**，
  不能笼统「点确定」。合并弹窗分支**必须排在 `OVERLAY` 之前** —— 它内部也含遮罩文案，但按钮不叫「确定」。
- 新增 `MODAL_MARKERS`，把「无模态残留」并入就绪判据：
  `ready = (无任何 MODAL_MARKERS) and 含「我的」`。
- `open_mine()` 失败时先清模态再重试，并把「疑似残留模态拦截」写进日志。
- 轮次耗尽时落 `boot_fail.xml/.png` 证据，并打印**具体**残留的模态文案。

**顺带挖出一个更隐蔽的坑（差点被我自己引入）**：最初想用 `云端有更新` 当弹窗匹配键，结果全量 dump 统计显示
它命中 **17** 份，而三个按钮只命中 **12** 份 —— 多出来的 5 份
（`S3R4_a_16384_syncpage` / `S3R4_a_16384_upload_pre` / `WDR2B_16416_download_pre` / `WDR2B_16416_syncpage` /
`wdr_mine_ok`）全是**误报源**：`我的` 页和同步页的列表项副标题就是 `同步\n云端有更新`（状态展示）。
拿它做子串匹配会让**正常页面**被永远判成"有弹窗"、再也到不了首页。
故最终用**只存在于弹窗里的按钮文案**做键，并把 `MERGE_DIALOG_NAME` 降级为**仅用于日志显示**。

**复现验证**（用当初存下的真实 dump 离线回放新判据）：4 份真弹窗 → 全部识别为 `MODAL`、`ready=False`、
按钮可定位；`wdr_mine_ok.xml`（我的页）→ `CLEAN` + 含「我的」→ `ready=True`；`*_syncpage.xml` → `CLEAN`。

### 6.5 测试方法学踩坑（供后续复测参考）

1. **拉库必须连 `-wal` 一起拉**。Drift 走 WAL，App 运行期间的新提交可能还在 `piggycount.sqlite-wal`。
   只 `cat piggycount.sqlite` 会静默丢行（上一轮曾把 A 的 40008 笔看成 40000 笔，凭空多出 8 笔假差异）。
   正确做法：`adb exec-out` 拉 `sqlite` + `-wal` + `-shm` 三件套同目录落盘，由 `sqlite3` 打开时自动重放 WAL。
   另注：`adb shell cat` 会把 `\n` 转成 `\r\n`，**拉二进制必须用 `adb exec-out`**。
2. **比对脚本必须传绝对路径**。`compare_sync_final.py` 在 `cwd` 不是仓库根时找不到 `lib/`，
   会跳过契约派生校验；给错相对路径时 `sqlite3.connect` 会**新建空库**，
   于是每列都报「无此列」，退出码 3 伪装成「契约漂移」。
3. **写入必须走 App**。绕过 Repository 直接改 DB 不产生 `local_changes`、也不触发代际失效，
   这种改动不会被上传，测试会得到「改了但没同步」的假阴性。
4. 模拟器会自发旋转到横屏导致坐标全变，操作前固定 `settings put system user_rotation 0`（本轮已设置）。
