### 2.1 关于「云端已有旧账本」的处理（本轮为预防性操作）

S3 是**文件式**后端：「全量上传」只覆盖同名对象、**不会删除云端独有账本**。若直接注入
8 个新账本（syncId 不同），云端会变成 16 个账本。为在**不删除任何云端数据**的前提下
让云端恒为 8 个账本，本轮把 8 个账本的 `sync_id` 改写为云端既有的那 8 个
（`align_ledger_syncids.py --syncids cloud_syncids.txt`，按 id 顺序一一对应），上传即原地覆盖。

> **本轮实测该操作纯属预防**：A 端 R1 冷启动日志（16:29:51）显示 8 个账本**全部**为
> `云端指纹: 无`，即**桶内实际已无对应对象**（上一轮的收尾把对象留在了 WebDAV，
> S3 桶为空）。因此 R1 的「全量上传」是**新建** 8 个对象，而非覆盖。
> 这一点也在 4.6 的收尾状态里得到闭环：本轮结束后桶内为 8 个对象、无多余槽位。

### 4.4 各轮冷启动的云端判读（解释各轮差异范围）

B 端每轮冷启动时 `StartupSyncChecker` 的判读结果，恰好构成一组自洽的因果链：

| 轮次 | B 端启动判读 | 与 A 端改动的对应关系 |
| --- | --- | --- |
| R2 | 仅 **1 个**账本（默认账本）指纹不一致 | R2 改的是默认账本内的交易，其余 7 本未变 |
| R3 | **8 个**账本全部指纹不一致 | R3 改的是**账户**（user-global 实体，被冗余携带进**每一本**快照）→ 8 本指纹同时变 |
| R4 | 1 个账本**云端元信息**与本地不同（`名称「Default-R4RENAMED」月起始日 1`） | R4 改的是账本名，属元信息而非交易内容 |

> 这条链同时从**运行时**侧印证了「账户/分类/标签/预算/周期/汇率覆盖是 user-global，
> 冗余承载于每一本快照」的设计（对应 `lib/cloud/transactions_json.dart` 的 `accounts`
> 导出段）。R2→R3 从「1 本不一致」跳到「8 本不一致」不是异常，是设计结果。

> **判据说明（重要）**：`FlutterSharedPreferences.xml` 的**文件级 sha256 与体积都不适合**
> 作为「配置没动」的判据 —— 该文件里除云配置外还存着 `flutter.app_logs`（**2000 条环形日志**）、
> `current_ledger_id`、各类 LRU 等**运行期必然写入**的内容，体积会随日志环的裁剪
> 上下浮动（基线 521201B / 518730B → 收尾实测在 515066B ~ 542704B / 506024B 之间摆动）。
> 因此证明「配置没动」的正确判据是
> **① secure storage 文件级哈希一致（凭据与密钥的载体）＋ ② 云配置键取值一致 + 条目数一致**，
> 而不是这个混合文件的整体哈希。本轮弃用了「混合文件哈希一致」这种会被日志噪声带偏的判据（见 6.4-4）。

## 6. 问题分析

### 6.1 `deleted_transactions`（回收站）不参与快照同步 —— 刻意设计，非缺陷

| 轮次 | A `transactions` | A 回收站 | B `transactions` | B 回收站 |
| --- | --- | --- | --- | --- |
| R1 | 40008 | 0 | 40008 | 0 |
| R2（软删 1 笔） | 40008 | **1** | 40008 | **0** |
| R3 | 40008 | 1 | 40008 | 0 |
| R4（全量下载后） | 40008 | **1** | 40008 | **0** |

**定性：设计行为。** 依据 `lib/pages/maintenance/recycle_bin_page.dart:25-27` 的类文档
——「回收站只在本机：归档行不进快照（`transactions_json` 只导 transactions 表），
所以它既不上云也不进备份」。即：**删除的语义（主表少一笔）传播，删除的"原件"（归档行）不传播**。

**影响**：删除效果能正确跨设备生效（A/B 主表逐字段一致，被删的 `71b41c24…` 两端均为 0 行，
不存在「删了又复活」）；但 B 端回收站为空，**用户无法在 B 端恢复该笔**（需回 A 端恢复后再同步）。

**工具侧**：`compare_sync_final.py` 的 `DEVICE_LOCAL_TABLES` 单列块把它显式打印为
`[OK*]`（A=1 / B=0 —— 设备本地态，设计内不同步），**不计入 issues、不影响退出码**，
并把结论文案收窄为「无非预期差异（限同步契约内字段）」。这样 `exit=0` 不会被误读成「全表一致」。

### 6.2 R3 分类 29 → 28：`getTransferCategory()` 被动合并（已知行为，本轮两端同步发生）

本轮 R3 唯一的结构变化是分类数从 29 降到 28，消失在 A 端的是
`88e2935d…`（`name=测-转账, kind=transfer, sort_order=108`）。

**代码级根因**（与上一轮同源，本轮复现）：`lib/data/repositories/local/local_repository.dart`
的 `getTransferCategory()` 存在**重复 transfer 分类被动合并** —— 库里同时有 App seed 的默认
「转账」（`id=1`）与注入脚本建的「测-转账」两条 `kind='transfer'` 分类时，首次调用即保留
id 最小的 keeper、删除 dupe。A 端 R3 打开账户详情页触发该调用，于是本地先合并成 28。

**与上一轮的差别（本轮为何没有分叉）**：上一轮 R3 只在 A 端合并，且走的是**合并路径**
（实体删除候选按 SYNC-05 设计默认不勾选）→ 出现 `A=28 / B=29` 的短暂不一致，到 R4 全量下载才收敛。
本轮 R3 之后 A 直接走**全量上传**、B 走**全量下载**（整体替换语义），快照里已经是 28 条 →
B 导入后同为 28。**两种结果都是设计的预期表现，不是缺陷。**

**影响**：被合并掉的是一个**无人引用**的分类（两端 4386 笔 transfer 交易的 `category_id`
全为 NULL，孤儿交易 0），不构成数据损伤；即便 B 端自行保留，下次调用 `getTransferCategory()`
也会自我修复。

### 6.3 启动期「纯内容差异」零提示：保守取舍正确，但告知面不完整【本轮新增】

**现象**（本轮 4 轮冷启动实测，可直接对照）：

| 轮次 | B 端启动时云端差异性质 | 用户看到的提示 |
| --- | --- | --- |
| R2 | 1 本**内容**差异（`SyncDiff.different`） | **无任何弹窗**（仅日志） |
| R3 | 8 本**内容**差异 | **无任何弹窗**（仅日志） |
| R4 | 1 本**元信息**差异（账本名） | ✅ 弹「云端账本信息与本地不同」+ 动作指引 |

**代码级根因**（`lib/cloud/startup_sync_checker.dart`）：

- `:579-592`：`SyncDiff.different`（指纹不同但时间戳/数量相等 → `direction=unknown`）
  的账本**不纳入候选**（`unknownDiffLedgers`），只记日志。
- `:624-676`：`candidates.isEmpty` 分支 ——
  - 若 `metaDiffLedgers.isNotEmpty` → `controller.info(...)` 弹提示（R4 的情形，`:663-673`）；
  - 否则 → **`controller.dismiss()` 静默关闭**（R2 / R3 的情形，`:674`），仅 `softFail` 记账。
- 已有的告知文案 `startupSyncCheckUnknownDiffHint`（四语：「另有 N 个账本本地与云端都有改动、
  无法判断新旧，本次不会同步；如需对齐请到「我的 → 云同步」手动处理。」）**只在
  「有候选」的弹窗里渲染**（`:698-703`）——而 `candidates.isEmpty` 时该弹窗根本不出现。

**为什么会这样（不是拍脑袋的取舍）**：`direction=unknown` 是**刻意的保守仲裁**。
`lib/cloud/transactions_sync_manager.dart:900-955` 说明：方向仲裁一旦误判成
`localAt > remoteAt` 就会**静默放行覆盖云端**（破坏性方向），而 `remoteAt` 来自
对端设备的时钟、存在偏移风险；因此仅在「本地确有未上云内容」的强证据成立时才敢判方向，
**跨设备情形一律退回 `unknown`，交给用户确认**。`startup_sync_checker.dart:580-583` 也写明
不把 `different` 纳入候选是为了避免「unknown 指纹永不收敛 → 每次启动误弹下载提示」。
`:949-955` 还备案了已知缺口（`transactions`/`categories` 无 `created_at` 列 →
跨 session 纯新增不留持久墙钟）。

**结论与建议**：**保守取舍（不自动合并、不阻塞启动）是对的，不建议改动同步语义。**
真正的缺口只在**告知面**：最常见的跨设备场景——「A 上传完，B 冷启动」——恰好落在
「纯内容差异 + 无候选 + 无元信息差异」这一格，于是**一个提示都没有**，用户只能自己去
「我的 → 云同步」才发现「云端有更新」。

> **本轮未改动此行为**：`startup_sync_checker.dart:650-651` 的注释明确写着
> 「不能宣称"已是最新"，也不阻塞用户，静默关闭」，这是一个**刻意的产品取舍**，
> 改它属于产品决策而非缺陷修复。建议（待产品确认）：
> 在 `candidates.isEmpty && unknownDiffLedgers.isNotEmpty && metaDiffLedgers.isEmpty`
> 这一支里，复用**已有**的 `startupSyncCheckUnknownDiffHint` 文案做一次轻量 `controller.info`
> （零新增文案、零同步语义变更、不阻塞交互），把「本次没同步」这件事说出口。

### 6.4 测试方法学踩坑（本轮新踩 3 个，供后续复测参考）

1. **探针静默吞错会造出"看起来通过"的假阴性（本轮最危险的一个）**。
   首版 `mutation_check.py` 的列名写错（`SELECT sync_id, type, ..., custom_values_json`
   里混进了不存在的列），`sqlite3` 抛异常后被 `except → ("ERR", msg)` 吞掉 →
   字典里只剩一个 `"ERR"` 键，**两侧长得一模一样** → 打印「新增 0 / 消失 0 / 字段变化 0」，
   看上去像「R2 什么都没改」。若照此写报告，就会把「改动了 3 处并成功同步」误报成
   「本轮无改动」——**假通过**。已改为**一律不吞 SQL 错误**，并直接复用
   `compare_sync_final.py` 的 `SPEC` + `build()`（见下条）。
2. **本地自增 id 直接比对会造出假告警**。同样的首版探针把 `transactions.category_id`
   （本机自增 id）直接相比，得到 `A=21 vs B=7` 的"差异"——实际上这两条分类的
   **syncId 完全相同**。契约口径是「关系列一律解析成 syncId 后再比」
   （`compare_sync_final.py` 的 `_fk()`）。教训：**跨设备比对永远不要碰 local id**，
   要么复用同一套归一化，要么别写第二套。
3. **logcat 覆盖不全 ≠ 证据丢失**。本轮 R2/R3 的 A 端 `*_logcat.txt` 当时没落盘
   （只剩 `*_boot_logcat.txt`），一度以为「中间两轮的传输证据没了」。
   实际上 `logger_service` 同时把结构化日志写进
   `SharedPreferences.flutter.app_logs`（2000 条环形缓冲，跨重启仍在），
   四轮的 `Starting upload / Post-upload verify passed / 上传完成 / 完整性终审通过 /
   全量覆盖下载完成` **全部还在**（已落盘 `s3_transport_evidence.txt`）。
   **往后的取数顺序应为：先 `flutter.app_logs`，再用 logcat 补实时性。**
4. **云配置保全不能拿「混合 prefs 文件」的哈希当判据**。`FlutterSharedPreferences.xml`
   里混着 `flutter.app_logs`（2000 条环形日志）等运行期必然写入的内容，体积会随日志裁剪
   上下浮动，哈希每轮都不同 —— 拿它比会得出「配置被改了」的**假告警**，
   或者反过来（若在清库这种对称时点比）得出「配置没事」的**假安心**。
   正确判据是 **secure storage 两个文件的哈希（凭据与密钥的实际载体）
   ＋ 云配置键的取值 ＋ 条目数**，本轮按此三件套取证（`final_state.py` / `prefs_keys.py`）。
5. （沿用上一轮）拉库必须 `sqlite` + `-wal` + `-shm` 三件套，且必须用 `adb exec-out`；
   清库只删业务库、绝不碰 `shared_prefs/`；写入必须走 App（绕过 Repository 直接改 DB
   不产生 `local_changes`、不触发代际失效，会被当成"改了但没同步"的假阴性）。
6. 统计口径要显式声明时区：`happened_at` 是 epoch 秒，按 `localtime` 还是 UTC 归年
   会让历史账本的**逐年数字 ±1**（合计不变）。本轮统计统一用 `localtime`（与 App 展示一致）。

## 7. 总体结论

| 维度 | 结论 |
| --- | --- |
| 上传（全量） | ✅ 4 轮 × 8/8 账本成功，逐本 `Post-upload verify passed`，单本 gzip 后 265~280KB |
| 下载（发现→导入 / 全量下载） | ✅ 8/8 成功，逐本 `完整性终审通过(内嵌指纹)` + `全量覆盖下载完成: 成功=8, 失败=0` |
| E2EE 同步加密 | ✅ 密文上传（encrypted+gzip outer）、B 端凭既有密钥直接解密，无需重新输入密码，零解密失败 |
| 数据一致性 | ✅ 40008 笔交易**逐字段差异 0**；其余 10 类实体全一致；**4 轮退出码均为 0** |
| 变更穿透 | ✅ R2/R3/R4 的每一处改动都在 B 端**取值同值**落地（含新增/修改/软删三类操作） |
| 附件 | ✅ 元数据行（9/9）、物理文件 sha256（7/7）、跨账本去重跳过（1 笔）三处均一致 |
| 幂等 / 收敛 | ✅ R4 复传 + 全量下载后，两端 8 本「本地指纹 = 云端指纹」**逐本一致**，无新上传 |
| 回收站 | ✅ **刻意设计**：`deleted_transactions` 不参与快照（删除效果传播、归档原件不传播） |
| 云备份配置 | ✅ 整轮未改动：secure storage 两个文件 sha256 与基线**逐字节一致**，云配置键取值一致 |

**可交付判定：S3 同步功能通过（4 轮闭环、退出码全 0、变更逐项穿透）。**

   纯内容差异时零提示。建议复用已有四语文案做轻量提示；同步语义不动。
2. **（已落地，沿用）** `compare_sync_final.py` 的 `DEVICE_LOCAL_TABLES` 单列块 +
   结论口径收窄（「无非预期差异（限同步契约内字段）」），本轮 4 轮均正确打印 A/B 行数。
