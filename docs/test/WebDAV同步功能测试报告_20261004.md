### 5.4 【铁证】E2EE 附件三段式 sha256 验证

| 环节 | 结论 | 数值 |
| --- | --- | --- |
| A 端落盘附件内容 sha256 | **== 文件名**（明文内容寻址键） | **7/7 相等** |
| B 端解密落盘附件内容 sha256 | **== 文件名** | **7/7 相等** |
| 服务端 `.bin` 对象内容 sha256 | **≠ 文件名**（存的是密文） | **7/7 不等** |

示例（`07dd…`）：

```
文件名（=明文sha） : 07dd2f6385aca43cfeead146e31cbcdb6a345b617a0d0c6336647d488bb72ab6
A 端内容 sha256    : 07dd2f63…ab6   ✅ 相等
B 端内容 sha256    : 07dd2f63…ab6   ✅ 相等
服务端内容 sha256  : 0e23193dd844eedf3fc3f0ff5fc40549eb84f336a3977d6dca17ed901486a2c4  ✅ 不等
```

> 复核者若只看「服务端 sha256 与文件名不符」会误判为 bug —— 这**恰恰证明**服务端存的是密文，
> 而 B 端能解密回与文件名逐字节相同的明文。三段合起来才构成「密文往返无损」的完整证据。

附件落盘实测（B 端目录，7 个文件，大小与 A 端一致）：

```

17184 sha_43d3…a9d.jpg    16197 sha_537f…5cd.jpg    23337 sha_b6ff…1a8.jpg
```

### 5.5 附件恢复的时序特性（重要观察）

WDR1 下载完成、**随即**取快照（`snapdb.py` 会 `force-stop`）时，B 端 `attachments/` 目录为**空**；
**重启 B 端并等待 ~45s 后，7 个附件全部补齐**，且与 A 端逐字节一致。

**机制**：附件恢复由 B 端导入后的后台任务异步完成（从密文信封拉取解密落盘，`drainAttachmentJobs`），
若在任务完成前 `force-stop`，任务被打断。

**结论**：附件恢复是**异步且非原子**于账本导入的。测试时若在下载完成后立即取快照，
会观察到"附件未恢复"的假象——**必须等待或重启一次再判定**。

## 6. 问题分析

### 6.1 `deleted_transactions`（回收站）不参与快照同步 —— **刻意设计，非缺陷**【修订】

**现象**（本轮 WebDAV 轮，`WDR3` 软删 1 笔后）：

| 轮次 | A `transactions` | A `deleted_transactions` | B `transactions` | B `deleted_transactions` |
| --- | --- | --- | --- | --- |
| WDR1 | 40008 | 0 | 40008 | 0 |
| WDR2 | 40009 | 0 | 40009 | 0 |
| WDR3（软删 1 笔） | 40008 | **1** | 40008 | **0** |
| WDR4（幂等复传 + 全量下载） | 40008 | **1** | 40008 | **0** |

**S3 轮同日完全复现**（R2 起 A=1 / B=0，四轮不收敛）→ 属**共享同步层行为，与后端无关**。

**代码级根因**：

- 软删实现：`lib/data/repositories/local/local_transaction_repository.dart:811-820`
  → `db.into(db.deletedTransactions).insert(...)` + `db.delete(db.transactions)…go()`。
- 全仓引用 `deletedTransactions` 的文件仅：`lib/data/db.dart`、`lib/data/db.g.dart`、
  `transaction_repository.dart`、`local_transaction_repository.dart`、
  `orphan_scanner.dart`、`widgets/biz/transaction_list.dart` —— **`lib/cloud/` 下 0 处引用**。
  快照导出/导入链路根本不读该表。

**影响**：

- **删除的数据效果正确传播**（快照导出的是已被移出被删笔的 `transactions`，两端主表逐字段一致，
  不存在"删了又复活"）。
- **回收站记录不传播** → B 端回收站为空，用户**无法在 B 端恢复**该笔。

**【修订】这是刻意设计。** `lib/pages/maintenance/recycle_bin_page.dart:25-27` 在该页面类文档里显式声明
「回收站**只在本机**：归档行不进快照……对端要感知这笔删除，走的仍是原本那条路——本地有/云端无的
diff 项，且按 SYNC-05 默认不勾选」。即**删除的语义传播、归档的"原件"不传播**，是设计好的；
把它当作"或纳入快照协议"的候选方案（初版口径）会引入归档行与主表互斥、两端各自恢复造重复等新问题。

**缺口有三处，本轮均已补**：

1. **UI 从未告知用户**（真正的产品缺口）→ 回收站页新增说明条 `_localOnlyNote`，文案
   `recycleBinLocalOnlyNote` 走 l10n 四语：「回收站只在本机：它不参与同步，其他设备上删除的记录也不会出现在这里。」

### 6.4 合并路径的收敛能力 —— **机制一直在，只差"没勾选"**【修订】

**事实**：「一键应用全部（合并）」只做新增/更新、**不应用删除**；「全量下载」是整体替换语义、**可收敛**。
本轮 WebDAV 四轮**全部走全量下载**，故四轮均无分叉。
（S3 轮 R3 曾出现分类 28/29 分叉，R4 改走全量下载后收敛——两轮对照印证该结论。）

**【修订】「不应用删除」不等于「没有删除能力」。** 读 `startup_sync_checker.dart:1072-1074`：

```dart
// 一键应用：按各变更的默认选中态（SYNC-05：added/modified 默认
// 选中，deleted 本地独有交易默认不选，避免破坏性变更静默执行）
final selected = preview.changes.where((ch) => ch.selected).toList();
```

「一键应用全部」= 应用**所有已勾选项**，而删除类变更**按设计默认不勾选**
（`sync_diff_service.dart:115`：`selected = selected ?? (type != SyncChangeType.deleted)`）。
所以这不是能力缺口，而是**破坏性变更必须由用户显式确认**的既定口径。

配套地，`StartupSyncChecker.shouldSkipMergePublish`（`:816-820`）在存在未勾选云端删除时
**会跳过回传**，防止「用户拒了删除、回传又把已删的东西送回去复活」；且该判据由
启动检查（一键应用 / 逐个确认）与两个手动合并入口**共用**。
实体删除候选本身由 `bf3cc900`（2026-10-03）落地，详见 S3 报告 6.2【修订】。

### 6.5 B 端空库时同步页显示「Exception: 账本 9 不存在」—— **真实兜底缺口，已修**【修订】

**现象**：清库后 B 端进入同步页，我的页「同步」行状态副标题为
`同步\nException: 账本 9 不存在`（原文案在 `lib/cloud/transactions_json.dart:522-524` 抛出）。

**证据（含对初版的更正）**：查 B 端本地库为**完全空**（0 账本 / 0 交易 / 0 `local_changes`），
而 `FlutterSharedPreferences.xml` 里残留 `<long name="flutter.current_ledger_id" value="9" />`。

> ⚠️ 初版写「`flutter.current_ledger_id` 为空」——**记错了**。实测该键就是 `9`
> （`scripts/live_db/run_20261004/WDR1B_16416_16416_prefs.xml`、`bprefs.xml` 均可复核）。
> 这个 9 正是异常里那个 9 —— 结论方向因此完全反转。

**更正后的定性**：初版判「纯测试构造产物、正常用户不会遇到、非同步缺陷」——**不准确**。
`lib/providers/database_providers.dart:85-93` 的注释（**改动前就已存在**）把可达场景列得很清楚：
「账本被其它设备删除后同步下来、本机恢复到他人的备份、清库后重建」。也就是说
**"id 悬空"是已知既存问题，只有"库里有别的账本"那一支做了回落自愈；
"库里一个账本都不剩"这一支漏了** —— 原实现只打了一条 warning 就把 `target` 留着，
于是 `currentLedgerIdProvider` 仍是 9，而「无账本」守卫全仓一律判 `currentLedgerId == 0`
（`cloud_sync_page.dart:635`、`share_poster_service.dart` 四处、`analytics_page.dart:576`、
`transactions_sync_manager.dart:2558`），**9 会把所有这些守卫全部绕过**，一路走到导出时抛异常。
多设备用户删掉本机仅剩的那个账本、或换机恢复备份，就能撞上。

**已修**：`ledgers.isEmpty` 分支改为把悬空 id **归零**（`target = 0;`），交给既有的
`currentLedgerId == 0` 守卫处理；并补齐自愈测试 `test/providers/current_ledger_selfheal_test.dart`
（三条用例：库空 → 归零；目标缺失但库有账本 → 回落最小真实 id；目标存在 → 原样采纳）。

**该现象不影响任何同步结果**：后续 4 轮 WDR1~WDR4 全部 `exit=0`。

### 6.6 测试方法学踩坑

1. **服务端必须以后台任务方式启动**：本会话首次用 `nohup … &` 起的服务随该次 shell 调用被回收
   （`netstat` 已无 8443 监听），App 侧报 `Failed to initialize WebDAV: Connection refused`。
   必须用可存活的后台任务方式并 `netstat` 复核 `LISTENING`。
2. **服务端日志需无缓冲**：Python stdout 重定向到文件时默认块缓冲，日志 0 字节；
   加 `-u` 后立即落盘（多轮测试的日志证据依赖此）。
3. **拉库必须连 `-wal`/`-shm` 一起拉**，且用 `adb exec-out`（`adb shell cat` 会把 `\n` 转 `\r\n` 损坏二进制）。
4. **比对脚本必须传绝对路径**（否则 `sqlite3.connect` 会新建空库，每列报「无此列」、退出码 3 伪装成契约漂移）。
5. **走 localhost 的测试在代理环境下会失败**：`urllib`/Dart 客户端若继承 `HTTP_PROXY` 会走代理隧道
   （本轮探测脚本曾报 `Tunnel connection failed: 502 Bad Gateway`），跑前须清理代理环境变量。
6. **MSYS 路径转换**：设备内绝对路径（`/data/data/...`、`/piggycount/`）传给 adb/python 前需
   `export MSYS_NO_PATHCONV=1`，否则被改写成 Windows 路径。
7. **`uiautomator dump` 的文本在 `content-desc` 上，`text` 恒为空**（本轮最大的排查弯路）：
   `grep 'text="…"'` 永远一无所获，必须 `grep 'content-desc="…"'`。把属性 grep 错，
   就会得出「工具采不到 Flutter 控件」的**错误结论** —— 详见 6.3 的撤回说明。
8. **`&#10;` 等实体不会被解码**：语义树里多行文本形如 `content-desc="同步&#10;云端有更新"`，
   用「状态副标题」当弹窗匹配键会**大面积误报**（实测「云端有更新」命中 17 份 dump，
   真弹窗只有 12 份）。匹配键必须选**只可能出现在目标控件里**的文案。
